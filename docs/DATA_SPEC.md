<a id="doc-01"></a>
### DOC-01：规范状态与声明边界〔确定〕

本文使用以下标记：

| 标记 | 含义 |
|---|---|
| 〔确定〕 | 已确认需求及其在当前架构下的必要契约；“必须/不得”具有约束意义 |

核心类型与身份定义、带编号的规则共同构成逻辑契约；示意路径、历史编码及机制讨论不增加新的强制要求。本文中的“支持”描述实现目标，不是现有脚本能力。

适用后端固定为 HDF5 2.x。一套公共 schema 覆盖多通道单晶、常规 PA、FMC；一个独立、自解释文件代表一个工件的扫描集合，允许多个独立 Scan 表达分块扫描、复扫和精扫。每个 Scan 承载一次固定采集方案；单晶与阵列数据仍不在同文件混存。“PA”指常规固定聚焦法则采集，并不表示 FMC 不属于阵列技术。

跨流异构合法，同一流在所属 Scan 内固定；不同 Scan 可使用不同固定定义。PA/FMC 同文件组合采集、独立通道时间轴、同一流动态变长、Scan 内定义变更、分卷、在线文件读取和 overlay 合并不在本版范围。多 Scan 不自动解除混存限制，也不引入自动拼接、重叠消解或结果替代。

本次修订读取缓冲模型：poll 由 SDK 管理内存、消费者同步拉取并借用只读视图；push 同步复制到调用者指定缓冲。两者与常规分析/Batch 内容交付分别定义，不再把全部读取归为调用者缓冲。Frame 优先、A-Scan 次之，单 Frame 不分块，无写入取消；显式 Flush 与调用级强原子性边界保留。文档版本仍为 `0.2-draft`，须按下述修订追溯要求区分新旧契约，不自动承诺旧实验编码兼容。

本次进一步将波形状态收敛为每槽位一个有效性位：调用者标记有效且通过结构校验的数据视为合法并无损保存，无效槽位零填充；不再分别记录 payload 存在性和业务有效性，也不保留“有值但业务无效”的独立状态。决定与替换边界见 STA-01，具体位图打包及 API 仍待 D-07/D-08/D-10。

`0.2-draft` 是文档版本，不是 HDF5 版本或已分配的文件内 `schema_version`。草案修订之间不自动承诺文件兼容。实验文件及报告必须追溯到所用 Spec 修订（例如文档哈希）、实现版本和 `test-only` 编码；正式标识留待 D-07。旧文件不能只更改版本号就宣称合规；可能的转换要求解释依赖充分、定义确实固定且关联可验证，参数变化需要分 Scan 或明确不支持。源文件不原地改写，本轮不实现迁移。

当前允许报告“某些确定规则已验证”或“采用指定参考映射的实验样例通过”。位置编码、身份编码等必要项未闭合前，不得宣布完整生产文件格式符合性，也不得声称独立读取器无需额外实验说明即可互通。

<a id="core-01"></a>
### CORE-01：Core 范围与调用边界〔确定〕

首版只提供文件内管理和数据、位置、元信息的存取及关联，不实现文件集合管理或派生资源管理。后续能力按基于 HDF5 的 Core + Extensions 方向规划；本轮只规定必要公共描述和扩展内容的关联边界，不设计完整 Extensions 体系或领域 schema。

写入提供同步单 Frame 和 Frame 批次入口；读取提供常规分析的随元信息返回方式，以及一次读取多个 Frame 的 Batch 只读内存视图。每次数据请求明确一个 Scan，以索引关联波形、位置及元信息；Batch 的连续/离散选择形式仍待 D-10，不跨 Scan 自动拼接。文件/Scan 目录和固定描述可独立访问，不做按位置查询。

首版按单 Reader、单 Writer 串行调用设计，不提供线程安全保证，不支持并发 Reader。SDK 仅同步读写；写入输入及 push 读取目标由调用者维持，poll 读取返回 SDK 管理的只读借用视图（BUF-01）。此处不授权同文件读写并行，正常读取仍遵守封存边界；不提供 update，多次等价读取值一致。写入无取消，普通写入不立即落盘；Flush 和批次失败见 WRT-03/IO-01，有效性位图与无效零填充见 STA-01。

Core 不负责等待、补全、设备协议解码、业务字节序转换或坐标计算；必要的存储类型和编码约定不因此省略。平台及语言目标见 DESIGN 的 [Core 决定](DESIGN.md#core-scope)，精确支持矩阵和 ABI 等见 D-12；本阶段不开展实现、部署设计或细节调优。

<a id="logical-model"></a>
## 2. 术语与逻辑模型

| 符号/术语 | 含义 |
|---|---|
| `File` / 工件容器 | 一个工件的 Scan 集合及工件身份；不是全局 Frame 轴，也不是工件已扫描完整的证明；Scan 映射关系待 D-11 |
| `Scan` | 一次扫描主体；持有固定方案、事件定义、波形流集合和共同 Frame 轴，不等于网格或图像 |
| `EventDefinition` / `e` | 固定方案中的发射事件槽位及含义；跨帧复用，不是每次实际发射的参数快照 |
| `WaveformStream` / `k` | 固定事件下固定接收输出的跨帧序列，具有固定 dtype、长度与采样解释；不必等于硬件通道或 dataset |
| `Frame` / `n` | 一次结构闭合的组合记录及其零起点索引，可显式标记无效波形槽位；不是三套模式专属主体 |
| `N` | 逻辑完整 Frame 前缀数量；不是 dataset 的物理长度，正式计数编码待定 |
| `K` | 固定波形流集合；不再表示旧版参数快照数量 |
| `S_k` / `τ_k` / `s` | 流 k 的固定样本数、原始 dtype 与样本索引 |
| `E_x` | 帧相关物理对象的 extent，可大于 N |
| `N_r` | 恢复视图验证出的完整 Frame 前缀长度，不等于声明值一定正确 |
| waveform / AScan | 指定 Frame、指定流的一条原始波形 |

```text
File（一个工件）
  ├─ 工件身份
  └─ Scan 集合
       └─ 每个独立 Scan
            ├─ Scan 描述（用途/区域/来源/坐标映射模型待 D-11）
            ├─ 固定定义
            │    ├─ Scan 共享采集设置与必要几何
            │    ├─ EventDefinition 集合
            │    └─ 各 WaveformStream 的固定接收与采样解释
            ├─ Frame 轴、原始位置与独立完整前缀
            ├─ 按类型/版本描述的元信息；其他坐标内容以额外 dataset 关联 Frame
            └─ WaveformStream 集合：各 Frame 的原始波形及状态
```

逻辑身份为：帧 `(Scan,n)`、事件实例 `(Scan,n,e)`、波形 `(Scan,n,k)`、样本 `(Scan,n,k,s)`。Scan 身份须在文件内唯一，跨文件结果还须携带文件来源；n/e/k 的作用域均为所属 Scan，同名局部身份或相同位置不能跨 Scan 合并。N、E_x、N_r 均逐 Scan 解释，不存在隐含的全文件 Frame 计数。k 静态关联正确的事件与接收输出；这些元组不分配 wire 字段。

接收输出必须辨识实际保存的数据层次，例如单接收阵元信号或固定接收法则的合成波形，不能从 shape、路径或硬件通道编号推断。同一硬件接收通道在不同事件下可以对应不同流。几何、探头、法则与采样解释属于固定定义的组成或引用；内容按 META-01 描述，具体领域子类型可由未来 Extensions 提供。Core 不验证物理法则，但必要身份与关联不能藏入没有类型/版本或作用域说明的任意字典。

| 模式 | 一帧的含义 |
|---|---|
| 多通道单晶 | 既定采集方案归组的一组多通道结果 |
| 常规 PA | 一次采集的全部预定声束槽位及有效性位图，无效槽位零填充 |
| FMC | 一次预定收发矩阵的槽位及有效性位图，结构闭合与全部槽位有效分别判断 |

事件定义不同不自动要求串行执行，共同 Frame 也不证明事件同时发生。“波形流”仅描述身份和跨帧序列，不引入逐通道时间轴、异步拼装或晚到补写。

<a id="scan-01"></a>
### SCAN-01：工件容器与独立 Scan〔确定〕

文件须能识别工件及枚举其中的 Scan。每个 Scan 独立持有固定定义、事件/流集合、Frame 轴、原始位置关联、状态和完整前缀。不同 Scan 的流数、长度、dtype、采样解释或几何可以不同，但每个 Scan 内仍遵守既有不变量及文件的采集类别限制。不能通过同名引用错误复用另一 Scan 的定义。

分块、停止后重新扫描、复扫、精扫、换探头、重装、重新标定或固定定义变化创建新 Scan，不修改旧 Scan。属于同一工件且满足文件类别限制时，可在未封存文件中创建；文件已封存则另建文件，不重新打开追加。跨文件任务关系仍可由外部清单组织，本版不定义跨文件来源解析协议。短暂停顿与一次扫描结束的实际区分仍需场景证据。

首版保持单写者，顺序完成 Scan 后再开始下一 Scan，不引入交错追加多个活动 Scan。每个 Scan 的必要解释须在文件内可解析，不以其他 Scan 的当前默认值解释历史；跨 Scan 定义去重不是本版要求。

<a id="scan-02"></a>
### SCAN-02：Scan 映射关系〔待定〕

已确定的目标是以多个独立 Scan 承载分块扫描工件、复扫/精扫特定区域；每个 Scan 如何映射到工件区域、如何与其他 Scan 关联，仍待决策，**不只是字段编码待定**。本条撤回上一轮提前确定的必填区域/来源、关系方向与基数、无环/已有来源约束、共同工件参考系、坐标变换及映射不可用处理规则。

以下仅为 D-11 的讨论范围，不作为当前强制字段或校验规则：

- 扫描用途、目标区域和来源关系是否需要显式保存，采用何种模型、作用域和必要性约定。
- Scan 与工件区域、Scan 与 Scan 之间的关系类型、引用、方向、基数及合法性约束。
- 是否采用共同参考系、如何表达局部坐标关系，以及是否需要坐标映射或不可用状态。
- 关系的建立/变更时机、读取接口，以及它们是否影响封存、恢复和符合性判断。

上述模型决定前，不要求每个 Scan 提交特定映射，不把缺少这些尚未定义的关系判为错误，也不以 test-only 编码或样例预先选择答案。工件容器、多 Scan 独立身份及原始历史不可覆盖仍按 SCAN-01、WRT-02 执行；不自动拼接、融合、替代或据此宣称完整覆盖的边界不变，见 U-14。Scan 内 Frame 位置绑定、PA 声束及 FMC Tx/Rx 映射不属于本次退回待定的范围。

<a id="rec-01"></a>
### REC-01：共同记录身份〔确定〕

所有流使用同一 Scan 的共同 Frame 轴，波形可追溯到 Frame、事件和接收输出。采集层一次提交完整 Frame 或批次；SDK 不接收逐流追加后等待拼装，不进行时间配准。Frame 不统一解释为一次物理触发；来源 ID 与文件内身份不同，不得据其隐式创建网格或同步关系。

共同 Frame 轴不说明规则网格、空间邻接、位置相同、相位同步或已完成运动校正。位置值相同的帧仍有独立身份。设备来源 ID 的解释由调用者提供，其承载方式属 D-02；SDK 不做回绕展开或自动补空帧。结构闭合不等于全部波形槽位有效；无有效数据以 STA-01 的有效性位和零填充表达，不等待或补采。

<a id="rec-02"></a>
### REC-02：计数、extent 与边界〔确定〕

N 的逻辑计数范围为 u64；n 合法范围为 `0 <= n < N`。实现必须分别检查计数、索引、切片及字节长度运算，不得静默截成 32 位、溢出或把不支持的尺寸当作空选择。

实现支持上限可以低于 u64 编码上限，但必须明确报告。HDF5 的特殊尺寸常量、绑定层整数范围和内存数组限制不能直接冒充普通记录数量。

物理 extent、填充值和完整 Frame 数量必须区分。正常读取不得暴露 `n >= N` 的尾部；必要对象在前缀内缺行或关联不完整时报告结构错误，不能静默缩短后继续宣称完整。旧 `committed_count` 字面值不是本轮已冻结的路径或计数协议。

## 3. 身份、版本与能力

<a id="id-01"></a>
### ID-01：解释身份〔确定〕

文件必须携带可识别的容器格式与 schema 身份、工件身份及各 Scan 身份、采集语义/profile 身份和物理布局身份。它们分别回答“哪套公共约定”“哪个工件/扫描”“采集是什么”“数据如何组织”，不得混用。文件公共描述与 Scan 专属描述的作用域须明确，不能从同级 Scan 隐式继承定义。单晶/阵列类别、PA/FMC 含义不能仅由 shape 推测；必要语义须足以拒绝类别冲突。

读取器在不理解必要 schema/profile/layout 语义时必须拒绝相应解释，不能按路径相似程度或当前设备默认值猜测。精确字段字面值、字符串编码、版本比较与兼容范围留待 D-07；不预设“同一主版本必兼容”。

<a id="id-02"></a>
### ID-02：必要能力与可选扩展〔确定〕

必须区分影响当前请求解释的必要信息和可以忽略的可选辅助块。未知可选辅助块可以跳过；未知必要语义、编码或 filter 不得静默忽略。

如果不支持位置的结构编码、不能验证其 Frame 关联，但仍能独立验证波形及记录范围，可以显式提供受限波形访问；必须报告位置/绑定读取不可用，不能伪造位置或宣布完整 profile 合规。若连记录边界也无法验证，则不能以此降级。不认识位置或元信息的领域 schema，与不能读取其公共描述、内容和索引关联不同：能够按公共约定交付时，不因此宣称已解释其业务含义，具体容器见 META-01/D-10。

扩展须具有格式标识、版本、必要类型/单位、来源与关联说明。能力声明的具体编码属 D-07。状态语义与编码边界见 STA-01。

<a id="meta-01"></a>
### META-01：公共描述与带类型/版本的内容〔确定组织，细节待定〕

元信息采用必要公共描述＋带类型/版本的扩展内容。公共描述须能辨识所关联对象、作用域及内容类型/版本；Core 负责保存、读取和结构关联，不要求理解全部设备或业务字段。固定定义继续按 Scan/事件/流作用域复用；不因可扩展而允许逐帧偷换固定定义。

本阶段不规定完整领域 schema、序列化格式或所有公共字段。更多元信息 schema 可由未来 Extensions 提供；必要公共描述的精确编码、内容承载及读取容器分别留待 D-07/D-09/D-10。类型/版本声明不等于 SDK 已实现该领域的解释器，未知必要公共语义与未知可选内容按 ID-02 区分。

元信息可以独立读取，也须能从相应数据定位其关联内容或可核对引用；不要求每条波形重复复制定义。扩展内容不能替代 Core 必要的 Frame、流、位置及 PA/FMC 映射身份。本轮不由元信息扩展入口引入文件集合或派生资源管理。

## 4. 波形、状态、位置与参数

<a id="wav-01"></a>
### WAV-01：流内固定与自解释〔确定〕

对每条流 k，包含无效槽位零填充的逻辑样本形状表示为：

\[
X_k \in \tau_k^{N\times S_k}
\]

`S_k`、`τ_k`、样本表示、接收输出身份及采样解释在所属 Scan 内固定，跨流、跨 Scan 可以不同；一个 Scan 的原始数据是有身份的数组集合 `k ↦ X_k` 及其有效性位图，不强制为一个 `[N,C,S]` 数组。有效性位决定槽位是否代表真实波形，不能从样本是否全 0 判断。

固定描述必须足以说明各流的类型、字节序、样本含义与必要单位、事件/接收输出映射和采样轴。若有效 ADC 位、对齐、偏置或比例不可缺少，也必须描述；不要求所有设备采用同一组 ADC 字段。相同样本索引、长度或 dtype 不证明相同物理采样时刻或信号处理层次。

实际 dtype 集合、原始整数码/物理量的具体表示和轴参数编码仍属 D-02/D-07。不得仅保存某个本地驱动函数名来替代解释。

<a id="wav-02"></a>
### WAV-02：严格接收与无损保存〔确定〕

每份标记 `valid=1` 的 waveform 必须提供样本，并与对应流的固定长度及 dtype 严格一致。SDK 接受调用者的有效性声明，不做幅值、成像意义或其他业务合法性判断；仍须校验身份、shape/dtype、容量和引用。SDK 不自动截断、补齐、广播、重采样、信号处理或数值转换。`valid=0` 不要求提供波形；若提供，其样本内容忽略，不作为原始数据保存，槽位按 STA-01 零填充；请求结构、位图关联和缓冲边界仍须合法。业务同构化属于显式计算输入转换，不能把转换结果描述为原始回读。写入输入缓冲归调用者，SDK 同步消费；具体布局仍属 D-02，不预设零拷贝或 TCS 输入。

标记有效且通过结构校验的样本必须无损回读，整数样本逐值一致；无效槽位没有调用者原始样本保真承诺。字节序不同的表示不能被直接当作原始字节相同；浮点 NaN、负零等逐位保真规则须在该 dtype 被纳入支持范围前补齐，不能先声称任意类型均受支持。

<a id="sta-01"></a>
### STA-01：单一有效性位图与零填充〔确定语义，打包待定〕

每个 `(Scan,n,k)` 波形槽位只使用一个有效性位 `valid`，默认值为 0；粒度为整条波形，不是逐样本有效性。不再独立保存 payload 存在性与业务有效性，也不区分无数据和“有值但业务无效”的原因。

| 有效性位 | 样本含义与存取行为 |
|---|---|
| `valid=0` | 无有效数据；不要求提供波形，若提供则忽略其样本内容，存储及读取的逻辑样本均为全 0 填充值，不代表真实零回波 |
| `valid=1` | 调用者声明有效，须提供符合 WAV-02 的波形；SDK 按有效数据无损保存和回读，包括真实全 0 波形 |

读取须同时交付所选波形的有效性位图，按相同 Frame/流或 PA/FMC 身份、顺序及重复项对应；不跳过无效槽位。稠密矩阵和 Batch 采用样本数组＋有效性位图，无效槽位零填充；异构结果同样保留各槽位身份、原始类型/长度及对应有效性位。不得仅凭全 0 推断无效，或将 `valid=0` 的填充值当成真实测量。具体返回容器和位图布局仍待 D-08/D-10。

默认位为 0、波形零填充只定义已提交范围内的逻辑表示，不授权暴露预分配尾部或用默认位掩盖位图缺行、损坏及关联错误。未完成写入、结构损坏、解码或 I/O 失败必须报错，不能自动变成 `valid=0` 的成功结果；完整前缀及调用级失败仍按 REC-02/WRT-02/IO-01 验证。SDK 不等待补采或晚到补写，零填充不是信号补全。

零填充不要求预先物理写满整个 dataset；可以通过符合约定的 HDF5 fill value/空间分配等机制实现，但不能把逻辑全 0 等同于磁盘空间、压缩率或性能保证。位图打包、位序、HDF5 映射和接口表示仍待 D-07/D-08/D-10；存储填充按所声明样本类型表达零，具体支持类型仍按 WAV-02 闭合。

本次决定替换旧的双维状态语义及“无效但有 payload 仍保留原始波形”的要求；无损保证仅覆盖标记有效并被接受的波形。旧 PAYLOAD_PRESENT/CALLER_VALID 及 0/1/3 编码不能作为当前用例的状态模型。草案修订追溯仍按 DOC-01，不通过更改版本号宣称旧文件兼容。本规则只处理波形有效性，不替代 D-01 的位置有效性决定。

<a id="pos-01"></a>
### POS-01：采集时位置绑定〔确定〕

每个完整 Frame 必须具有明确的帧级原始采集位置关联；多通道单晶沿用共享关联，PA 使用唯一原始映射位置，见 PA-01。绑定基于 Frame 身份，不依赖时间戳、浮点坐标相等或最近邻搜索。FMC 的矩阵关联不自动提供各收发对的独立空间位置，更细的运动定位模型暂缓。

绑定读取必须对波形、状态与位置使用同一 Frame 选择及对应顺序，并关联正确的固定定义。位置是采集时写入的历史值，不得被后处理或 overlay 静默替换。采集层负责采集关联准确性；SDK 只验证可表达的结构与关联，不进行插值或校准。

“存在位置关联”不预先决定无效位置是否允许及如何表示，见 D-01。不得用零坐标替代尚未定义的缺失位置语义。D-01 必须先决定“波形有效但原始位置获取失败”能否提交，再闭合具体编码；这是提交语义缺口，不只是字段选择，波形有效性位不能替代位置状态。

<a id="pos-02"></a>
### POS-02：位置描述边界〔确定〕

位置仿照元信息，采用必要公共描述＋带类型/版本的内容。不同 Scan 可以使用不同位置描述，同一 Scan 的位置描述固定，每帧保存一份对应值。描述须能说明具体实例的字段、类型、必要单位、轴/参考对象、来源及版本；不预设 XYZ、四元数、编码器轴数或完善的领域 schema。A/B 编码器计数可以作为一份位置值的两个字段，不要求转换成物理坐标。

如果需要同时保存实际反馈坐标、理论坐标等多份坐标内容，以额外 dataset 按 Frame 索引关联，各自保留描述和来源，不转为每束一份独立位置，也不替换帧级原始位置。额外 dataset 的精确引用、值缺失表示、提交时机及是否影响提交/封存仍待 D-01/D-05；不预设所有附加坐标都必填，也不由此承诺晚到补充已提交记录的能力。

独立反馈流不得要求通过时间配准才能恢复 Frame 位置绑定。首版仅按索引关联，不按位置查找数据；未来其他匹配方式与位置 schema 一起规划。Core 不计算坐标变换、标定或空间网格，也不承诺自动恢复 B/C/D 排列。具体编码与无效位置表示仍为 D-01。

<a id="pa-01"></a>
### PA-01：唯一帧位置与派生声束解释〔确定〕

第 n 帧原始关系为 `Frame_n = (P_n, {W_n,b}, 状态与关联)`。PA 帧所有声束共用帧级原始位置 P_n，例如同一对 A/B 编码器值，不为 B 个声束另存 B 份独立位置测量。读取结果可随束交付这一引用，但事实来源保持在 Frame 层。POS-02 的额外坐标 dataset 是独立的按帧关联内容，不改变同帧共享位置的原则。

声束空间解释依赖 `P_n + 固定探头/安装几何 + 对应固定聚焦法则及必要解释`。束号必须找到正确事件和接收输出，不与法则、硬件通道或阵元编号混用。参考样例一组法则对应一个保存声束，不把它变成所有设备的假设。

入射点、方向、焦点与样本空间位置不是同一对象，样本定位可能还需传播模型。本轮不定义坐标字段或几何算法。原始读取不以定位完成为前提；派生声束位置或图像不覆盖 P_n，共享 P_n 不代表束在工件中位置相同。旧“PA 逐事件独立采集位置”候选已被替代。

<a id="par-01"></a>
### PAR-01：固定采集定义的作用域与复用〔确定〕

Scan 共享设置只保存一次，事件专属设置每个事件保存一次，流专属设置每条流保存一次。固定参数指整个采集程序与定义不随帧变化；预定执行 L0、L1、L2 后在下一帧重复，不属于修改参数，也不要求程序只有一种法则。

本轮不需要逐帧 config_index、动态快照历史、生效区间或重复法则内容。所有必要固定引用须存在且可解释；真实采集设置、方案、流身份、长度、dtype 或采样解释变化应新建 Scan，是否另建文件按 SCAN-01 判断，不能更换定义或增加配置引用维持旧身份。固定性的作用域为 Scan，不要求同文件所有 Scan 共用一套定义。位置、波形与状态是可变化的观测结果，不因参数固定而移除。

固定定义遵循 META-01；本阶段只推进 Core 必要公共描述与引用，不要求设计完善的设备、探头或法则 schema，更多领域 schema 可由 Extensions 提供。D-09 保留必要内容承载和序列化缺口；不得依赖设备当前默认值或只保存本地驱动函数名代替必要说明，Core 也不据此承担物理法则校验。

<a id="par-02"></a>
### PAR-02：旧动态快照字节区〔已替代〕

`data + offsets` 动态快照字节区不是当前模型的必要对象或活动参考映射。保留编号用于项目内历史追踪，不表示 PASS；其职责已由 PAR-01 的固定定义复用取代。固定定义采用何种序列化仍待 D-09，不预设 JSON。

<a id="fmc-01"></a>
### FMC-01：固定 Tx/Rx 映射与覆盖〔确定〕

固定有序发射集合 I、接收集合 J 及映射 π 定义 `M_n[i,j] = X_π(i,j)[n,:]`；行是 Tx，列是 Rx。流目录顺序、物理排列或扁平编号不构成隐式映射。

声明为完整矩阵的采集域必须覆盖 I×J，每个有序收发对有明确且唯一的逻辑流对应；引用须存在，流的事件发射身份与接收输出须与对应 Tx/Rx 一致。不同有序对不得别名到同一测量身份。物理打包或共享存储对象不等于共享逻辑波形。

普通单阵列完整 FMC 样例中 I、J 为选定的同一阵元集合，包含全部有序对。覆盖声明须说明阵元范围，子孔径不冒充全探头。`Tx0→Rx2` 与 `Tx2→Rx0` 保持独立；不利用互易性合并、推算或复制另一半矩阵。

帧结构闭合与矩阵全部槽位有效分别判断：预定槽位及关联明确可结构闭合；声明域全部对的 `valid=1` 才能称矩阵数据全部有效。SDK 不另行判断业务合法性或记录独立的 payload 存在性。无有效数据的对采用 `valid=0` 和零填充，不作为真实零信号；固定映射缺口、未完成写入或解码失败不能转换成无效槽位。具体位图编码和读取容器仍待 D-08/D-10。

<a id="fmc-02"></a>
### FMC-02：矩阵访问与异构结果〔确定〕

访问层须在一个明确 Frame 内交付完整矩阵、固定 Tx 行、固定 Rx 列、有序 Tx×Rx 子矩阵、显式收发对清单及给定样本选择。可组合基础读取，不要求每项独立函数；不能只交付未解释的流集合，让调用者自行维护映射。Batch 可包含同一 Scan 的多个 Frame；其选择及内存布局按 READ-03/D-10 细化，不自动规定任意离散帧清单。

矩阵、流和单波形视图使用同一原始来源，不维护两份可分别修改的事实。一般矩阵单元为：

\[
M_n[i,j]\in\tau_{ij}^{S_{ij}}
\]

所选单元长度和 dtype 一致时必须可取得单 Frame 的逻辑轴序 `[Tx,Rx,Sample]` 稠密数值视图，同时返回对应有效性位图；Batch 保留各 Frame 身份以及矩阵/样本轴，物理排列及具体返回 shape 待 D-10。逻辑轴序不承诺连续内存或一次 I/O，显式转置须保留轴身份。无效单元按 STA-01 零填充，不跳过、不仅因无效而拒绝稠密交付，也不得将填充值当作原始测量或宣称矩阵数据全部有效。

共同物理时间轴还要求采样解释一致；仅 shape/dtype 一致时只能声明按样本序号堆叠，并保留各流解释。异构时返回有 Tx/Rx 身份的波形矩阵或分组结果，不隐式转换、填充或截断。同构主路径不降为只有逐流访问，矩阵读取也不强制全扫描驻内存。

TFM 消费收发波形及对应路径的传播时间；不同收发对可能取不同样本。按传播时间选样还依赖各流的采样起点、间隔及必要解释，不能仅由矩阵 shape 推出。逐对选样可以在已读输入块上执行，不要求逐像素磁盘读取。本轮不实现传播时间、TFM 或图像重建；Tx/Rx 轴不是工件网格，派生图像不替代原始矩阵。

## 5. HDF5 组织边界

<a id="map-01"></a>
### MAP-01：逻辑语义与物理组织分离〔确定边界，编码待定〕

本轮不规定 HDF5 路径、chunk、压缩、缓存或定义序列化。逻辑职责如下，不是已冻结字段表；`TBD` 不得作为实际文件的万能解释。

| 逻辑对象 | 逻辑形状/关系 | 编码边界 |
|---|---|---|
| 工件容器 / Scan 集合 | 工件身份、Scan 枚举；用途/区域/来源/坐标映射模型待定 | 容器语义 SCAN-01；Scan 映射关系 SCAN-02/D-11，协同 D-01/D-07/D-09 |
| 解释身份 | schema、Scan、采集语义、物理布局 | 必要语义确定，字面值/版本/路径 D-07 |
| 固定定义与元信息 | Scan/事件/流及其必要引用；公共描述＋带类型/版本的内容 | META-01；必要承载 D-09，编码 D-07；完整领域 schema 后置 |
| Frame 轴与位置 | 身份、Scan 内固定位置描述及每帧一份值 | POS-01/02；额外坐标以 dataset 按帧关联，细节 D-01/D-07 |
| 各流样本 | 每流 `[N,S_k]`、dtype τ_k；有效样本无损保存，无效槽位零填充 | 逻辑流不必一流一个 dataset；零填充不要求预先物理写满 |
| 有效性位图 | 每个 `(n,k)` 槽位一位，默认 0，与样本身份对应 | 单一有效性语义 STA-01；打包/位序/路径 D-07/D-08 |
| PA/FMC 映射 | 束→事件/输出；Tx/Rx→流 | 必须明确，不由目录顺序推断 |
| 前缀与生命周期 | 各 Scan 的 N、完成/故障/恢复范围；文件封存 | 确认协议 D-05，编码 D-07 |
| 可选辅助块 | 自解释扩展及其关联 | 不替代必要位置、固定定义或采集语义 |

HDF5 datatype、dataspace 与布局是不同属性，Frame 不要求一帧一个 group。初始化不要求知道最终 N；采用逐行组织的必要对象须覆盖 `[0,N)`，位置编码也须能验证该段逻辑关联。预分配使 E_x>N 本身不是错误，但不能仅凭 extent 判定封存。

物理设计需要区分以下机制；这些说明不分配生产路径或默认值：

| 机制 | 本项目中的解释与约束 |
|---|---|
| datatype | 描述存储元素的类型、位宽及字节序，不由 shape 决定；HDF5/绑定层可执行类型转换，不意味着 SDK 可跳过 WAV-02 的严格输入校验或改变原始样本 |
| dataspace / extent | 描述数据轴及物理尺寸；预分配或 resize 不等于 Frame 逻辑提交，完整前缀由 REC-02/WRT-02 验证 |
| chunk / filter | chunk 是物理分块和常见压缩处理单元，不是事件、波形流或事务身份；逻辑样本窗口可能触发整块解码，局部追加可能重写未填满的块 |
| HDF5 chunk cache / OS cache | 缓存层不同，命中会改变读取代价但不得改变逻辑结果；逻辑样本吞吐不等于磁盘物理带宽 |
| 属性与固定描述 | HDF5 对象属性和 dataset 数据可以承载编码，但对象路径及数组维度本身不提供采集含义；必要身份、单位和引用仍须明确 |

旧 SPLIT 路径和 CTS/TCS 只可作为适用工作负载的历史参考，不升格为所有模式的强制映射。样例可采用明确标记的 test-only 编码；物理设计选择不得改变语义和保真要求。

## 6. 写入和生命周期

本节定义写入、封存及恢复的逻辑边界；具体 flush/确认顺序、持久化与恢复协议仍属 D-05，不是本次已确定的实现方案，也不要求下一阶段全部测试一并实现。

<a id="wrt-01"></a>
### WRT-01：提交校验与阻塞行为〔确定〕

一个单写者通过同步单 Frame 或 Frame 批次接口向明确指定的活动 Scan 追加，提交单元不跨 Scan。每帧结构须闭合，可按 STA-01 标记无效槽位并零填充，不等待或补采。SDK 必须在修改 extent 或推进前缀之前完成提交单元的结构校验，包括 Scan 身份、有效性位图及其关联、有效波形的存在性/shape/dtype、容量和固定引用；无效槽位可不提供波形。校验失败不改变逻辑帧数量、相关 extent 或已提交数据。不得通过帧提交偷换固定定义。

写入慢时允许阻塞，不主动丢弃已交付数据或静默跳过记录，不提供写入取消。I/O 错误须按 IO-01 整批失败并报告原因/错误码，停止正常追加，不能当成输入校验失败后无条件重试。具体错误码、故障后状态及重试规则属 D-05/D-10。

输入缓冲由调用者维持，SDK 同步消费；调用返回后不再借用该缓冲，后续 Flush 不得依赖调用者仍保留原输入。普通写入成功不要求立即落盘，可使用 SDK/HDF5/OS 缓存；内部暂存和批次提交协议仍需设计，不从“同步”推定已取得原子性或持久化。设备缓存、停采及归组由调用方处理。

<a id="wrt-02"></a>
### WRT-02：完整前缀与不可变历史〔确定〕

在每个 Scan 的正常写入流程中，其 N 单调不减；新 Scan 从自己的 Frame 轴开始，不延长旧 Scan 的 N。推进批次提交边界前，相关波形、状态、原始位置和固定定义依赖须完成选定的写入/提交步骤；普通写入不强制逐批持久化。已提交 Frame 和其历史解释不得原地修订或晚到补写。

这是逻辑顺序，不是 HDF5 自带的跨 dataset 事务。后续追加可能改写包含旧数据的未填满压缩 chunk，故仅最后更新 N 不能证明批次失败已回滚或旧数据安全。IO-01 的原子失败目标需专门的提交/故障协议；调用返回、Flush、持久化和封存不能互相等同，机制及证据仍属 D-05。

<a id="wrt-03"></a>
### WRT-03：显式 Flush 与落盘〔目标确定，协议待定〕

除普通同步写入外，提供显式同步 `Flush`，供调用者要求将此前成功写入的数据及解释它们所必需的元数据强制落盘。普通 Writer 写入不要求立即落盘，成功返回不等于已持久化；Flush 不完成 Scan、不封存文件、不开放在线读取，也不修复失败批次。

Flush 的目标是持久化，不是仅清空 SDK 缓冲。实现须核对所用 HDF5 VFD、操作系统及文件系统的实际路径，并完成所需的库缓存刷新和 OS 持久化步骤；不能仅凭调用 `H5Fflush` 就宣称已实现强制落盘。Linux `fsync`、Windows `FlushFileBuffers` 是平台机制示例，不是已选定的实现。返回成功的精确持久化边界、失败后的 Writer 状态、关闭/封存是否自动执行同等 Flush，以及目录项/设备缓存的覆盖仍待 D-05。

持久化不等于批次事务；Flush 失败也不意味着此前写入已撤销。不得宣称不受设备和文件系统约束的绝对断电保证；机制与故障证据未闭合前不报告 Flush 已验证。

D-05 还须区分 Flush 是完成指定环境下的时点持久化屏障，还是建立受后续追加故障保护的确认范围；本次不选择其中一种。必须分别说明“Flush 成功后立即中断”和“成功后继续追加再中断”的保证与环境假设，不能用恢复报告如实描述损失来替代成功 Flush 的后条件，也不能以尚未选择后续保护语义为由放宽已定落盘目标。

<a id="io-01"></a>
### IO-01：批次 I/O 调用级强原子性〔确定边界，机制待定〕

批次读写是一个成功/失败单元。任一部分发生 I/O 错误时，要求整个批次原子性失败并返回原因/错误码，不交付可消费的部分成功批次，也不通过悄悄缩短数量报告成功。写入目标是失败批次不成为已提交数据；读取目标是失败批次不成为有效结果。不能只统一错误码而把部分结果视为完成。

首版采用调用级强原子性，覆盖运行中可返回的批次读写 I/O 错误：

- **push 读失败**：调用者目标数据缓冲逐字节保持调用前状态，不部分更新随批交付的位置、状态和元信息；错误通道另行返回原因/错误码，不发布有效的部分结果。
- **poll 读失败**：整批失败并报告原因/错误码，不发布本次有效视图或部分结果。先前借用视图已在本次读取开始时到期，不因读取失败恢复有效，也不承诺其 SDK 内部缓冲保持原内容；这是 BUF-01 的借用期限，不放宽 push 的目标缓冲不变保证。
- **写失败**：不新增已提交 Frame，提交范围及此前成功写入的数据和关联保持不变。允许文件中留下不可见的未提交空间或改变物理布局，不要求文件逐字节恢复原状。
- **范围**：不承诺进程崩溃或断电后批次仍全有或全无；这不是崩溃一致事务。普通未 Flush 的成功写入不自动获得持久化保证，Flush 的强制落盘目标继续独立按 WRT-03 实现，不因本条降级。

HDF5 不提供此处所需的通用跨对象事务；失败后再 resize 或只推进/撤销计数，不足以证明上述目标。push 读暂存、poll 全批成功后发布及写提交/保护机制仍需设计，本轮不选定日志、影子文件或缓存策略。遇到无法确认的文件状态须停止正常追加并如实报告，不能声称回滚成功或将不满足保证的实现判为合规。机制未验证前，不能把仅返回整批错误的实验计为 IO-01 通过。

故障模型及可观察边界仍须在 D-05/D-10 中闭合：底层错误类型与发生层次、延迟写回错误的归属、“此前成功数据不变”的核对方式，以及失败后 Reader/Writer 的可用操作。只检查 N 或热缓存不足以证明旧数据安全；协议需要提供独立核对依据。故障模型的补充不能静默缩减本条保证；若机制无法兑现，须按契约修订流程处理，而不是将未知状态列为合规。

原生调用与语言绑定之间的分配、封送、结果构造失败另属 D-05/D-10/D-12 的待定边界。例如原生写入已提交后绑定构造结果失败，或 push 复制完成后构造关联对象失败，不能未经决定就等同于本条的 I/O 失败。公共 API 尚须明确成功/失败单元是否包含整个绑定调用、错误是否意味着未提交及何时允许重试；本次不新增“部分提交也算原子失败”的例外。

<a id="lif-01"></a>
### LIF-01：正常封存与读取〔确定〕

文件生命周期包括初始化、顺序写入 Scan、正常封存及故障/未正常关闭。Scan 生命周期包括定义/初始化、追加、完成或故障；完成 Scan 后拒绝继续追加，但未封存文件可开始下一个 Scan。完成 Scan 不等于文件封存或持久化保证；普通读取仍等待整个文件封存。状态字节编码未定。

文件正常封存需核对 Scan 集合、每个 Scan 的完成状态/前缀及已确定的必要定义和 Scan 内关联，完成所选关闭流程；不得把未完成 Scan 静默跳过后宣布全文件正常。D-11 尚未决定的区域/来源/坐标映射不作为当前封存前提。初始化时 N=0 不代表 Scan 已完成；是否允许空 Scan 完成并纳入正常封存文件、是否允许无 Scan 的文件正常封存及相应 API 行为，留待 D-05/D-10。此处“完成”仅指存储记录闭合，不证明区域实际覆盖或整个工件检测完成。

普通读取面向已封存文件，常规追加入口必须拒绝修改已封存文件。实时显示走采集内存，不要求读取增长中的文件或实施 SWMR。正常文件若不能满足必要结构和引用约束，应明确报错，不得自动当成有效的较短扫描。

<a id="lif-02"></a>
### LIF-02：尽力只读恢复〔确定〕

未正常关闭的文件通过显式恢复模式处理，不伪装成正常封存：

1. 只读尝试打开，失败时报告，禁止为打开而自动修复原文件。
2. 检查可读取的前缀、物理范围和必要关联；不把填充值或可解码字节自动认作完整 Frame。
3. 如果可建立可信完整前缀，则暴露验证范围 N_r；只有声明的 N 本身可验证时，才可以将其作为上界依据。前缀标记缺失/不可信时，不凭各 extent 最小值猜测恢复数量。
4. 报告声明范围、验证范围、失败对象及未执行检查；结构可读与逐样本完整性验证须区分。
5. 不原地续写、修复或截断源文件。超出可信前缀的抢救、前缀标记损坏后的重建策略留待 D-05。

上述 N/N_r 与范围验证逐 Scan 执行，并报告 Scan 集合及已确定的必要结构检查结果。某 Scan 失败不允许静默缩短或合并其他 Scan；能够独立验证的 Scan 可显式报告为恢复子集，但不代表整个文件正常。D-11 的映射关系验证等待模型决定，不因尚无关系定义而伪造关联或报告产品规则失败。HDF5 group 不构成事务或故障隔离边界，文件级元数据损坏仍可能使多个乃至全部 Scan 无法访问。

HDF5 元数据损坏时可能无法打开。恢复目标是尽力，不预设最大损失时长；未 Flush 的普通成功写入不自动获得持久化保证。WRT-03 的显式 Flush 成功范围须由持久化协议和证据确定，不能用“尽力恢复”免除其强制落盘目标，也不能仅凭未知 flush 标记猜测数据存在。不得将不完整尾部或损坏记录改成 `valid=0` 并零填充来掩盖故障。

## 7. 读取语义与规模

<a id="read-01"></a>
### READ-01：独立和绑定访问〔确定〕

SDK 提供波形、位置、元信息的独立及关联访问，具体函数签名不属于本文。每次数据请求指定一个 Scan 和单 Frame 或 Batch 的 Frame 索引选择；优先满足 Frame/Batch 读取，其次支持 A-Scan 读取，不新增逐流追加写入。波形返回对应状态，独立波形读取不强制解码位置，但须满足 ID-02。两种交付方式见 READ-03，均保留 Frame、流及事件/输出来源。

访问层还须能枚举/选择 Scan 并识别所属工件；用途、目标区域、Scan 间来源及坐标映射的读取能力等待 D-11。不能默认第一个或“最新”Scan；Batch 在同一 Scan 内选择 Frame，不隐式拼接不同 Scan 的轴、统一 dtype 或筛选替代结果。即使各 Scan 的 n/k 和位置相同，也须保留独立数据来源，不据此推导空间映射或按位置查询。

绑定访问按 POS-01 保持关联，保留无效波形槽位及其有效性位并按 STA-01 零填充，不重新按时间匹配、不以 overlay 替换历史位置。一个请求无法满足时必须显式报告，不以空数组或零位置伪装成功。

读取不提供文件 update；同一不变文件的等价成功读取须返回相同数值、有效性位、位置和元信息关联，不因前一选择、缓存、poll/push 或交付用途改变。poll 视图只读且有借用期限；push 的调用者缓冲可以复用，其内存变化不更新文件。多次读取一致不表示旧 poll 指针永久有效或 push 目标永不覆盖。失败行为见 IO-01；位图接口/布局、Batch 布局和错误码仍待 D-08/D-10，不设计并发 Reader。

<a id="read-02"></a>
### READ-02：选择结果语义〔确定语义，API 编码待定〕

下列语义用于访问规划和 UC 验证；不冻结函数签名、返回类型、异常名称或负索引等 API 扩展语法（D-10）：

- Frame 可单独指定或由 Batch 选择多个，Batch 起点/数量或离散索引语法尚未冻结；不得因此自动声称支持任意清单。同一 Frame 内有序 Stream、PA 声束、Tx/Rx、配对和 Sample 清单保序保重复，例如 `[2,0,2]`。批次输出须保持所声明的 Frame 顺序及全部关联；若后续开放有序 Frame 清单，同样不得静默排序或去重。
- Tx 清单与 Rx 清单的交叉选择为笛卡尔子矩阵；显式收发对清单只返回列出的对，不展开成子矩阵。
- 样本边界按每个选中流自己的 S_k 检查，不以最长流的边界替代其他流，不静默截断、补齐或溢出。
- Sample 清单 `[3,1,3]` 表示按顺序交付原始样本 `s=3、1、3`，不能排序或去重后改变结果；逐流/逐对给定样本清单时，同一要求分别适用。此类显式有序清单不等于已经确定负步长切片等逆序 API 语法。
- 选择结果保留 Frame、流/轴身份、状态、固定定义关联；绑定结果还保留原始位置来源。
- 逐对样本选择表或窗口可以作用于已读数据块；不承诺每项选择单独触发磁盘 I/O。

本项目用半开区间 `[a,b)` 和可含重复项的有序清单表达预期，不冻结 API 语法、返回对象形态或异常类名。少量空选择、单元素、首尾、越界变体属于后续用例素材；具体空结果表示、负索引或逆序语法留待 D-10，不可用空结果伪装越界成功。

请求异构流集合时，必须明确报告越界流及相关范围，不静默截断、补齐或伪装整个请求成功。采用整个请求拒绝，还是显式逐项结果/错误的形式，本轮不决定，留待 D-10。不支持的选择须明确报告，不能算能力通过，也不能削弱 FMC-02 的目标能力。

批次 I/O 失败遵守 IO-01，不得用逐项错误容器交付部分成功；上述输入选择校验的具体报告形式不放宽 I/O 原子失败要求。`valid=0` 是正常数据状态，读取时按 STA-01 交付零填充和对应位图，不等同于 I/O 错误；I/O 错误也不能转换成无效槽位。

<a id="read-03"></a>
### READ-03：分析读取与 Batch 内存视图〔方式确定，布局待定〕

提供两种关联内容交付方式，共用同一文件来源，不维护两份可独立修改的数据。它们描述内容/用途，与 BUF-01 的 poll/push 内存所有权是两个维度，不把分析读取限定为 push，也不把 Batch 限定为 poll：

1. **常规分析**：返回数据及关联元信息、位置/状态，保持 Frame/流/事件身份；固定描述可以共享，不要求逐波形复制。具体容器及元信息选择形式待 D-10。
2. **Batch 消费**：一次同步读取同一 Scan 的多个 Frame，通过 poll 借用 SDK 只读内存视图，或通过 push 复制到调用者缓冲供上传 GPU。批次数用 `B` 表示，以免与 Scan 的总前缀 `N` 混淆。结果须附可核对的范围、类型、形状/偏移及身份关联说明，不能只返回无法解释的裸地址。

Batch 的选择形式、同构连续排列、异构多缓冲/偏移描述以及是否携带完整元信息仍待 D-10；有效波形不隐式转换、填充或截断来拼成一个数组。无效槽位零填充，随样本交付有效性位图，不跳过槽位；位图与数据缓冲的具体布局仍待 D-08/D-10。主机指针不代表 GPU 设备指针、固定页内存、GPU 解压或零拷贝；SDK 本轮不负责 GPU 上传与异步传输调度。

<a id="buf-01"></a>
### BUF-01：poll/push 缓冲与同步生命周期〔确定所有权，表示待定〕

本文沿用 poll/push 名称：poll 指消费者经 SDK 同步拉取并借用结果，不是轮询任务状态；push 指 SDK 在同步调用中向指定目标复制，不是后台主动推送。两种读取模型都支持，写入仍由调用者提供输入缓冲、SDK 同步消费。

| 模型 | 内存所有者与操作 | 有效期 |
|---|---|---|
| poll | SDK 读取/必要时解码到自己管理的主机内存，成功后返回只读借用指针/视图；调用者不得释放或修改它 | 至同一 Reader 的下一次数据读取开始，或对应文件/Reader 关闭，以先发生者为准 |
| push | 调用者提供可写目标指针及容量，SDK 同步读取并复制数据；SDK 不接管目标分配/释放 | 由调用者管理；关闭 Reader 或对其他缓冲读取不会使其失效，复用该目标会覆盖内容 |

“磁盘上的内存指针”不是此处的物理实现：可解引用指针必须指向进程可访问的内存。poll 不承诺把 HDF5 文件偏移直接当作指针，也不承诺 mmap、固定地址、免解压或零拷贝。实现可以复用或重新分配 SDK 缓冲；旧视图到期不等于必须立即覆写，但调用者不得再使用它。

同一 Reader 的下一次 poll 或 push 数据读取均结束先前 poll 借用期，包括该次读取失败的情况；不承诺失败后旧视图恢复有效。push 的调用者目标在 I/O 失败时仍须按 IO-01 保持不变。依附 poll 结果内存的关联位置/元信息视图遵循同一借用期，不能只保存裸指针后在下一次读取继续使用；独立复制的内容不受此借用期影响。

GPU 上传若异步执行，poll 调用者须在上传完成前禁止同一 Reader 下次数据读取或关闭；push 调用者须在上传完成前保持目标缓冲有效且不复用/修改。SDK 的同步返回不等于外部 GPU 操作已完成。语言绑定须表达借用期/所有者；仅保留 Reader 对象引用不能延长已被下一次读取或显式关闭终止的 poll 视图，push 则须避免调用中 Python/.NET 缓冲移动或释放。具体绑定见 D-12，不默认自动复制延长 poll 寿命。

裸缓冲导出、派生视图及受检包装的选择仍待 D-10/D-12；Python/.NET 对象仍存活不证明底层借用有效。后续须分别验证派生视图、失败读取、显式关闭、GC/终结器和异常路径释放；不能以永久保留全部旧分配来绕过借用期或有界资源要求。本条不承诺自动撤销已经导出的裸地址。

SDK 不在同步返回后继续借用调用者的 push 目标或写入输入。缓冲长度/布局/对齐、元信息容器及容量报告形式待 D-02/D-10；须检查运算和容量，不允许越界。poll 缓冲及 push 原子暂存都须有界；内部暂存不改变对外所有权，也不构成全链路零拷贝承诺。

<a id="cap-01"></a>
### CAP-01：超 RAM 访问〔确定〕

目标是超过 100 GB 的单文件，每个 Scan 的 N 仍在 u64 范围内，不要求其总和可表示为一个全局 N。写入缓冲和读取缓存必须有界，不随各 Scan 的总 Frame 数线性增长；波形、位置、状态、相关定义及 Scan 目录访问均须有界，不能要求打开时全量物化所有 Scan 的定义。正常打开不要求扫描全部波形，深度检查单独执行。

读写组织优先 Frame/Batch、其次 A-Scan 读取；代表性负载包含连续批量写入、Frame 随机读、GPU 上传前的 Batch 读及 A-Scan 随机读。单 Frame 不提供帧内分块交付；支持的 Frame/Batch 大小和容量要求须明确，超出上限须明确失败，不能偷偷改为部分结果或分块接口。调用者可控制 Batch 大小，不要求全扫描或整个通道驻内存。原子失败所需暂存也须计入内存预算。本阶段不做布局/压缩/cache 调优；小文件测试不证明规模目标。

D-02/D-03 的资源口径须区分调用者输入/目标、SDK 结果及原子暂存、HDF5 缓存/解码工作区、位图/位置/元信息和绑定副本，明确请求上限、峰值口径及超限检查时机。调小 Batch 不能解决单 Frame 超限；实际 Frame 规模和上游交付证据应先约束支持范围，不能只用小型 H/P/F/W 推断设备适配性。具体预算值尚未确定。

## 8. 压缩与解码

<a id="cmp-01"></a>
### CMP-01：无损与依赖可识别〔确定〕

压缩用于降低磁盘流量与长期容量，必须满足 WAV-02。文件的有效 filter 编码链和必要参数必须可识别，读取端可以部署第三方 filter；缺少解码器或不支持参数时明确报告，不能回退为错误数值。

不固定 codec、级别、chunk、线程或缓存参数（D-04）。“具有 filter ID”不表示所有 HDF5 安装均自带解码器。生产带宽规划不得以当前合成数据压缩率作为不可压缩输入仍不丢数据的证明。

<a id="cmp-02"></a>
### CMP-02：GPU 可选能力的声明〔确定〕

CPU 可读路径是基础，GPU 解压是待验证的可选能力（D-06）。声称 GPU 解压时，必须验证从实际存储的压缩表示到样本的完整链路，包括封装、压缩块、预处理逆变换、尾块及存在的校验。

主机先解压再 H2D 不属于 GPU 解压。缺少 GPU 不影响基础 CPU 读取符合性；GPU 厂商、库、输出顺序和性能阈值不在本版指定。

压缩字节在主机到设备间传输后再由 GPU 解码，与主机先解码再传输原始样本，是两条不同的消费路径。后续比较须包含实际传输字节、解码、预处理逆变换、必要布局转换及下游消费代价，不能仅凭传输量减少或单独解码计时宣称端到端更快。具体测量规划见 SPEC_TEST_PLAN 的性能与 GPU 专项；本轮没有运行验证。

## 9. 符合性检查与错误解释

<a id="val-01"></a>
### VAL-01：分层、可追溯的验证报告〔确定〕

检查必须区分文件错误、不支持的能力、调用者标记的无效槽位以及尚未验证；不增加独立的业务合法性检查：

|---|---|---|
| 识别 | schema/profile/layout、必要能力、解码依赖 | 不证明数据完整 |
| 结构 | 各流类型/shape、固定定义、状态与声明长度 | 不证明全部字节已正确落盘 |
| 关联 | Frame 前缀、原始位置、事件/接收输出引用、PA/FMC 映射 | 不证明物理位置准确或成像正确 |
| 深度 | 分批解码、内容比对/已定义的完整性校验 | 不自动证明抗断电、性能或设备不丢数据 |

测试记录至少包括 Spec 修订、采用的参考映射/临时编码、输入样例、规则编号、检查层次、执行结果和未覆盖项。结果可以表达 PASS、FAIL、NOT_RUN、BLOCKED、UNSUPPORTED 等含义，但正式错误码与报告序列化格式未定。

待定编码造成的 BLOCKED、选择未实现的 UNSUPPORTED、未执行的 NOT_RUN 都不得计为完整符合性通过。未知可选块被跳过，也不等于该块已经被验证。

当前仅定义规则与测试计划，没有发布符合性检查器或样例文件。完整规范的冻结需要解决必要编码项并取得独立读取证据，见 [SPEC_TEST_PLAN.md](SPEC_TEST_PLAN.md)。

## 11. 契约修订流程

按“候选规则 → 正反样例 → 独立检查 → 修订规则”迭代。每次规则升级说明需求依据、影响的数据解释、旧实验样例是否仍适用及验证证据。改变记录含义不能伪装成纯性能优化。

文档职责：需求理由在 DESIGN.md；规则与必要机制解释在本文；访问覆盖在 ACCESS_USE_CASE_PLAN.md；样例、覆盖和执行证据在 SPEC_TEST_PLAN.md/实验报告。不要在其他文档或测试代码中维护第二套隐含规范。采用 HDF5 或借鉴通用采集概念不构成与其他文件格式、SDK 或算法实现兼容的声明。
