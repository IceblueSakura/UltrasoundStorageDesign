## 1. 如何选择与使用

不必一次回答所有问题，可以按下表选择一组，或限定到一种设备、采集模式和算法。单一有效性与零填充、三模式公共模型、多 Scan 独立性、poll/push 所有权、同步串行和单 Frame 不分块等已定边界不重开。未掌握的信息保留为“尚不清楚”；实际不存在的场景标为“不适用”，不据此扩展格式。

需要区分三类内容：

| 类型 | 要解决的问题 | 可用依据 |
|---|---|---|
| 事实补充 | 设备或业务实际如何工作？ | 设备说明、接口/调用示例、实际采集方案、算法输入说明 |
| 工程选择 | 在已知约束下，产品或 SDK 采用什么行为？ | 候选方案、适用范围、取舍理由及正反例 |
| 实验取证 | 某项保证在目标环境中是否成立？ | 可复核的正确性、持续负载、资源和故障实验结果 |

事实不能由实验默认值代替；工程选择不能代替设备能力；完成文档不能代替运行证据。本文列出的行为选项只是讨论提示，不表示已经采纳。

## 2. 设备与采集语义

<a id="angle-01"></a>
### 角度 1：Scan 起止与暂停

在已采纳多 Scan 方向下，需要补充：

- 哪些实际动作表示 Scan 开始、完成或中断，何时封存整个工件文件？
- 运动暂停、设备暂停、短暂停顿与结束后重启如何区分？
- 是否需要显式表示目标区域或来源 Scan？如果需要，它们的业务含义、模型及必要性是什么，而不是先指定关系方向、基数或无环约束？
- 是否需要共同工件参考系或 Scan 坐标映射？若需要，关系由谁提供，作用域及不可用情况怎样讨论？

适合提供的材料：一个工件的分块及局部复扫/精扫流程，说明 Scan 边界和实际空间/来源关系需求；未知项留空，不要求先构造区域或变换。

当前约束见 [R-01/R-12](DESIGN.md#r-01)及 [SCAN-01](DATA_SPEC.md#scan-01)，问题入口为 A-01、[SCAN-02/D-11](DATA_SPEC.md#scan-02)。不再把“是否允许多 Scan”列为待决策，但每个 Scan 的映射关系仍待决策；自动拼接、结果替代及已封存文件重开追加仍不在当前范围。

**候选与建议（未采纳）**：

- Scan 映射：首发只声明独立 Scan 容器，或先定义必要区域/来源/坐标关系再声明映射能力。推荐前者以避免 D-11 阻塞 Core；代价是消费者不能依靠 SDK 自动解释这些关系。若业务确需后者，先提供实际分块/复扫流程，不预设引用图或变换。
- 空 Scan/无 Scan 文件：允许作为合法空结果，或拒绝正常完成/封存。推荐只有明确消费场景时才纳入合法空结果；当前尚无足够事实选择，不能先写允许/拒绝断言。
- 不论空对象选择如何，都需补一张 File/Scan/Reader/Writer 的“状态 × 操作 → 结果/下一状态”表，覆盖完成、封存、关闭、故障及重复调用。Scan 完成不等于工件检测完成。

### 角度 4：位置描述与额外坐标关联

已确定采用必要公共描述＋带类型/版本内容，Scan 内描述固定、每帧保存一份值，PA 全部声束共用位置。需要补充：

- 最小公共描述、值编码及无效位置表示是什么？不要求本轮完善领域 schema。
- 实际反馈/理论坐标等额外 dataset 如何引用同一 Frame，怎样辨识描述与来源？
- 额外坐标缺值怎样表达，是否参与提交/封存检查？
- 绑定读取选择哪些位置内容，返回值还是可核对引用？结果生命周期怎样定义？

适合提供的材料：位置数据示例、参考对象说明，以及正常/异常位置下的操作预期。

关联 D-01/D-09、A-02/A-04。原始绑定与位置描述见 [POS-01](DATA_SPEC.md#pos-01)、[POS-02](DATA_SPEC.md#pos-02)；位置值不代替 Frame 身份，零坐标不代替缺失决定。更细运动模型若超出现有范围，单独记录冲突。

**需要明确的行为选择（均未采纳）**：

| 问题 | 候选与影响 | 推荐方向及条件 |
|---|---|---|
| 波形有效、原始位置获取失败 | 整个提交单元拒绝：合同简单，但无法通过该次提交保存波形；明确位置无效状态仍保存：保留波形，但消费者必须处理不能定位的数据 | 若实际采集会出现短时定位失败，推荐显式位置状态；否则可选择严格拒绝。先补实际失败场景，不以波形无效位或零坐标替代 |
| 附加坐标是否必需 | 全部必需会扩大提交依赖；逐份声明必要性可容纳缺值，但需要固定的缺失与校验规则 | 推荐由 Scan 定义固定必要性，原始位置与附加内容分开解释 |
| 附加坐标晚到 | 同一提交单元提供或显式缺失，符合不可变历史；允许后补则需另定义时序及一致性，并审查既有禁止晚到补写边界 | 推荐首版不引入后补，真实业务冲突先回到 DESIGN 决策 |

产出应同时说明接受/拒绝条件、位置与波形状态组合、附加内容缺值和封存关系，然后再选择编码。仅提供正常位置字段表不能关闭本组问题。

## 3. SDK 行为与消费接口

<a id="angle-06"></a>
### 角度 6：批次原子失败与写入确认

失败语义见 [IO-01](DATA_SPEC.md#io-01)：push 失败目标不变；poll 不发布部分新结果，旧借用也不因读取失败延寿；写失败不新增提交且此前成功数据不变。不要求物理布局复原或崩溃事务，后续需设计和取证：

- push 怎样暂存后全批复制、保持失败目标不变？poll 怎样在下次读取开始时终止旧借用期，并仅在全批成功后发布新视图？两者预算如何限制？
- 怎样提交写批次、保护此前成功数据，尤其是与新数据共享的压缩 chunk 和 HDF5 元数据？
- 未提交空间如何处理，何时允许安全重试？Flush/封存协议如何与逻辑提交分开？
- 出错后的 Reader/Writer 状态、失败清理再次失败、原因/错误码如何表达？不能将未知状态称为回滚成功。
- “旧数据不变”由哪些独立观察证明？延迟写回旧批次失败时，错误如何归属？仅检查 N 或热缓存不够。
- 分配、封送或结果构造失败是否处于公共调用的成功/失败单元内？原生已提交、绑定却抛错时怎样报告，调用者是否可以重试？

适合提供的材料：一次 Batch 的调用前后可观察状态及故障预期。实现不得只统一错误返回码就称为原子性；暂不选定日志、影子文件或暂存策略。设备停采/缓存仍是上游责任。

关联 D-02/D-05/D-10、A-06；提交与前缀规则见 [WRT-01](DATA_SPEC.md#wrt-01)、[WRT-02](DATA_SPEC.md#wrt-02)。接口选择不能放宽完整 Frame 提交、前置校验或故障后停止正常追加的边界。

**候选与建议（未采纳）**：

| 决策 | 候选与代价 | 推荐方向 |
|---|---|---|
| 故障覆盖与观察边界 | 未列清底层故障会使保证无法验收；逐项明确错误层次、旧数据观察及环境假设，才能比较机制 | 先形成故障/结果矩阵，再评估机制；覆盖错误不能由实现失败后随意删除 |
| 旧数据保护 | 隔离新旧写入并控制发布，或采用日志/影子等保护策略；各有空间、I/O、元数据和恢复复杂度 | 不先选具体架构；用小规模真实 HDF5 取证淘汰不满足 IO-01 的候选，不能只回退 N |
| 绑定层失败 | 将可失败准备工作放在提交/目标复制前，或设计能区分已提交/未提交/未知的错误结果合同 | 优先减少提交后的可失败工作；仍存在的失败必须可区分，不得包装成可盲重试的“未提交”。这不新增 IO-01 的部分成功例外 |

讨论输入至少包含两条序列：① A 成功未 Flush，追加 B 时旧 chunk/共享元数据写回失败；② native 写入成功，绑定结果构造失败。先决定可观察预期，再提出机制；取证方法落入 T-14，不能仅选择一种错误码便关闭 D-05。

<a id="angle-07"></a>
### 角度 7：有效性位图接口与错误结果

单一有效性位图与无效零填充已按 [STA-01](DATA_SPEC.md#sta-01) 确定，不再独立区分缺数据与“有值但业务无效”。剩余需要讨论：

- 位图输入/输出如何表达、打包并与 Frame/流/PA/FMC 身份对应，怎样检查长度、位序和容量？
- 无效槽位可不提供波形；具体接口怎样表达省略，仍需校验哪些请求结构和缓冲边界？
- 异构请求一项越界时，是请求级拒绝还是逐项结果/错误？
- 空选择、不支持能力、位置无效与结构/解码错误如何分别表达？
- 算法怎样消费样本＋有效性位图，避免把无效零填充当作真实零回波？不重新引入 SDK 业务合法性判断或无效原因分类。

适合提供的材料：几组输入/请求及预期结果说明，先说明含义，不必先选异常类或错误码。

关联 D-01/D-08/D-10、A-11；状态与选择语义见 [STA-01](DATA_SPEC.md#sta-01)、[READ-02](DATA_SPEC.md#read-02)。稠密读取随样本返回位图，无效槽位零填充且不跳过；不再讨论是否拒绝无效矩阵或保存无效输入波形。零填充不是补采，不引入等待或晚到补写。

**候选与建议（未采纳）**：

- 输入选择有一项越界：请求整体拒绝，或返回明确逐项校验结果。推荐首版整体拒绝，简化调用与原子目标的组合；代价是调用者需要拆分请求。无论选择哪种，批次 I/O 错误仍按 IO-01 整批失败。
- API 位图：直接暴露打包位图，或在绑定提供更易用的布尔表示并明确转换。前者便于容量与 GPU 消费，后者增加副本与转换；推荐先统一槽位顺序、位序/尾部位及容量规则，再决定每个绑定是否增加显式适配，不要求磁盘与 API 编码相同。
- 需要分别给出空选择、容量不足、不支持能力、结构/解码错误的结果，以及错误后能否继续使用 Reader/Writer；不要只列错误枚举而省略状态和目标缓冲语义。

<a id="angle-08"></a>
### 角度 8：分析/Batch 交付与布局

分析结果随元信息返回，Batch 一次读取多个 Frame；poll 借用 SDK 只读视图，push 复制到指定调用者缓冲，两种所有权不与内容用途绑定。Frame 优先、A-Scan 次之，单 Frame 不分块，无 update，重复等价读取值一致。还需细化：

- Batch 使用起点/数量还是也支持离散索引，范围越界怎样报告？
- 同构内存排列、异构多缓冲/偏移怎样描述，Frame/流及样本身份怎样核对？
- 分析模式元信息与额外坐标如何组织；Batch 除必要布局/身份说明外是否带完整元信息？
- 容量如何查询或声明，超出 Frame/Batch 上限怎样失败？不能退化为截断或帧内分块。
- 样本和有效性位图怎样排列、报告容量并共同交付，特别是 Batch GPU 消费路径？无效槽位按 STA-01 零填充，不能丢位图、隐式跳过或为拼接改变有效样本 dtype。

poll 旧视图在同一 Reader 下次数据读取（含 push 或失败）或关闭时失效，不能释放或继续解引用；push 缓冲由调用者管理，关闭 Reader 不释放它。GPU 异步上传完成前，poll 不能再读/关闭，push 不能复用/释放目标。主机指针不是磁盘地址或零拷贝承诺。记录入口见 [场景审计第 4 节](SCENARIO_AUDIT.md#4-算法输入与读取方式核查)。

关联 D-03/D-10、A-08/A-10/A-12；访问能力见 [访问规划](ACCESS_USE_CASE_PLAN.md)。不默认所有读取都零拷贝或连续，也不因实现方便改变保序保重复及逐流边界语义。

**候选与建议（未采纳）**：

| 问题 | 候选与影响 | 推荐方向 |
|---|---|---|
| Batch Frame 选择 | 连续起点/数量简单且便于容量估算；离散清单更灵活，但增加保序重复、聚合和错误检查 | 首版先连续 Batch，除非实际请求证明离散清单必需；不影响已定帧内有序选择 |
| 异构交付 | 逐流多缓冲直观；打包缓冲＋偏移便于集中管理，但对齐和容量校验更复杂 | 先采用能保留身份/原始类型的最小描述方案，通过消费示例比较，不预定连续单数组 |
| push 容量准备 | 提供需求查询，或要求调用者从描述计算；后者减少 API，但易重复布局逻辑 | 推荐可核对的容量/布局查询，明确查询是否终止 poll 借用，不能把这点留给绑定猜测 |

最小产出是一组读写调用示例及结果描述：单 Frame、Batch、异构、位图、关联元信息、容量不足和空选择。分析/Batch × poll/push 是两个维度，不能只实现两个对角组合便宣称覆盖。

## 4. 正式格式与运行证据

<a id="angle-09"></a>
### 角度 9：正式格式与独立读取

需要讨论：

- 首个正式 profile 支持哪些模式、样本表示、位置描述和固定定义？如何限定支持范围？
- format/schema/profile/layout、版本与必要能力如何精确编码和解释？
- 状态、生命周期、计数、引用、字符串和字节序如何映射到 HDF5？
- 未知必要语义或 filter 参数如何拒绝？部署方案暂不设计。
- 独立读取器还需要哪些未写入正式说明的约定？

适合提供的材料：拟支持范围及必要编码方案，配套正反样例和独立读取证据规划。

关联 D-01/D-07/D-09、T-22；身份及组织边界见 [ID-01](DATA_SPEC.md#id-01)、[ID-02](DATA_SPEC.md#id-02)、[MAP-01](DATA_SPEC.md#map-01)。精确解释映射与性能默认值不是同一件事；可以先闭合一个范围明确的 profile。

**候选与建议（未采纳）**：一个有限、完整可解释的首发 profile，或同时冻结多种编码/布局与能力组合。推荐前者，代价是首发支持面受限，但不能删除已定三模式、异构与多 Scan 能力；范围冲突须显式修订需求。冻结清单须覆盖样本/位置/元信息表示、身份/引用、位图/计数/生命周期、版本/能力及实际布局/filter。精确映射先受角度 6＋11 的机制约束，再由独立读取核对，不把 chunk/codec 最优参数作为先决条件。

<a id="angle-10"></a>
### 角度 10：Frame/Batch 优先负载与后续取证

负载覆盖连续批量写、Frame 随机读、GPU 上传前的 Batch 读及次级 A-Scan 随机读。Frame/Batch 优先，本阶段只做设计、不调优，后续补充：

- 持续/突发输入速率、典型扫描规模和实际请求序列是什么？
- 延迟、阻塞、内存预算和输出连续性要求是什么？哪些是期望目标，哪些是已有测量？
- 目标机器、CPU、磁盘及解码依赖环境是什么？
- 能否取得可用于实验的真实波形和不可压缩压力输入？
- 在固定语义及负载下，如何比较布局、chunk、codec、cache、批量和预分配？

适合提供的材料：一份目标环境与工作负载说明；初期可先补事实和目标，不立即确定调优参数。

关联 D-02/D-03/D-04、A-12；测量方法见 [验证计划第 6 节](SPEC_TEST_PLAN.md#6-性能与-gpu-专项)。历史微基准的限制见 [BENCHMARK_REPORT.md](BENCHMARK_REPORT.md)，不能替代真实负载或超 RAM 证据。

**需要输入的目标**：典型/最大流数与 S_k、最大 Frame 字节量、Batch 范围、持续/突发输入及持续时间、Frame/Batch/A-Scan 请求比例、吞吐/延迟/阻塞门槛、内存上限和目标机器。数值未知就明确缺口，不在本文件填猜测默认值。

**候选与建议（未采纳）**：固定一组目标环境与验收负载，或为多档环境分别声明配置和门槛。推荐先固定一组可复核环境，不宣称结果普遍成立。峰值口径应覆盖调用者目标、SDK 结果/原子暂存、HDF5 解码/cache、位图/关联和绑定副本；B=1 仍要能容纳单 Frame。更多调优可后置，但已声明的超 RAM、有界资源及负载目标不能以“以后再优化”免验。

<a id="angle-11"></a>
### 角度 11：封存、持久化与恢复

需要讨论并取证：

- Scan 完成与文件封存分别怎样检查？是否允许空 Scan 完成或无 Scan 文件封存，接口如何表达？
- 普通写入不立即落盘、显式 Flush 强制落盘已定；何时算完成 OS 持久化步骤，如何覆盖必要元数据，失败怎样报告？
- 关闭/封存是否自动执行等价 Flush，调用前哪些成功批次在其保证范围内？
- Flush 成功只表示当时完成持久化屏障，还是建立受后续追加故障保护的确认范围？两者需分别说明环境假设，不等同于崩溃批次事务。
- Scan 目录及各 Scan 的完整前缀由什么建立可信依据？声明值、extent 或标记不可信时怎样报告？
- 磁盘满、I/O 失败、进程中断和断电分别怎样影响已接受数据？
- 部分压缩 chunk 更新中断是否影响旧帧？哪些损坏可检测，哪些只能报告尚未验证？
- 恢复报告怎样区分结构可读、可解码、内容已核对及未执行检查？

适合提供的材料：异常结束时的用户预期、候选确认/封存协议，以及受控故障实验计划。

关联 D-05/D-07/D-10、T-12/T-15；边界见 [LIF-01](DATA_SPEC.md#lif-01)、[LIF-02](DATA_SPEC.md#lif-02)。恢复仍是显式尽力只读，不预设零损失、固定时间窗或自动修复；讨论实验不等于授权破坏性故障操作。

**候选与建议（未采纳）**：

| 问题 | 候选与影响 | 推荐方向 |
|---|---|---|
| Flush 的成功保证 | 时点屏障较容易界定，但不能自动承诺后续原地更新不损伤旧数据；受保护确认范围更利于恢复依赖，但可能增加布局/协议成本 | 先由消费方明确是否依赖“后续故障仍保住已 Flush 数据”；再比较机制，不在缺少业务答案时默认选择较弱保证 |
| 正常封存/关闭 | 正常封存包含等价 Flush，使封存成功有明确落盘边界；或要求调用者显式 Flush，接口需清楚区分逻辑封存与持久化 | 推荐正常封存包含等价 Flush；普通关闭、异常释放是否封存/刷新另行定义，不让析构或终结器隐式宣布成功 |

讨论应为“Flush 成功后立即中断”“成功后继续追加再中断”“持久化步骤失败”逐项给出预期及未覆盖条件，并区分进程中断和断电。验收材料落入 T-14/T-15 的 Flush 子范围；如实报告恢复失败本身不证明 Flush 已履约。

<a id="angle-12"></a>
### 角度 12：可选 GPU 解压

需要补充并取证：

- 目标 GPU、库、实际 filter 链及下游计算输入是什么？
- 压缩封装、逆变换、尾块及校验是否全部能够正确处理？
- 与 CPU 解码对照时，原始样本及轴身份是否一致？
- 包含传输、解码、布局转换和下游消费后，端到端收益是什么？

适合提供的材料：目标 GPU 消费路径及实际编码链，而不只是一个 GPU 解码函数计时。

关联 D-06、T-20；声明边界见 [CMP-02](DATA_SPEC.md#cmp-02)。该方向可独立暂缓，不阻塞基础 CPU 读取。

**候选与建议（未采纳）**：首发不声明 GPU 解压、保留 CPU 解码与 Batch 主机交付，或把明确 GPU/filter 链加入首发可选支持。推荐前者，避免可选加速拖延 Core；代价是初版不能宣传 GPU 解压收益。后续声明须独立完成 M4，不改变已定的 Batch 内容与位图交付目标。

<a id="angle-13"></a>
### 角度 13：平台与语言绑定

目标为最新 Linux LTS、Windows 10+，优先 Python 和 .NET Framework 4.8，倾向 C/C++/pybind11。pybind11 不自动解决 .NET 绑定；具体语言/版本/ABI 仍待选择。绑定须区分 poll 借用失效与 push 所有者保活；保留 Reader 对象不等于跨下一次读取/显式关闭延长旧视图，不能默认偷偷复制或后台借用。这里不扩为部署/打包方案。

.NET Framework 4.8 消费端面向 Windows，不能把这一目标解释成 Linux 上运行该框架。原生库、Python 和 Windows .NET Framework 4.8 的支持应分别取得证据；精确矩阵见 D-12，当前没有实现或验证声明。

**候选与建议（未采纳）**：

- 原生边界：统一 C ABI 供不同绑定消费，或使用各语言专属的桥接入口。推荐评估统一 C ABI 以集中句柄、错误及所有权合同；代价是需显式设计类型/布局与版本边界。C/C++ 实现、pybind11 与 .NET 桥接路径需共同验证，不据此直接定架构。
- poll：受检借用包装，或直接导出裸缓冲/数组并约定到期使用属于调用者违规。推荐优先验证受检包装；若必须导出裸缓冲，要明确检查覆盖不到外部派生视图，不能承诺自动撤销或暗中复制延寿。
- 支持范围：精确列出 OS 发行版/版本、CPU 架构、Python 版本、原生库与 Windows .NET Framework 4.8 的组合，或分阶段增加组合。推荐只声明已取得证据的组合；精确列表仍待确认，不以 flake 环境或“最新 Linux LTS”替代。

最小可行性样例需要覆盖派生视图、下一次成功/失败读取、显式关闭、GC/终结器、push/写入缓冲固定与保活，以及 native 已成功后绑定失败。保留 Reader 引用不是对全部这些问题的答案；把全部旧分配永久保留也不是有界内存方案。

## 5. 建议的选择顺序

按[决策顺序](#decision-order)组织后续讨论，不要求一次回答全部问题。应把工作分成三种结果：

1. **可以写回契约的决定**：例如位置异常接收策略、Batch 选择及错误状态；必须有适用范围和理由，不由实现默认值替代。
2. **需要 M1 取证的机制候选**：例如旧数据保护、Flush 和绑定视图；可以形成候选协议，但没有运行证据前不宣称可行或关闭全部 D 项。
3. **明确后置的能力**：例如尚未定义的 Scan 映射、可选 GPU 及更多表示；需说明首发是否声明，不把未支持改记为 PASS。

故障模型 → 提交/Flush 协议 → 布局/生命周期编码 → 正式文件/API 冻结；真实 Frame 规模、资源目标和绑定验证并行反馈。不得按“先冻结所有编码、最后才验证失败机制”的顺序推进。

里程碑及证据状态以 [SPEC_TEST_PLAN.md](SPEC_TEST_PLAN.md#milestones) 为准，D 项的具体阶段依赖以 [DATA_SPEC 闭合表](DATA_SPEC.md#closure-gates) 为准。暂缓某一方向不表示该项已解决，也不阻止其他独立方向继续补充。
