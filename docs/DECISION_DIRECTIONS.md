## 1. 如何选择与使用

不必一次回答所有问题，可以只选一个角度，或限定到一种设备、采集模式和算法。未掌握的信息保留为“尚不清楚”；实际不存在的场景标为“不适用”，不据此扩展格式。

需要区分三类内容：

| 类型 | 要解决的问题 | 可用依据 |
|---|---|---|
| 事实补充 | 设备或业务实际如何工作？ | 设备说明、接口/调用示例、实际采集方案、算法输入说明 |
| 工程选择 | 在已知约束下，产品或 SDK 采用什么行为？ | 候选方案、适用范围、取舍理由及正反例 |
| 实验取证 | 某项保证在目标环境中是否成立？ | 可复核的正确性、持续负载、资源和故障实验结果 |

事实不能由实验默认值代替；工程选择不能代替设备能力；完成文档不能代替运行证据。本文列出的行为选项只是讨论提示，不表示已经采纳。

## 2. 设备与采集语义

<a id="angle-01"></a>
### 角度 1：Scan 起止与暂停

在已采纳多 Scan 方向下，需要补充：

- 哪些实际动作表示 Scan 开始、完成或中断，何时封存整个工件文件？
- 运动暂停、设备暂停、短暂停顿与结束后重启如何区分？
- 是否需要显式表示目标区域或来源 Scan？如果需要，它们的业务含义、模型及必要性是什么，而不是先指定关系方向、基数或无环约束？
- 是否需要共同工件参考系或 Scan 坐标映射？若需要，关系由谁提供，作用域及不可用情况怎样讨论？

适合提供的材料：一个工件的分块及局部复扫/精扫流程，说明 Scan 边界和实际空间/来源关系需求；未知项留空，不要求先构造区域或变换。

当前约束见 [R-01/R-12](DESIGN.md#r-01)及 [SCAN-01](DATA_SPEC.md#scan-01)，问题入口为 A-01、[SCAN-02/D-11](DATA_SPEC.md#scan-02)。不再把“是否允许多 Scan”列为待决策，但每个 Scan 的映射关系仍待决策；自动拼接、结果替代及已封存文件重开追加仍不在当前范围。

<a id="angle-02"></a>
### 角度 2：Frame 输入与事件/输出映射

需要补充：

- 上游向同步接口提交的一帧包含哪些事件、接收输出、波形流及对应有效性位？
- 设备来源 ID 等信息如何承载？其跳号/回绕/归组处理由调用者完成，不设计 SDK 等待或补全策略。
- 事件、硬件通道、阵元、合成输出和声束身份分别来自哪里？
- PA 的束如何对应事件、输出和法则？FMC 的有序 Tx/Rx 集合和 π 如何取得，是全探头还是子孔径？

适合提供的材料：一份采集方案和一帧交付示例，附事件/输出/流对应关系；设备不适用的模式无需填写。

关联 D-02/D-08/D-09、A-03/A-05。边界见 [REC-01](DATA_SPEC.md#rec-01)、[PA-01](DATA_SPEC.md#pa-01)、[FMC-01](DATA_SPEC.md#fmc-01)：归组由采集层承担，不将逐流拼装或晚到补写转移给 SDK。

<a id="angle-03"></a>
### 角度 3：样本表示与采样轴

需要补充：

- 各流实际 dtype、长度范围、字节序、有效 ADC 位、对齐、偏置及必要比例是什么？
- 保存的是原始整数码、物理量、RF、IQ、包络还是其他处理层次？哪些表示确实需要首版支持？
- 采样起点、间隔、延迟和单位如何解释？不同流是否使用共同物理时间轴？
- 若需要浮点或复数，原始表示与特殊值保真要求是什么？

适合提供的材料：按流列出的数据描述、少量可核对样本及采样轴解释，不以本地驱动函数名代替含义。

关联 D-02/D-07/D-09、A-07；契约见 [WAV-01](DATA_SPEC.md#wav-01)和[WAV-02](DATA_SPEC.md#wav-02)。可限定首版支持类型，不必先承诺所有 dtype；算法转换与原始存储分开。

<a id="angle-04"></a>
### 角度 4：位置描述与额外坐标关联

已确定采用必要公共描述＋带类型/版本内容，Scan 内描述固定、每帧保存一份值，PA 全部声束共用位置。需要补充：

- 最小公共描述、值编码及无效位置表示是什么？不要求本轮完善领域 schema。
- 实际反馈/理论坐标等额外 dataset 如何引用同一 Frame，怎样辨识描述与来源？
- 额外坐标缺值怎样表达，是否参与提交/封存检查？
- 绑定读取选择哪些位置内容，返回值还是可核对引用？结果生命周期怎样定义？

适合提供的材料：位置数据示例、参考对象说明，以及正常/异常位置下的操作预期。

关联 D-01/D-09、A-02/A-04。原始绑定与位置描述见 [POS-01](DATA_SPEC.md#pos-01)、[POS-02](DATA_SPEC.md#pos-02)；位置值不代替 Frame 身份，零坐标不代替缺失决定。更细运动模型若超出现有范围，单独记录冲突。

<a id="angle-05"></a>
### 角度 5：固定定义与元信息承载

必要公共描述＋带类型/版本的扩展元信息已采纳；更多领域 schema 可后续通过 Extensions 支持。本阶段只需补充：

- 公共描述最少包含哪些身份、作用域、类型/版本及引用信息？
- 内容如何承载和独立读取，不依赖当前设备配置？
- 未知领域内容与未知必要结构编码如何区别，能交付哪些关联结果？
- 固定内容怎样复用，如何避免逐帧请求重复复制整份定义？

适合提供的材料：实际方案导出或字段说明，并标注“必要原始解释 / 算法依赖 / 可选辅助”。

关联 D-02/D-09、A-05/A-09/A-11；固定定义规则见 [PAR-01](DATA_SPEC.md#par-01)。H/P/F 的关联标记不是实际设备子 schema；不要因此宣称真实几何或完整算法可复现性已解决。

## 3. SDK 行为与消费接口

<a id="angle-06"></a>
### 角度 6：批次原子失败与写入确认

失败语义见 [IO-01](DATA_SPEC.md#io-01)：push 失败目标不变；poll 不发布部分新结果，旧借用也不因读取失败延寿；写失败不新增提交且此前成功数据不变。不要求物理布局复原或崩溃事务，后续需设计和取证：

- push 怎样暂存后全批复制、保持失败目标不变？poll 怎样在下次读取开始时终止旧借用期，并仅在全批成功后发布新视图？两者预算如何限制？
- 怎样提交写批次、保护此前成功数据，尤其是与新数据共享的压缩 chunk 和 HDF5 元数据？
- 未提交空间如何处理，何时允许安全重试？Flush/封存协议如何与逻辑提交分开？
- 出错后的 Reader/Writer 状态、失败清理再次失败、原因/错误码如何表达？不能将未知状态称为回滚成功。

适合提供的材料：一次 Batch 的调用前后可观察状态及故障预期。实现不得只统一错误返回码就称为原子性；暂不选定日志、影子文件或暂存策略。设备停采/缓存仍是上游责任。

关联 D-02/D-05/D-10、A-06；提交与前缀规则见 [WRT-01](DATA_SPEC.md#wrt-01)、[WRT-02](DATA_SPEC.md#wrt-02)。接口选择不能放宽完整 Frame 提交、前置校验或故障后停止正常追加的边界。

<a id="angle-07"></a>
### 角度 7：有效性位图接口与错误结果

单一有效性位图与无效零填充已按 [STA-01](DATA_SPEC.md#sta-01) 确定，不再独立区分缺数据与“有值但业务无效”。剩余需要讨论：

- 位图输入/输出如何表达、打包并与 Frame/流/PA/FMC 身份对应，怎样检查长度、位序和容量？
- 无效槽位可不提供波形；具体接口怎样表达省略，仍需校验哪些请求结构和缓冲边界？
- 异构请求一项越界时，是请求级拒绝还是逐项结果/错误？
- 空选择、不支持能力、位置无效与结构/解码错误如何分别表达？
- 算法怎样消费样本＋有效性位图，避免把无效零填充当作真实零回波？不重新引入 SDK 业务合法性判断或无效原因分类。

适合提供的材料：几组输入/请求及预期结果说明，先说明含义，不必先选异常类或错误码。

关联 D-01/D-08/D-10、A-11；状态与选择语义见 [STA-01](DATA_SPEC.md#sta-01)、[READ-02](DATA_SPEC.md#read-02)。稠密读取随样本返回位图，无效槽位零填充且不跳过；不再讨论是否拒绝无效矩阵或保存无效输入波形。零填充不是补采，不引入等待或晚到补写。

<a id="angle-08"></a>
### 角度 8：分析/Batch 交付与布局

分析结果随元信息返回，Batch 一次读取多个 Frame；poll 借用 SDK 只读视图，push 复制到指定调用者缓冲，两种所有权不与内容用途绑定。Frame 优先、A-Scan 次之，单 Frame 不分块，无 update，重复等价读取值一致。还需细化：

- Batch 使用起点/数量还是也支持离散索引，范围越界怎样报告？
- 同构内存排列、异构多缓冲/偏移怎样描述，Frame/流及样本身份怎样核对？
- 分析模式元信息与额外坐标如何组织；Batch 除必要布局/身份说明外是否带完整元信息？
- 容量如何查询或声明，超出 Frame/Batch 上限怎样失败？不能退化为截断或帧内分块。
- 样本和有效性位图怎样排列、报告容量并共同交付，特别是 Batch GPU 消费路径？无效槽位按 STA-01 零填充，不能丢位图、隐式跳过或为拼接改变有效样本 dtype。

poll 旧视图在同一 Reader 下次数据读取（含 push 或失败）或关闭时失效，不能释放或继续解引用；push 缓冲由调用者管理，关闭 Reader 不释放它。GPU 异步上传完成前，poll 不能再读/关闭，push 不能复用/释放目标。主机指针不是磁盘地址或零拷贝承诺。记录入口见 [场景审计第 4 节](SCENARIO_AUDIT.md#4-算法输入与读取方式核查)。

关联 D-03/D-10、A-08/A-10/A-12；访问能力见 [访问规划](ACCESS_USE_CASE_PLAN.md)。不默认所有读取都零拷贝或连续，也不因实现方便改变保序保重复及逐流边界语义。

## 4. 正式格式与运行证据

<a id="angle-09"></a>

- 状态、生命周期、计数、引用、字符串和字节序如何映射到 HDF5？
- 未知必要语义或 filter 参数如何拒绝？部署方案暂不设计。

适合提供的材料：拟支持范围及必要编码方案，配套正反样例和独立读取证据规划。

<a id="angle-10"></a>
### 角度 10：Frame/Batch 优先负载与后续取证

负载覆盖连续批量写、Frame 随机读、GPU 上传前的 Batch 读及次级 A-Scan 随机读。Frame/Batch 优先，本阶段只做设计、不调优，后续补充：

- 持续/突发输入速率、典型扫描规模和实际请求序列是什么？
- 延迟、阻塞、内存预算和输出连续性要求是什么？哪些是期望目标，哪些是已有测量？
- 目标机器、CPU、磁盘及解码依赖环境是什么？
- 能否取得可用于实验的真实波形和不可压缩压力输入？
- 在固定语义及负载下，如何比较布局、chunk、codec、cache、批量和预分配？

适合提供的材料：一份目标环境与工作负载说明；初期可先补事实和目标，不立即确定调优参数。

关联 D-02/D-03/D-04、A-12；测量方法见 [验证计划第 6 节](SPEC_TEST_PLAN.md#6-性能与-gpu-专项)。历史微基准的限制见 [BENCHMARK_REPORT.md](BENCHMARK_REPORT.md)，不能替代真实负载或超 RAM 证据。

<a id="angle-11"></a>
### 角度 11：封存、持久化与恢复

需要讨论并取证：

- Scan 完成与文件封存分别怎样检查？是否允许空 Scan 完成或无 Scan 文件封存，接口如何表达？
- 普通写入不立即落盘、显式 Flush 强制落盘已定；何时算完成 OS 持久化步骤，如何覆盖必要元数据，失败怎样报告？
- 关闭/封存是否自动执行等价 Flush，调用前哪些成功批次在其保证范围内？
- Scan 目录及各 Scan 的完整前缀由什么建立可信依据？声明值、extent 或标记不可信时怎样报告？
- 磁盘满、I/O 失败、进程中断和断电分别怎样影响已接受数据？
- 部分压缩 chunk 更新中断是否影响旧帧？哪些损坏可检测，哪些只能报告尚未验证？
- 恢复报告怎样区分结构可读、可解码、内容已核对及未执行检查？

适合提供的材料：异常结束时的用户预期、候选确认/封存协议，以及受控故障实验计划。

关联 D-05/D-07/D-10、T-12/T-15；边界见 [LIF-01](DATA_SPEC.md#lif-01)、[LIF-02](DATA_SPEC.md#lif-02)。恢复仍是显式尽力只读，不预设零损失、固定时间窗或自动修复；讨论实验不等于授权破坏性故障操作。

<a id="angle-12"></a>
### 角度 12：可选 GPU 解压

需要补充并取证：

- 目标 GPU、库、实际 filter 链及下游计算输入是什么？
- 压缩封装、逆变换、尾块及校验是否全部能够正确处理？
- 与 CPU 解码对照时，原始样本及轴身份是否一致？
- 包含传输、解码、布局转换和下游消费后，端到端收益是什么？

适合提供的材料：目标 GPU 消费路径及实际编码链，而不只是一个 GPU 解码函数计时。

关联 D-06、T-20；声明边界见 [CMP-02](DATA_SPEC.md#cmp-02)。该方向可独立暂缓，不阻塞基础 CPU 读取。

<a id="angle-13"></a>
### 角度 13：平台与语言绑定

目标为最新 Linux LTS、Windows 10+，优先 Python 和 .NET Framework 4.8，倾向 C/C++/pybind11。pybind11 不自动解决 .NET 绑定；具体语言/版本/ABI 仍待选择。绑定须区分 poll 借用失效与 push 所有者保活；保留 Reader 对象不等于跨下一次读取/显式关闭延长旧视图，不能默认偷偷复制或后台借用。这里不扩为部署/打包方案。

.NET Framework 4.8 消费端面向 Windows，不能把这一目标解释成 Linux 上运行该框架。原生库、Python 和 Windows .NET Framework 4.8 的支持应分别取得证据；精确矩阵见 D-12，当前没有实现或验证声明。

## 5. 建议的选择顺序

以下是推进建议，不是新增里程碑完成条件，也不要求现在选择全部主题：

1. **有效性位图与 Batch 交付**：优先选角度 7＋8，明确数据/位图布局、接口、元信息及 poll/push API；遵守已定单一有效性、零填充及借用期/所有权，不加入帧内分块。
2. **调用级强原子性机制**：选角度 6，设计读暂存和写提交/旧数据保护；不重开已定边界，也不把目标误作已实现保证。
3. **Flush/封存**：选角度 11，细化显式落盘的保证及错误状态；写入取消已排除。
4. **最小公共描述与互通**：选角度 3～5、9、13，明确 Core 必要描述和消费端边界，不先完善领域 schema 或部署方案。
5. **后续运行证据**：选角度 10～11，明确 Frame/Batch 优先指标，再推进 M3；本阶段不启动实验或调优。
6. **可选 GPU 解压**：角度 12 独立推进，面向 M4；与 Batch 主机视图不同。

里程碑及证据状态以 [SPEC_TEST_PLAN.md](SPEC_TEST_PLAN.md#milestones) 为准，D 项的具体阶段依赖以 [DATA_SPEC 闭合表](DATA_SPEC.md#closure-gates) 为准。暂缓某一方向不表示该项已解决，也不阻止其他独立方向继续补充。
