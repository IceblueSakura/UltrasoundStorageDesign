## 1. 如何选择与使用

不必一次回答所有问题。当前先细化下列业务含义；已确认范围见 [ADR-0011](decisions/0011-ultrasound-business-boundary.md)，不再询问是否接纳无位置记录、位置异常有效波形、模式 schema 或 C 扫快照。既有工程决定保留适用范围，但不直接限制新增能力；本轮不讨论实现细节、许可证或 API 定版，不修改或运行旧代码/测试。

| 类型 | 要解决的问题 | 可用依据 |

## 2. 设备与采集语义

<a id="angle-01"></a>
### 角度 1：Scan 起止与暂停

在已采纳多 Scan 方向下，需要补充：

- 哪些实际动作表示 Scan 开始、完成或中断，何时封存整个工件文件？
- 运动暂停、设备暂停、短暂停顿与结束后重启如何区分？未封存文件干净关闭后（例如次日复扫）是否需要重开追加？（D-15）
- 目标区域及复检/局部重扫指向原扫描具体区域的需求已定；待恢复区域讨论时，再明确区域内容、模型和适用条件，不预设关系基数、无环约束或坐标表示。
- 是否需要共同工件参考系或 Scan 坐标映射？若需要，关系由谁提供，作用域及不可用情况怎样讨论？

适合提供的材料：一个工件的分块及局部复扫/精扫流程，说明 Scan 边界和实际空间/来源关系需求；未知项留空，不要求先构造区域或变换。

当前约束见 [R-01/R-12](DESIGN.md#r-01)及 [SCAN-01](DATA_SPEC.md#scan-01)，问题入口为 A-01、[SCAN-02/D-11](DATA_SPEC.md#scan-02)。不再把“是否允许多 Scan”列为待决策，但每个 Scan 的映射关系仍待决策；自动拼接、结果替代及已封存文件重开追加仍不在当前范围。

**候选与建议（未采纳）**：

- Scan 映射：承载必要关系已确认，继续按实际分块/独立复检场景明确具体关系，不预设引用图或计算变换。旧 Core 容器可以作为局部验证对象，但不能据此取消产品的必要关系责任。
- 空 Scan/无 Scan 文件：允许作为合法空结果，或拒绝正常完成/封存。推荐只有明确消费场景时才纳入合法空结果；当前尚无足够事实选择，不能先写允许/拒绝断言。
- 不论空对象选择如何，都需补一张 File/Scan/Reader/Writer 的“状态 × 操作 → 结果/下一状态”表，覆盖完成、封存、关闭、故障及重复调用。Scan 完成不等于工件检测完成。

<a id="angle-02"></a>
### 角度 2：Frame 输入与事件/输出映射

需要补充：

- 上游向同步接口提交的一帧包含哪些事件、接收输出、波形流及对应有效性位？
- 设备来源 ID 等信息如何承载？其跳号/回绕/归组处理由调用者完成，不设计 SDK 等待或补全策略。
- 事件、硬件通道、阵元、合成输出和声束身份分别来自哪里？
- PA 的束如何对应事件、输出和法则？FMC 的有序 Tx/Rx 集合和 π 如何取得，是全探头还是子孔径？

适合提供的材料：一份采集方案和一帧交付示例，附事件/输出/流对应关系；设备不适用的模式无需填写。

**需要提交的事实，不是待选实现方案**：对首发每个模式提供可核对的交付说明或真实小样例，包含模式/设备版本、事件—接收输出—流映射、dtype/长度/采样轴、有效性和位置来源、最大 Frame 大小。材料暂缺则记录缺口；H/P/F/W 的合成期望不替代这些输入，也不要求现在操作设备。是否属于首发范围须与角度 9 一起确认。

关联 D-02/D-08/D-09、A-03/A-05。边界见 [REC-01](DATA_SPEC.md#rec-01)、[PA-01](DATA_SPEC.md#pa-01)、[FMC-01](DATA_SPEC.md#fmc-01)：归组由采集层承担，不将逐流拼装或晚到补写转移给 SDK。

<a id="angle-03"></a>
### 角度 3：样本表示与采样轴

需要补充：

- 各流实际 dtype、长度范围、字节序、有效 ADC 位、对齐、偏置及必要比例是什么？
- 保存的是原始整数码、物理量、RF、IQ、包络还是其他处理层次？哪些表示确实需要首版支持？
- 采样起点、间隔、延迟和单位如何解释？不同流是否使用共同物理时间轴？
- 若需要浮点或复数，原始表示与特殊值保真要求是什么？

适合提供的材料：按流列出的数据描述、少量可核对样本及采样轴解释，不以本地驱动函数名代替含义。

关联 D-02/D-07/D-09、A-07；契约见 [WAV-01](DATA_SPEC.md#wav-01)和[WAV-02](DATA_SPEC.md#wav-02)。可限定首版支持类型，不必先承诺所有 dtype；算法转换与原始存储分开。

**候选与建议（未采纳）**：按实际输入限定一组样本表示，或首发就承诺广泛整数/浮点/复数。推荐前者，逐项写明支持/拒绝和保真规则；代价是范围外输入必须显式拒绝，而不是转换后保存。没有实际依据时不在本文指定类型清单；纳入浮点/复数前须闭合特殊值保真，不能把 H 的测试 dtype 直接当首发列表。

<a id="angle-04"></a>
### 角度 4：位置描述与帧级附加记录

已确定采用必要公共描述＋带类型/版本内容，Scan 内描述固定、每帧保存一份值，PA 全部声束共用位置；时间戳、来源 ID、额外坐标统一为帧级附加记录，与 Frame 同一提交单元写入（[ADR-0001](decisions/0001-stream-groups.md)）。需要补充：

- 无空间位置、位置未知/无效及正常位置怎样分别表达？业务接收方向已定，只需继续明确必要描述及读取含义。
- 实际反馈/理论坐标等帧级附加记录怎样辨识描述与来源？
- 各帧级附加记录缺值怎样表达，是否参与提交/封存检查？
- 绑定读取选择哪些位置内容，返回值还是可核对引用？结果生命周期怎样定义？

适合提供的材料：位置数据示例、参考对象说明，以及正常/异常位置下的操作预期。

关联 D-01/D-09、A-02/A-04。原始绑定与位置描述见 [POS-01](DATA_SPEC.md#pos-01)、[POS-02](DATA_SPEC.md#pos-02)；位置值不代替 Frame 身份，零坐标不代替缺失决定。更细运动模型若超出现有范围，单独记录冲突。

无空间位置记录及位置异常时保全有效波形已由 POS-01 确认，不再保留拒绝有效波形作为并列选择。剩余讨论如下：

| 问题 | 候选与影响 | 推荐方向及条件 |
|---|---|---|
| 帧级附加记录是否必需 | 全部必需会扩大提交依赖；逐份声明必要性可容纳缺值，但需要固定的缺失与校验规则 | 推荐由 Scan 定义固定必要性，原始位置与附加内容分开解释 |
| 附加记录晚到 | 同一提交单元提供或显式缺失，符合不可变历史；允许后补则需另定义时序及一致性，并审查既有禁止晚到补写边界 | 推荐首版不引入后补，真实业务冲突先回到 DESIGN 决策 |

产出应同时说明接受/拒绝条件、位置与波形状态组合、附加内容缺值和封存关系，然后再选择编码。仅提供正常位置字段表不能关闭本组问题。

<a id="angle-05"></a>
### 角度 5：固定定义与元信息承载

模式专属 schema 与解释已有数据所需参数已是 SDK 责任（REL-01）；公共描述和类型/版本不能代替内容语义。继续补充：

- 公共描述最少包含哪些身份、作用域、类型/版本及引用信息？
- 内容如何承载和独立读取，不依赖当前设备配置？
- 未知领域内容与未知必要结构编码如何区别，能交付哪些关联结果？
- 固定内容怎样复用，如何避免逐帧请求重复复制整份定义？

适合提供的材料：实际方案导出或字段说明，并标注“必要原始解释 / 算法依赖 / 可选辅助”。

关联 D-02/D-09、A-05/A-09/A-11；固定定义规则见 [PAR-01](DATA_SPEC.md#par-01)。H/P/F 的关联标记不是实际设备子 schema；不要因此宣称真实几何或完整算法可复现性已解决。

继续按实际超声数据列清必要参数、单位、信号表示及关联；单探头/相控阵的差异明确表达，不把必要身份与采样解释藏入无约定字节块。只需解释已有数据，不因此恢复完整工艺、现场条件或扫描复现目标；Core/扩展划分不在本轮定案。

### 角度 6：失败机制与绑定层失败

已决定（[ADR-0002](decisions/0002-durability-and-failure.md)、[ADR-0006](decisions/0006-core-io-and-selection-layer.md)）：IO-01 作用于每一次数据读写调用；写失败后 Writer 进入失败态，失败调用不得修改已提交数据，并以校验值观察；带失败标记封存是失败后可用的读取路径。参考机制见 [MAP-02](DATA_SPEC.md#map-02)。仍未决定：

- 参考机制（物理块只写一次 + 尾部日志 + 双槽提交记录 + push 两阶段读）是否采用，或以什么替代；push 两阶段读的暂存与时间代价是否可接受（见 [M1 报告](../experiments/m1/REPORT.md)）。
- 未提交空间如何处理；失败态下哪些错误允许重试，是否存在可恢复的瞬时错误。
- 分配、封送或结果构造失败是否处于公共调用的成功/失败单元内？原生已提交、绑定却抛错时怎样报告，调用者是否可以重试？
- 失败清理再次失败、带失败标记封存本身失败时的错误表达。

关联 D-05/D-10/D-12、A-06。

**候选与建议（未采纳）**：

| 决策 | 候选与代价 | 推荐方向 |
|---|---|---|
| 写入保护机制 | 只写一次的物理块：写入端须按组整块组装（内存随每块帧数增长），Scan 完成时尾块只写一次；或在 SWMR 下追加（不回收空间，但仍会重写尾块） | 以 M1 证据为准，优先只写一次；SWMR 作为附加的元数据顺序保护另行取证 |
| push 读失败目标不变 | 两阶段读（先解码到暂存、校验通过再复制）多一份暂存与复制；或放宽为"失败后目标内容未定义" | 先看 M1 测得的代价；代价可接受则保持既定语义 |
| 绑定层失败 | 将可失败准备工作放在提交/目标复制前，或设计能区分已提交/未提交/未知的错误结果合同 | 优先减少提交后的可失败工作；仍存在的失败必须可区分，不得包装成可盲重试的"未提交" |

### 角度 7：有效性位图接口与错误结果

单一有效性位图与无效零填充已按 [STA-01](DATA_SPEC.md#sta-01) 确定；写入须显式提交完整位图并提供可选严格模式（[ADR-0003](decisions/0003-explicit-validity-bitmap.md)）。剩余需要讨论：

- 位图输入/输出如何表达、打包并与 Frame/流/PA/FMC 身份对应，怎样检查长度、位序和容量？
- 无效槽位可不提供波形；具体接口怎样表达省略？严格模式按 Writer、Scan 还是调用开启？
- 异构请求一项越界时，是请求级拒绝还是逐项结果/错误？
- 空选择、不支持能力、位置无效与结构/解码错误如何分别表达？
- 算法怎样消费样本＋有效性位图，避免把无效零填充当作真实零回波？不增加 SDK 业务合法性判断，但须区分 RET-01 的未保留、缺测、无效与有效零值；波形位不能独自表达它们。

适合提供的材料：几组输入/请求及预期结果说明，先说明含义，不必先选异常类或错误码。

关联 D-01/D-08/D-10、A-11；状态与选择语义见 [STA-01](DATA_SPEC.md#sta-01)、[READ-02](DATA_SPEC.md#read-02)。稠密读取随样本返回位图，无效槽位零填充且不跳过；不再讨论是否拒绝无效矩阵或保存无效输入波形。零填充不是补采，不引入等待或晚到补写。

**候选与建议（未采纳）**：

- 输入选择有一项越界：请求整体拒绝，或返回明确逐项校验结果。推荐首版整体拒绝，简化调用与原子目标的组合；代价是调用者需要拆分请求。无论选择哪种，I/O 错误仍按 IO-01 使整个调用失败。
- API 位图：直接暴露打包位图，或在绑定提供更易用的布尔表示并明确转换。前者便于容量与 GPU 消费，后者增加副本与转换；推荐先统一槽位顺序、位序/尾部位及容量规则，再决定每个绑定是否增加显式适配，不要求磁盘与 API 编码相同。
- 需要分别给出空选择、容量不足、不支持能力、结构/解码错误的结果，以及错误后能否继续使用 Reader/Writer；不要只列错误枚举而省略状态和目标缓冲语义。

### 角度 8：分析/Batch 交付与布局

分析结果随元信息返回，Batch 一次读取 B≥1 个 Frame；poll 借用 SDK 只读视图，push 复制到指定调用者缓冲，两种所有权不与内容用途绑定。Core I/O 按流组交付，组内为稠密块，帧内选择是选择层（[ADR-0006](decisions/0006-core-io-and-selection-layer.md)）。还需细化：

- Batch 使用起点/数量还是也支持离散索引，范围越界怎样报告？
- 跨流组的多缓冲/偏移怎样描述，Frame/流组/流及样本身份怎样核对？
- 分析模式元信息与帧级附加记录如何组织；Batch 除必要布局/身份说明外是否带完整元信息？
- 容量如何查询或声明，超出 Frame/Batch 上限怎样失败？不能退化为截断或帧内分块。
- 样本和有效性位图怎样排列、报告容量并共同交付，特别是 Batch GPU 消费路径？无效槽位按 STA-01 零填充，不能丢位图、隐式跳过或为拼接改变有效样本 dtype。

借用结束条件与 GPU 双缓冲方式已定（[BUF-01](DATA_SPEC.md#buf-01)、[ADR-0004](decisions/0004-concurrency-and-borrow-scope.md)）。主机指针不是磁盘地址或零拷贝承诺。记录入口见 [场景审计第 4 节](SCENARIO_AUDIT.md#4-算法输入与读取方式核查)。

关联 D-03/D-10、A-08/A-10/A-12；访问能力见 [访问规划](ACCESS_USE_CASE_PLAN.md)。不默认所有读取都零拷贝或连续，也不因实现方便改变保序保重复及逐流边界语义。

**候选与建议（未采纳）**：

| 问题 | 候选与影响 | 推荐方向 |
|---|---|---|
| Batch Frame 选择 | 连续起点/数量简单且便于容量估算；离散清单更灵活，但增加保序重复、聚合和错误检查 | 首版先连续 Batch，除非实际请求证明离散清单必需；不影响已定帧内有序选择 |
| 跨组交付 | 每组一个缓冲直观；打包缓冲＋偏移便于集中管理，但对齐和容量校验更复杂 | 先采用每组一个稠密缓冲的最小描述方案，通过消费示例比较，不预定连续单数组 |
| push 容量准备 | 提供需求查询，或要求调用者从描述计算；后者减少 API，但易重复布局逻辑 | 推荐可核对的容量/布局查询（已定：容量查询不结束 poll 借用） |

最小产出是一组读写调用示例及结果描述：单 Frame、Batch、异构、位图、关联元信息、容量不足和空选择。分析/Batch × poll/push 是两个维度，不能只实现两个对角组合便宣称覆盖。

<a id="angle-15"></a>
### 角度 15：超内存访问与上位机内存池

**状态：暂缓（2026-10-25）。** 上位机的内存组织方式尚未确定；以下问题与候选保留备查，不作为当前设计方向，也不阻塞其他接口决定。

已决定：调用者控制 Batch 大小，不要求整个 Scan 驻留内存（[CAP-01](DATA_SPEC.md#cap-01)）；SDK 不在调用返回后保留 push 目标的引用，调用者可以复用目标缓冲（[BUF-01](DATA_SPEC.md#buf-01)）；单 Frame 不分块交付；同一 Reader 同一时刻只有一份 poll 视图（[ADR-0004](decisions/0004-concurrency-and-borrow-scope.md)）。上位机曾考虑以可复用内存池承载 push 目标、按 Batch 读写超内存文件，尚未决定。恢复讨论时需要回答：

- 块几何与容量查询：每个流组每块的帧数、每帧样本/位图/帧级附加记录的字节数及 Batch 所需容量，以什么调用提供（D-10）。
- SDK 内部内存（push 两阶段读的暂存、解码工作区、写入端的整块组装缓冲）只需可查询并可设上限，还是也要从上位机内存池分配（D-02/D-10）。
- Batch 未按存储块对齐时，SDK 是否缓存边界块，缓存预算由谁设定（D-04）。
- 写入端每块帧数 F 怎样随 Frame 大小选择，使整块组装缓冲（每组最多 F−1 帧）不超出预算（D-02/D-04）。

适合提供的材料：内存池的形式（固定大小槽位或按需大小、对齐或锁页要求、是否同时用于 GPU 上传）、典型访问模式（顺序遍历、随机跳转浏览、局部反复访问）与内存预算。

关联 D-02/D-04/D-10、T-18/T-19；访问场景见[访问规划](ACCESS_USE_CASE_PLAN.md)。M1 原型以 3 个各 64 帧的槽位（共 46 MB）遍历 2995 帧（解码后 749 MB），进程常驻内存稳定在约 100–104 MB，不随已读帧数增长（[M1 报告](../experiments/m1/REPORT.md)）；数据量小于内存，不代替 T-18 的超 RAM 验证。

**候选与建议（未采纳）**：

| 方案 | 做法与代价 | 建议 |
|---|---|---|
| A. 上位机内存池＋push | 上位机按容量查询分配若干槽位，每次 Batch push 到空闲槽位；SDK 内存只含单次调用的暂存与解码工作区，与文件大小无关；不需要新的所有权模型 | 推荐作为 Core 路径；补充块几何与容量查询，使槽位大小与 Batch 边界能按存储块对齐 |
| B. SDK 管理的多份借用（租借池） | SDK 持有缓冲池，读取返回须显式归还的租借，可省去一次复制；但要放开“同一 Reader 只有一份 poll 视图”，绑定须管理多份借用的寿命 | 暂不采用；只有测得复制成为瓶颈时再议 |
| C. 可注入的内存资源 | 上位机以回调提供分配/释放，SDK 内部暂存与工作区也计入上位机预算 | 首版不做；可扩展参数已定（ADR-0010），以后加入不改签名 |
| D. 绑定层的惰性数组视图 | 例如 Python 对象按切片发起 Batch 读取，.NET 按 Batch 枚举非托管缓冲 | 作为绑定便利层建在 A 之上，不进入 Core 语义 |
| E. mmap 映射 | 存储块经过压缩并带校验，映射文件得不到解码后的样本；只对不压缩的布局可行（按块偏移映射），却绕过校验并锁定布局 | 不采用 |

A 的配套建议：

- **对齐**：Batch 的起点与帧数取块帧数 F 的整数倍时，每个块只解码一次，暂存也等于目标大小。M1 原型中，未对齐的顺序遍历吞吐低约 19%；B=16 的随机读多解码一个块，耗时约翻倍。
- **边界块缓存**：SDK 保留最近解码的边界块（每组一块，预算有界），未对齐的顺序遍历就不再重复解码。属实现选择，尚未测量。
- **预读**：由上位机控制，例如第二个线程把下一个 Batch 读入下一个槽位；SDK 不做隐式后台预读，与“不偷偷复制或后台借用”一致。进程内 HDF5 调用串行化，但解码可以在锁外并行。
- **浏览缓存**：随机跳转浏览时，上位机可以把槽位当作以（Scan、流组、块对齐起点）为键的 LRU 缓存。
- **写入端**：整块组装缓冲每组最多 F−1 帧；FMC 等大 Frame 宜取 F=1，或沿 K 切分物理块（只是物理布局，不改变以 Frame 为单位的交付）。
- **后续**：是否需要额外概览数据按实际需求另议，不因本候选扩张产品范围；已确认 C 扫快照按 SNAP-01，不以“只属于 Extension”为由排除。

### 角度 16：公开 API 稳定性

已决定：公开 API 的稳定包括调用语义稳定与接口演进兼容；原生库唯一的稳定边界是 C ABI，长度 64 位、缓冲以“指针＋字节长度”描述，选项结构体以自身大小开头且可能演进的调用带预留标志，错误码与提交状态稳定（[ADR-0010](decisions/0010-public-api-stability.md)、[API-01](DATA_SPEC.md#api-01)）。IO-01 按调用生效、poll/push 所有权与借用结束条件、Core I/O 与选择层的边界不随实现变化（[ADR-0004](decisions/0004-concurrency-and-borrow-scope.md)、[ADR-0006](decisions/0006-core-io-and-selection-layer.md)）。仍未决定：

- 兼容承诺的级别、对象与起始版本：只保证源码兼容，还是也保证二进制兼容；对哪些消费端承诺；草案期是否允许不兼容修改。
- 版本规则，以及库版本与能力的运行时查询。
- 文件格式版本与库/API 版本的关系（与 D-07 一起）。
- 错误码清单、分类与可重试性的具体内容（D-10，原则已定）。
- 各绑定是否建在 C ABI 之上（[角度 13](#angle-13)）。

适合提供的材料：首发消费端清单与各自的升级方式（原生库是否随应用一起发布、是否有第三方插件直接链接 SDK）、可接受的兼容期限。

关联 D-07/D-10/D-12。

**候选与建议（未采纳）**：

| 主题 | 建议 | 理由与代价 |
|---|---|---|
| 版本与能力 | 运行时可查询库版本与能力（codec、可选特性）；文件格式版本与库版本分离；按语义化版本管理，Linux 上 SONAME 随不兼容变更递增，并以符号版本脚本只导出公开符号 | 同一版本的不同构建（例如缺少某个 codec）行为可判断 |
| 兼容检查 | CI 中用 libabigail 的 `abidiff` 比较相邻发布的 ABI，并保留旧版消费示例的编译与运行测试 | 把“稳定”变成可自动执行的门禁 |
| 所有权与线程 | 函数名与类型区分借用（poll）与复制（push）；关闭幂等；每个函数注明线程安全等级（任意线程/同一句柄串行），与 ADR-0004 的进程内串行化一致 | 绑定可以据此机械生成，不靠口头约定 |
| 回调 | 需要回调时（日志、分配器）使用函数指针结构体＋上下文指针；回调内不得重入 SDK，不得跨边界抛出异常 | 避免跨语言异常与重入问题 |
| 绑定 | Python/.NET 只做薄封装，不在绑定层加入独立语义（自动重试、隐藏复制）；绑定版本跟随原生版本 | 语义只有一份，跨语言行为一致 |
| 草案期 | 1.0 之前允许不兼容修改，但从现在起维护 API 变更记录，并以消费示例驱动接口设计 | 冻结前保留调整余地，冻结时已有可检查的基线 |

### 角度 10：访问优先级与后续负载取证

连续批量写、Frame 随机读、GPU 上传前的 Batch 读及 A-Scan 随机读是既有候选负载。优化优先级按 ACCESS-01 的实际场景确认，不固定旧的 Frame/Batch 优先顺序；当前不调优，后续补充：

- 持续/突发输入速率、典型扫描规模和实际请求序列是什么？
- 延迟、阻塞、内存预算和输出连续性要求是什么？哪些是期望目标，哪些是已有测量？
- 目标机器、CPU、磁盘及解码依赖环境是什么？
- 能否取得可用于实验的真实波形和不可压缩压力输入？
- 在固定语义及负载下，如何比较布局、chunk、codec、cache、批量和预分配？

适合提供的材料：一份目标环境与工作负载说明；初期可先补事实和目标，不立即确定调优参数。

关联 D-02/D-03/D-04、A-12；测量方法见 [验证计划第 6 节](SPEC_TEST_PLAN.md#6-性能与-gpu-专项)。历史微基准的限制见 [BENCHMARK_REPORT.md](BENCHMARK_REPORT.md)，不能替代真实负载或超 RAM 证据。

**需要输入的目标**：典型/最大流数与 S_k、最大 Frame 字节量、Batch 范围、持续/突发输入及持续时间、Frame/Batch/A-Scan 请求比例、吞吐/延迟/阻塞门槛、内存上限和目标机器。数值未知就明确缺口，不在本文件填猜测默认值。

**候选与建议（未采纳）**：固定一组目标环境与验收负载，或为多档环境分别声明配置和门槛。推荐先固定一组可复核环境，不宣称结果普遍成立。峰值口径应覆盖调用者目标、SDK 结果/原子暂存、HDF5 解码/cache、位图/关联和绑定副本；B=1 仍要能容纳单 Frame。更多调优可后置，但已声明的超 RAM、有界资源及负载目标不能以“以后再优化”免验。

<a id="angle-11"></a>
### 角度 11：封存与恢复细节

已决定（[ADR-0002](decisions/0002-durability-and-failure.md)、[ADR-0008](decisions/0008-process-crash-scope.md)）：Flush 成功后条件覆盖之后任意时刻的进程崩溃，断电与操作系统崩溃不作保证、不取证；Flush 只需把数据交给操作系统，不要求 fsync；完成 Scan 隐含 Flush；正常封存以等价 Flush 结束；提交记录唯一权威，逐块校验值必需；恢复不改源文件。仍未决定：

- HDF5 自身元数据刷新期间崩溃（例如块索引或空间管理元数据更新中）由什么覆盖：SWMR 的写入顺序、SDK 自有提交记录，或二者兼有？是否让每个 Scan 进入 SWMR（Scan 之间须重开文件，见 MAP-02）？
- 带失败标记封存、Scan 完成记录、提交记录与校验值的编码（与 D-07 一起）。
- 是否允许空 Scan 完成、无 Scan 文件封存，接口如何表达？
- 提交记录损坏、超出可信前缀的抢救是否提供？
- 未封存文件干净关闭后能否重开追加（D-15）。

适合提供的材料：上位机进程异常结束的典型场景与用户预期、可接受的未 Flush 损失。

关联 D-05/D-07/D-10/D-15、T-12/T-15；边界见 [LIF-01](DATA_SPEC.md#lif-01)、[LIF-02](DATA_SPEC.md#lif-02)。讨论实验不等于授权破坏性故障操作。

**候选与建议（未采纳）**：

- SWMR：M1 中非 SWMR 与 SWMR 两种模式在随机 SIGKILL 与故障点下都满足后条件。非 SWMR 的崩溃文件只要在内存中清除 superblock 状态标志，就能原地只读打开，恢复结果与“复制＋`h5clear`”一致，不必复制整个文件（[M1 报告](../experiments/m1/REPORT.md)）；该做法依赖 HDF5 的私有属性，须随版本复核，替代方案是读取时修补 superblock 的只读 VFD。是否采用 SWMR 因此只取决于它对元数据写入顺序的保护。推荐先在块索引足够大（块数多、索引多级）的文件上比较两种模式的崩溃结果再决定；SWMR 属实现内部选择，不进入公开 API。
- 空对象：只有明确消费场景时才纳入合法空结果；当前尚无足够事实选择，不先写允许/拒绝断言。
- 补一张 File/Scan/Reader/Writer 的“状态 × 操作 → 结果/下一状态”表，覆盖完成、封存、带失败标记封存、关闭、故障及重复调用。

<a id="angle-12"></a>
### 角度 12：可选 GPU 解压

需要补充并取证：

- 目标 GPU、库、实际 filter 链及下游计算输入是什么？
- 压缩封装、逆变换、尾块及校验是否全部能够正确处理？
- 与 CPU 解码对照时，原始样本及轴身份是否一致？
- 包含传输、解码、布局转换和下游消费后，端到端收益是什么？

适合提供的材料：目标 GPU 消费路径及实际编码链，而不只是一个 GPU 解码函数计时。

关联 D-06、T-20；声明边界见 [CMP-02](DATA_SPEC.md#cmp-02)。该方向可独立暂缓，不阻塞基础 CPU 读取。

**候选与建议（未采纳）**：首发不声明 GPU 解压、保留 CPU 解码与 Batch 主机交付，或把明确 GPU/filter 链加入首发可选支持。推荐前者，避免可选加速拖延 Core；代价是初版不能宣传 GPU 解压收益。后续声明须独立完成 M4，不改变已定的 Batch 内容与位图交付目标。

<a id="angle-13"></a>
### 角度 13：平台与语言绑定

保留 Linux LTS、Windows 10+、Python 和 Windows .NET Framework 4.8 目标，并须满足 UMS 的 .NET 10、Windows/Linux x64 消费需求；C/C++/pybind11 是既有工程倾向。进程内串行化与多 Reader 已定（[ADR-0004](decisions/0004-concurrency-and-borrow-scope.md)）；原生库唯一的稳定边界是 C ABI（[ADR-0010](decisions/0010-public-api-stability.md)）。pybind11 不自动解决 .NET 绑定；实现语言、绑定方式与版本仍待选择。.NET Framework 单个托管数组上限约 2 GiB（即使开启 `gcAllowVeryLargeObjects`，byte 数组最多 2,147,483,591 字节），更大的 Batch 须走非托管内存。绑定须区分 poll 借用失效与 push 所有者保活；保留 Reader 对象不等于跨下一次读取/显式关闭延长旧视图，不能默认偷偷复制或后台借用。这里不扩为部署/打包方案。本阶段只在 Linux 上设计与验证；Windows（含 .NET Framework 4.8）在草案基本确定后测试，接口须预先满足其约束（64 位长度、非托管缓冲，见 [API-01](DATA_SPEC.md#api-01)）。

.NET Framework 4.8 消费端面向 Windows，不能把这一目标解释成 Linux 上运行该框架。原生库、Python 和 Windows .NET Framework 4.8 的支持应分别取得证据；精确矩阵见 D-12，当前没有实现或验证声明。

**候选与建议（未采纳）**：

- 绑定构建：各绑定建在 C ABI 之上，或使用语言专属的桥接（例如 pybind11 直接封装 C++ 实现）。推荐建在 C ABI 之上，使句柄、错误与所有权合同只有一份；代价是 Python 侧多一层封装。C/C++ 实现、pybind11 与 .NET 桥接路径需共同验证。
- poll：受检借用包装（例如 Python 仿照 `bytearray`，仍有导出视图时下一次读取抛出 `BufferError`），或直接导出裸缓冲/数组并约定到期使用属于调用者违规。推荐优先验证受检包装；若必须导出裸缓冲，要明确检查覆盖不到外部派生视图，不能承诺自动撤销或暗中复制延寿。
- 支持范围：精确列出 OS 发行版/版本、CPU 架构、Python 版本、原生库与 Windows .NET Framework 4.8 的组合，或分阶段增加组合。推荐只声明已取得证据的组合；精确列表仍待确认，不以 flake 环境或“最新 Linux LTS”替代。

最小可行性样例需要覆盖派生视图、下一次成功/失败读取、显式关闭、GC/终结器、push/写入缓冲固定与保活，以及 native 已成功后绑定失败。保留 Reader 引用不是对全部这些问题的答案；把全部旧分配永久保留也不是有界内存方案。

<a id="angle-14"></a>
### 角度 14：混合解释与部分矩阵

混合扫描范围明确暂缓。流组已能表达多组，但不能据此推定多模式共享 Frame 或位置；旧 Core profile 的同文件类别限制不作为产品永久边界（[DOC-01](DATA_SPEC.md#doc-01)）。恢复讨论时需要补充：

- 目标设备是否同时采集多种解释（例如 PA + TOFD、TFM/FMC + PA、单晶通道与阵列同时工作）？
- 多个独立运动的探头是否共用一个帧位置？若不共用，位置怎样按组绑定？（D-13）
- 是否需要 HMC、PWI、Sparse 等部分收发对或以法则/平面波为发射单元的矩阵？（D-14）
- 是否需要跨流组（异构）的 Tx×Rx 矩阵？首版一个矩阵限于单个流组（[ADR-0009](decisions/0009-review-contract-clarifications.md)）。（D-14）

适合提供的材料：设备的采集组配置示例，以及每组的位置来源。

关联 D-13/D-14、A-03；参考：MFMC v2.0.0 的 sequence 与发射/接收法则，Evident NDE 4.4 的 group 与 acquisitionPattern（FMC/HMC/PWI/Sparse）。

不预先推荐用“同 Scan 多流组”或同文件混存作为混合扫描答案；先明确实际组合及业务关联，再判断旧 Core 模型是否适用。部分矩阵仍按 D-14 单独讨论，不借 `valid=0` 冒充未采集的收发对。

## 5. 建议的选择顺序

当前按[业务细化入口](#business-next)推进；后续工程阶段再按[决策顺序](#decision-order)组织，不要求一次回答全部问题。应把工作分成三种结果：

1. **可以写回契约的决定**：例如必要关系、快照含义、代表规则与基础取值；位置异常接收方向已经确认；必须有适用范围和理由，不由实现默认值替代。
2. **需要 M1/M2 取证的机制候选**：例如参考写入保护机制、是否采用 SWMR 和绑定视图；可以形成候选协议，但没有运行证据前不宣称可行或关闭全部 D 项。
3. **明确后置的能力**：例如尚未定义的 Scan 映射、可选 GPU 及更多表示；需说明首发是否声明，不把未支持改记为 PASS。

机制取证 → 布局/生命周期编码 → 正式文件/API 冻结（遵循 API-01 的稳定原则）；真实 Frame 规模、资源目标和绑定验证并行反馈。不得按“先冻结所有编码、最后才验证失败机制”的顺序推进。

里程碑及证据状态以 [SPEC_TEST_PLAN.md](SPEC_TEST_PLAN.md#milestones) 为准，D 项的具体阶段依赖以 [DATA_SPEC 闭合表](DATA_SPEC.md#closure-gates) 为准。暂缓某一方向不表示该项已解决，也不阻止其他独立方向继续补充。
