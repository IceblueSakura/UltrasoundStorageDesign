# 超声采集文件：需求与架构决策

状态：逻辑架构已收敛；数据 Spec 为 `0.1-draft`，生产格式和参数未冻结。

本文只维护需求、边界和选择理由，不再重复字段表与完整接口不变量。数据契约的权威来源是 [DATA_SPEC.md](DATA_SPEC.md)，规则覆盖与验证方法见 [SPEC_TEST_PLAN.md](SPEC_TEST_PLAN.md)。下一轮从 [扫描场景与算法需求审计](SCENARIO_AUDIT.md)补充实际证据；历史 benchmark 的证据局限见 [BENCHMARK_REPORT.md](BENCHMARK_REPORT.md)，不作为当前选型结论。

## 1. 需求基线

编号用于关联 Spec 和测试，不表示这些能力已实现或已经验收。

| 编号 | 已确认需求/既有设计约束 |
|---|---|
| <a id="r-01"></a>R-01 | 一个连贯扫描 Session 对应一个独立、自解释原始文件；换探头、重装、重新标定、停止后继续、局部重扫或采样布局变化均新建文件 |
| <a id="r-02"></a>R-02 | 多通道共享同一次触发、共同记录轴，所有通道结构同构；初始化后固定采样布局 |
| <a id="r-03"></a>R-03 | 采集层组装完整记录及共享位置后提交；只做位置同步，不做时间同步，SDK 不组装逐通道到达数据 |
| <a id="r-04"></a>R-04 | SDK 支持波形与位置独立读取，以及绑定获得扫描时写入的位置；记录关联不能丢失 |
| <a id="r-05"></a>R-05 | 严格保存原始样本和调用者声明的状态，不隐式转换或按业务有效性丢弃；SDK 管结构合法性，不管成像判断 |
| <a id="r-06"></a>R-06 | 正常采集过载时以绝不丢数据为目标，允许阻塞写入；专门的背压协议暂不作为设计目标 |
| <a id="r-07"></a>R-07 | 实时显示走采集内存；普通文件读取在封存后进行，封存后原始文件只读 |
| <a id="r-08"></a>R-08 | 未正常关闭文件尽力只读恢复；不预设严格同步时间或最大损失时间界限，依据测试细化 |
| <a id="r-09"></a>R-09 | 单文件允许超过 100 GB、远超 RAM；T 在 u64 范围，无分卷需求 |
| <a id="r-10"></a>R-10 | 无损压缩用于降低采集磁盘流量和长期容量，允许第三方 filter；GPU 解压是期望的可选能力 |
| <a id="r-11"></a>R-11 | 固定解释、采集参数快照和辅助块职责分开，文件可独立解释；离线 overlay 不改写原始历史 |

## 2. 职责划分

```text
设备与采集层
  ├─ 组装同一触发的通道波形和共享位置
  ├─ 采集内存 → 实时显示
  └─ 阻塞提交完整记录/批次
          ↓
       SDK 单写者 → 单一 HDF5 文件
                         ├─ 正常封存 → 普通离线读取
                         └─ 异常结束 → 显式尽力只读恢复
```

SDK 负责存取、结构校验及记录关联，不做时间配准、位置插值、标定、包络、门指标或几何重建。位置对物理触发的同步准确性由采集层负责。

阻塞式单写者降低并发与缓冲复杂度，不引入无界异步队列。但阻塞调用并不证明设备可以无限暂存；端到端不丢数据仍需后续设备/缓冲契约。正常过载目标不等于断电后零损失。

## 3. 主要架构决策及理由

| 决策 | 理由与边界 | 数据契约入口 |
|---|---|---|
| HDF5 容器，公共容器/profile/物理布局分层 | 不将采集语义与 chunk、codec 等调优值绑定；不要求现在实现任意布局框架 | [ID-01](DATA_SPEC.md#id-01)、[MAP-01](DATA_SPEC.md#map-01) |
| 首版为常规同构通道，共享记录身份 | 对应设备与采集层已确认行为，不需要独立通道时间轴或 SDK 拼装 | [REC-01](DATA_SPEC.md#rec-01) |
| SPLIT 作为参考实现 | 每通道 `[T,S]` 访问直接，便于解释；不是证明全局最快或生产默认已冻结 | [MAP-01](DATA_SPEC.md#map-01) |
| 位置由记录身份绑定，独立于可选辅助反馈 | 避免依赖硬件不提供的时间同步；位置字段保持待定 | [POS-01](DATA_SPEC.md#pos-01)、[POS-02](DATA_SPEC.md#pos-02) |
| 完整记录提交、完整前缀、不修订历史 | 将波形、位置、状态和配置依赖保持在同一逻辑单元；不把它包装成 HDF5 事务 | [WRT-01](DATA_SPEC.md#wrt-01)、[WRT-02](DATA_SPEC.md#wrt-02) |
| 封存后读取，不做在线文件读取 | 实时显示已有采集内存路径，首版无需 SWMR 或跨进程发布协议 | [LIF-01](DATA_SPEC.md#lif-01) |
| 异常只读恢复 | 保留原始证据，避免自动修复或续写扩大损失；恢复范围由故障测试决定 | [LIF-02](DATA_SPEC.md#lif-02) |
| 分批访问、有界内存 | 文件远超 RAM，位置/状态等元数据也不能默认全量载入 | [CAP-01](DATA_SPEC.md#cap-01) |
| CPU 解码基础路径，GPU 解压可选 | GPU 完整编码链兼容性尚无证据，不应成为基本可读性的前提 | [CMP-01](DATA_SPEC.md#cmp-01)、[CMP-02](DATA_SPEC.md#cmp-02) |

CTS 保留为性能对照；TCS 在全通道输入/输出成本分析中仍可比较。候选布局并不是每个生产读取器都必须支持的集合。单通道查询权重尚未确认，不能为了让某布局更快而改变真实需求。

压缩重点候选为 Bitshuffle + LZ4、Blosc2 + Bitshuffle + LZ4 及低级别 Zstd，保留无压缩对照。最终选择由实际数据、I/O/CPU 预算与部署兼容性决定，而不是当前合成数据的单项排名。

### 3.1 下一轮需要验证的设计前提

现有约束继续作为审计基线，不因提出问题而自动撤销；若实际场景与其冲突，应显式修订需求、Spec 和测试，而不是在实现里加入例外。

- **Session 与轨迹**：先区分停止、短暂停顿、局部重扫和多文件任务；记录轴与位置绑定不等于扫描网格或空间邻接。
- **通道与测点**：共享采集位置不自动表示各通道的物理测点重合；需要核查通道身份、参考位置和必要几何解释是否充分。
- **算法输入**：先明确数值/采样轴、坐标系、参数历史、状态策略以及输出顺序，再决定是否需要单通道、全通道、门内或空间邻域读取。
- **运行边界**：实时算法走采集内存，文件算法面向封存或显式恢复视图；若实际需求要求增长文件读取，属于范围变更。
- **正确性与性能**：先用有独立期望值的小样例确认语义，再定义资源与延迟目标；SPLIT、压缩候选和 GPU 期望均不构成生产性能保证。

具体问题与设计细节索引集中在 [SCENARIO_AUDIT.md](SCENARIO_AUDIT.md)，不在这里维护第二份待定项清单。

## 4. 首版不包含的范围

- PA/FMC 的事件及张量语义；它们不能仅通过更换 shape 来定义。
- 独立通道流、异构或动态变长通道。
- Session 内 Segment、Round、RescanLink、重扫融合或完整重建模型。
- 分卷、多写者、在线文件读取、独立背压协议。
- SDK 等待缺通道、乱序组装和已提交记录的晚到补写。
- 自动修复/原地续写异常文件、严格断电零损失保证。
- overlay 加载与冲突合并；仅保留原始历史不覆盖的边界。

任务归组可由外部清单处理。辅助计划/反馈和记录位置不等于完整扫描拓扑，不能因此承诺自动生成 B/C/D 空间排列。
