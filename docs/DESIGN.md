## 设计基线与维护原则

当前设计语义、必要机制说明及验收素材均在项目文档内定义，按下列职责统一维护。

1. `DATA_SPEC.md` 是唯一活动数据契约；需求与架构理由在本文维护。访问规划、验证计划及将来的代码不能新增隐含规范，若发现矛盾须同步修订契约及相关文档。
2. 明确的逻辑语义与待定的编码、字段、API 和物理细节分开；不因历史实现已有写法或测试需要而提前确定生产格式。
3. H/P/F/W 和 UC 是本项目的语义样例与验收素材，不等于已经编写可执行用例。夹具标识、错误返回方式和实现建议不自动成为产品要求。
4. 未决内容统一登记到 D 项，验证只追踪本项目已定义的规则和用例，不维护外部附件编号或第二套验收依据。

本阶段完成的含义是：对象、身份、关联、不变量、替换关系和未决边界一致可追踪，足以指导下一阶段编写测试；不是生产格式冻结或运行验证通过。

## 1. 需求基线

编号用于关联 Spec 和测试，不表示这些能力已实现或已经验收。

| 编号 | 已确认需求/既有设计约束 |
|---|---|
| <a id="r-01"></a>R-01 | 一个文件代表一个工件的扫描集合，允许多个独立 Scan 表达分块扫描、复扫/精扫特定区域。换探头、重装、重新标定、停止后继续、局部重扫或采集定义变化均新建 Scan；同工件且满足类别限制时可留在未封存文件内。单晶与阵列仍不在同文件混存；短暂停顿与结束后重启的区分仍需场景证据 |
| <a id="r-02"></a>R-02 | 多通道单晶、常规 PA、FMC 共用核心类型和 Frame 轴；跨波形流异构合法，同一流的长度、dtype、样本表示及采样解释固定。Frame 表示一次逻辑完整采集，不泛化为一次物理发射或同一瞬间 |
| <a id="r-03"></a>R-03 | 采集层归组完整 Frame 及其关联后提交；SDK 不做时间配准、逐流等待拼装或晚到补写。单晶共同触发是具体采集约束，不泛化到 PA/FMC |
| <a id="r-04"></a>R-04 | SDK 支持波形与位置独立及绑定读取，保留 Frame、事件、接收输出、状态和固定定义关联；PA 声束及 FMC Tx/Rx 访问不能由调用者猜测 |
| <a id="r-05"></a>R-05 | 严格保存原始样本和调用者声明的状态，不隐式转换或按业务有效性丢弃；SDK 管结构合法性，不管成像判断 |
| <a id="r-06"></a>R-06 | 正常采集过载时以绝不丢数据为目标，允许阻塞写入；专门的背压协议暂不作为设计目标 |
| <a id="r-07"></a>R-07 | 实时显示走采集内存；普通文件读取在封存后进行，封存后原始文件只读 |
| <a id="r-08"></a>R-08 | 未正常关闭文件尽力只读恢复；不预设严格同步时间或最大损失时间界限，依据测试细化 |
| <a id="r-09"></a>R-09 | 单文件允许超过 100 GB、远超 RAM；每个 Scan 的 Frame 数量 N 在 u64 范围，无分卷需求，不建立隐含的全文件 Frame 轴 |
| <a id="r-10"></a>R-10 | 无损压缩用于降低采集磁盘流量和长期容量，允许第三方 filter；GPU 解压是期望的可选能力 |
| <a id="r-11"></a>R-11 | Scan、事件、流的采集设置分别固定，每份定义保存一次；不要求逐帧参数快照或 config_index。观测位置、波形和状态可变化；派生结果与辅助块不改写原始历史 |
| <a id="r-12"></a>R-12 | 多 Scan 服务于分块扫描工件、复扫/精扫特定区域；原始结果并存，不自动拼接、融合或替代旧结果。每个 Scan 的区域、来源及坐标映射关系均待决策，不仅是编码待定；工件容器不等于完整覆盖证明 |

## 2. 职责划分

```text
设备与采集层
  ├─ 按固定采集方案归组完整 Frame、各流波形及原始关联
  ├─ 采集内存 → 实时显示
  └─ 阻塞提交完整 Frame/批次
          ↓
       SDK 单写者 → 单一 HDF5 工件文件
                         ├─ 顺序写入：Scan A 完成 → Scan B 完成 → …
                         ├─ 文件正常封存 → 普通离线读取
                         └─ 异常结束 → 显式尽力只读恢复，逐 Scan 报告
```

SDK 负责存取、结构校验及 Frame/事件/接收输出关联，不做时间配准、位置插值、标定、包络、门指标、聚焦或几何重建。帧级原始位置的采集准确性由采集层负责；共同 Frame 轴不证明物理同步或完成运动校正。

阻塞式单写者降低并发与缓冲复杂度，不引入无界异步队列。但阻塞调用并不证明设备可以无限暂存；端到端不丢数据仍需后续设备/缓冲契约。正常过载目标不等于断电后零损失。

## 3. 主要架构决策及理由

| 决策 | 理由与边界 | 数据契约入口 |
|---|---|---|
| 固定 HDF5 2.x，一套公共 schema | 不再做后端选型；采集语义与物理布局分离，模式通过必要语义区分而非 shape 猜测 | [ID-01](DATA_SPEC.md#id-01)、[MAP-01](DATA_SPEC.md#map-01) |
| 文件为工件容器，Scan 为独立采集单元 | 分块及复扫/精扫可一起交付；每个 Scan 仍有固定定义、局部 Frame 轴和独立前缀，不将多次扫描拼成动态配置的大 Scan | [SCAN-01](DATA_SPEC.md#scan-01) |
| 多 Scan 结果并存，映射关系后置 | 先支持工件容器和独立扫描；区域/来源/坐标关系的模型及约束待定，不因应用目标预设字段或映射，也不自动融合 | [SCAN-01](DATA_SPEC.md#scan-01)、[SCAN-02](DATA_SPEC.md#scan-02) |
| 三个主体定义及一个 Frame 组合记录 | Scan、EventDefinition、WaveformStream 职责明确，不新增三套模式专属主体；采集层归组 | [逻辑模型](DATA_SPEC.md#logical-model)、[REC-01](DATA_SPEC.md#rec-01) |
| 流间异构、流内固定 | 保留设备原始表示；不能为了稠密数组而隐式转换。同一硬件接收通道在不同事件下可对应不同流 | [WAV-01](DATA_SPEC.md#wav-01)、[WAV-02](DATA_SPEC.md#wav-02) |
| 扫描/事件/流固定定义保存一次 | 固定程序重复执行不产生参数历史；真实定义变化新建 Scan，不要求整个文件共用定义 | [PAR-01](DATA_SPEC.md#par-01) |
| PA 一帧一个原始映射位置 | 声束空间解释来自位置、固定几何与法则；不要求逐束新增采集位置，也不覆盖原始位置 | [POS-01](DATA_SPEC.md#pos-01)、[PA-01](DATA_SPEC.md#pa-01) |
| FMC 显式矩阵语义与共享来源 | 流视图与 Tx/Rx 矩阵视图等价；同构可稠密，异构保留单元表示，互易对独立 | [FMC-01](DATA_SPEC.md#fmc-01)、[FMC-02](DATA_SPEC.md#fmc-02) |
| 物理布局后置 | 逻辑流不必对应一个 dataset，Frame 不必对应一个 group；旧 SPLIT 只是历史参考 | [MAP-01](DATA_SPEC.md#map-01) |
| 完整 Frame 提交、完整前缀、不修订历史 | 波形、状态、位置和固定定义依赖保持一致；不把逻辑闭合包装成 HDF5 事务 | [WRT-01](DATA_SPEC.md#wrt-01)、[WRT-02](DATA_SPEC.md#wrt-02) |
| 封存后读取，不做在线文件读取 | 实时显示已有采集内存路径，首版无需 SWMR 或跨进程发布协议 | [LIF-01](DATA_SPEC.md#lif-01) |
| 异常只读恢复 | 保留原始证据，避免自动修复或续写扩大损失；恢复范围由故障测试决定 | [LIF-02](DATA_SPEC.md#lif-02) |
| 分批访问、有界内存 | 文件远超 RAM，位置/状态等元数据也不能默认全量载入 | [CAP-01](DATA_SPEC.md#cap-01) |
| CPU 解码基础路径，GPU 解压可选 | GPU 完整编码链兼容性尚无证据，不应成为基本可读性的前提 | [CMP-01](DATA_SPEC.md#cmp-01)、[CMP-02](DATA_SPEC.md#cmp-02) |

SPLIT/CTS/TCS 可在适用的同构工作负载中作为后续物理实验对照，不是公共 schema 的强制组织，也不是每个生产读取器都必须支持的集合。访问频率尚未确认，不能为了让某布局更快而改变数据含义。

Bitshuffle + LZ4、Blosc2 + Bitshuffle + LZ4 及低级别 Zstd 仅是可探索的压缩候选，不作为本轮选型优先级或测试前提。布局、压缩参数及缓存全部暂缓；后续选择由真实工作负载与部署证据驱动。

### 3.1 本轮逻辑收敛与尚未验证的边界

v0.2 已替换同构共同触发、动态快照以及排除 PA/FMC 的旧前提。其余边界继续保留；若实际场景与新契约冲突，应显式修订需求、Spec 和测试，而不是在实现里加入例外。

本次进一步用“一个工件文件包含多个独立 Scan”替换原一文件一扫描限制。多 Scan 扩展不改变封存后只读、同文件类别限制或不自动融合的范围；文件未封存时顺序创建 Scan，已完成 Scan 不再追加。跨 Scan 数据共用物理文件，不获得 HDF5 group 级故障隔离保证。

- **Scan 与轨迹**：分块/复扫/精扫以独立 Scan 承载；每个 Scan 的映射关系（含区域、来源和坐标模型）保持待决策，撤回上一轮提前设定的关系约束。短暂停顿仍需场景证据，Frame 轴不等于空间邻接或实际覆盖。
- **输出与测点**：接收阵元、合成输出、硬件通道和声束身份分开；共享帧位置不表示各输出的物理测点重合。
- **算法输入**：Frame/Stream、PA 声束、FMC 矩阵选择已形成逻辑基线；实际采样解释、坐标编码、状态策略、请求频率及资源目标仍需证据。
- **运行边界**：实时算法走采集内存，文件算法面向封存或显式恢复视图；若实际需求要求增长文件读取，属于范围变更。
- **正确性与性能**：先用有独立期望值的小样例确认语义，再定义资源与延迟目标；SPLIT、压缩候选和 GPU 期望均不构成生产性能保证。

具体问题与设计细节索引集中在 [SCENARIO_AUDIT.md](SCENARIO_AUDIT.md)，不在这里维护第二份待定项清单。

## 4. 首版不包含的范围

- PA 与 FMC 的同文件组合采集方案；这是当前不覆盖，不是硬件上的必然禁令。
- 独立通道时间轴、同一流动态变长或采集定义在同一 Scan 内变更。
- Scan 内 Segment/Round、跨 Scan 自动拼接、重扫融合、结果替代优先级或完整重建模型；Scan 间映射/来源关系另列 D-11 待决策，不当作已确定能力。
- 分卷、多写者、在线文件读取、独立背压协议。
- SDK 等待缺通道、乱序组装和已提交记录的晚到补写。
- 自动修复/原地续写异常文件、严格断电零损失保证。
- 已封存文件重新打开追加 Scan、多个活动 Scan 交错追加、跨 Scan 固定定义去重。
- overlay 加载与冲突合并；仅保留原始历史不覆盖的边界。

同工件的文件内扫描归组由工件容器承担，跨文件任务可由外部清单处理。区域、来源关系、辅助计划/反馈和记录位置不等于完整扫描拓扑，不能因此承诺自动生成 B/C/D 空间排列。
