## 设计基线与维护原则

当前设计语义、必要机制说明及验收素材均在项目文档内定义，按下列职责统一维护。

1. `DATA_SPEC.md` 是唯一活动数据契约；需求与架构理由在本文维护。访问规划、验证计划及将来的代码不能新增隐含规范，若发现矛盾须同步修订契约及相关文档。
2. 明确的逻辑语义与待定的编码、字段、API 和物理细节分开；不因历史实现已有写法或测试需要而提前确定生产格式。
3. H/P/F/W 和 UC 是本项目的语义样例与验收素材，不等于已经编写可执行用例。夹具标识、错误返回方式和实现建议不自动成为产品要求。
4. 未决内容统一登记到 D 项，验证只追踪本项目已定义的规则和用例，不维护外部附件编号或第二套验收依据。

本阶段确认产品范围、数据含义和责任边界，保留明确未决项；不是完整数据模型、首发范围、格式/API 或实现定版。本次从 UMS 已确认决策同步，冲突以该业务基线为准；落地后本仓库维护 SDK 权威规格，UMS 保留产品需求与接入约束，不维护第二套 SDK 细节。

### 本次收束结论与后续约束

产品限定为超声数据专用的规范化存取库，包含 schema 和读写能力，独立维护并开源，以功能单一为约束。不承载设备/任务流程、复杂处理、点云、标注/缺陷成果或额外导出；完整边界由 DATA_SPEC 的 BUS-01～MEAS-01 定义。当前先细化业务含义，不规划许可证、实现方案或 API 定版。

| 层次 | 当前结论 | 不代表什么 |
|---|---|---|
| 业务基线 | 超声范围、必要解释与关系、三种保留模式、快照、基础取值及子集访问已确认 | 混合范围、具体关系/取值/选择与快照组织仍开放 |
| 既有工程合同 | HDF5、流组/Frame、poll/push、写入保护等保留在适用的原始波形 Core 路径 | 不把旧模型直接套到仅特征或混合扫描，不因本次同步重新批准全部旧选择 |
| 实现验收 | 尚无 SDK 与产品级用例；仅有 M1 test-only 实验证据 | 文档检查通过不等于产品测试通过 |

原始事实不变及快照写失败保护是业务要求；具体机制属于后续工程设计。既有实验及技术取证只保留原适用范围，不用于证明新增快照、仅特征或基础取值已经可用。本次不重跑 SDK 的代码、测试、实验或 benchmark。

待决策问题、选项及推荐方向集中在 [DECISION_DIRECTIONS.md](DECISION_DIRECTIONS.md#decision-order)，推荐均未自动采纳；正式 D 项与阶段依赖只在 [DATA_SPEC](DATA_SPEC.md#closure-gates) 维护。必要关系模型仍待 D-11，混合扫描仍待 D-13，快照/代表访问/取值细节见 D-16～D-18；GPU 解压仍为可选。仅完成旧 Core 路径不能宣称完整产品需求通过，也不能以缩小 profile 静默删除已确认能力。

<a id="core-scope"></a>
### 产品边界与既有 Core 设计

SDK 只面向超声数据的规范存取、必要关系、基础窗口取值及规范子集访问。模式参数仅解释已有数据，不承担扫描复现；曲面仅承载必要解释几何。C 扫快照在范围内，标注和缺陷分析成果仍归 UMS。布局规划用于存取优化，不限制其它布局支持。具体规则归 [业务边界](DATA_SPEC.md#bus-01)，不是 HDF5 自带的 schema。Core 与扩展如何划分继续随需求设计，不沿用“只做 Core”排除上述产品责任。

以下列出保留的工程方向及本次范围修订；未冲突的决定不自动撤销，但不作为当前必须讨论或冻结的实现细节：

| 决定 | 理由与剩余边界 |
|---|---|
| 必要公共描述与模式专属 schema | SDK 负责解释已有数据所需信息；单探头/相控阵 schema 明确可辨识，具体内容待 D-09；不能以透传任意元信息代替解释责任 |
| 同构流组（ADR-0001） | 组内 dtype、样本数、样本表示与采样间隔一致，逐流差异以流表保存；通道组/PA 声束集/Tx×Rx 矩阵是组的解释。异构只在组间发生，单条特殊流可独占一组 |
| 位置及其状态与波形分别解释 | 无空间位置记录合法；位置异常仍保全有效波形。旧 Core 的帧级关联模型保留，混合扫描不自动共享位置；不做坐标转换 |
| poll/push 两种同步读取缓冲模型 | poll 借用 SDK 管理的只读内存，至同一 Reader 下一次样本读取开始或 Reader 关闭（ADR-0004）；push 同步复制到调用者指定缓冲，由调用者管理。写入仍同步消费调用者输入，不承诺直接磁盘指针或全链路零拷贝 |
| 同步单 Frame／Frame 批次写入，无写入取消 | 普通写入不要求立即落盘；显式 Flush 的成功后条件、写失败态、提交记录与校验值见 ADR-0002；只覆盖进程崩溃，断电与操作系统崩溃不作保证（ADR-0008）；机制取证仍待 D-05 |
| 单一有效性位图＋无效槽位零填充 | 仅在原始波形槽位层使用该规则，不替代 RET-01 的保留、缺口与特征状态；写入时须显式提交完整位图（ADR-0003），有效样本原样保存，无效槽位不保留输入内容。位图与样本一起交付，真实全 0 与无效零填充可区分；具体打包和 API 待定 |
| 两种内容交付：随元信息返回、Batch 消费 | 常规分析关联元信息；GPU 消费按 Batch 读取多个 Frame。用途与 poll/push 所有权分别定义，不相互绑定；不自动恢复任意 Frame 清单语法 |
| 原始 Core I/O 与纯选择层保留，产品访问按业务细化 | 旧工程划分不等于 ACCESS-01 的顶层代表/底层来源访问；优先布局与访问场景待 D-03/D-17，不预定 Frame/Batch 永远优先 |
| 每次数据读写调用强原子，失败给出原因/错误码 | push 读失败目标不变；poll 失败不发布部分新结果，旧借用期已在本次读开始时结束；写失败无新增提交，已提交数据不被修改且可由校验值观察，Writer 进入失败态。不是崩溃事务；参考机制见 DATA_SPEC MAP-02 |
| 读取不更新原始事实，指定快照允许后续写入 | 相同数据与条件下等价读取一致；快照新增/替换及失败保护按 SNAP-01，不等于覆盖文件或原始 Scan 续写 |
| 进程内全局串行化，多 Reader、已封存文件多进程只读（ADR-0004） | 同一对象不得并发调用，不承诺对象级线程安全；一个文件只有一个 Writer，写入期间无其他读者，由 SDK 检测并拒绝（ADR-0009） |
| 目标平台为最新 Linux LTS、Windows 10+ | 本阶段只在 Linux 上设计与验证，Windows 在草案基本确定后测试；公开 API 不得预先排除 Windows/.NET 的约束。Linux 的具体发行版及版本基线待确认；本阶段不规划部署方案 |
| API 稳定原则保留供后续工程设计（ADR-0010），当前不定版 | 原生库唯一的稳定边界是 C ABI，长度 64 位、缓冲以“指针＋字节长度”描述，参数可扩展且带预留标志，错误码与提交状态稳定（[API-01](DATA_SPEC.md#api-01)）；物理持久化只覆盖进程崩溃，布局、codec 与写入保护机制可以在不改公开 API 的前提下调整。版本与兼容规则见[决策入口角度 16](DECISION_DIRECTIONS.md#angle-16) |
| 保留 Python、.NET Framework 4.8 目标，并满足 UMS .NET 10/Windows/Linux x64 消费需求 | 功能集中，便于使用 pybind11 等成熟绑定工具；pybind11 是 Python 候选路径，不解决 .NET 绑定；原生稳定边界为 C ABI（ADR-0010），实现语言与绑定方式仍未冻结；.NET Framework 4.8 消费端面向 Windows |
| 库为 HDF5 2.x，写出文件限定 1.10–1.14 可读格式（ADR-0005） | 第三方工具仍可能链接 1.x；不使用 2.0 专有特性，复数采用复合类型约定 |

本轮不启动 SDK 产品实现或物理参数调优；`experiments/m1/` 只是验证机制与契约的 test-only 原型。有效性位图打包/接口、Batch 布局/选择、原子性与 Flush 的正式机制仍未闭合；波形槽位有效性和零填充语义保留；成果保留状态、位置状态及特征状态不能压缩成同一位。原子性与 Flush 的后条件已定，不以同步调用或一次错误返回代替实现证据。平台/语言剩余决定登记在 D-12。

## 1. 需求基线

编号用于关联 Spec 和测试，不表示这些能力已实现或已经验收。

| 编号 | 已确认需求/既有设计约束 |
|---|---|
| <a id="r-01"></a>R-01 | 既有 Core 以工件容器关联独立 Scan，原始结果不覆盖。产品承载必要数据关系；Run/Scan/工件/文件具体映射待 D-11，混合范围待 D-13，不把旧同文件类别限制当作最终产品边界 |
| <a id="r-02"></a>R-02 | 多通道单晶、常规 PA、FMC 共用核心类型和 Frame 轴；流按同构流组组织，跨组异构合法，同一流组的长度、dtype、样本表示及采样解释固定。Frame 表示一次逻辑完整采集，不泛化为一次物理发射或同一瞬间 |
| <a id="r-03"></a>R-03 | 采集层归组完整 Frame 及其关联后提交；SDK 不做时间配准、逐流等待拼装或晚到补写。单晶共同触发是具体采集约束，不泛化到 PA/FMC |
| <a id="r-04"></a>R-04 | SDK 按索引提供分析/Batch 内容交付，并支持 poll 借用只读视图与 push 复制到调用者缓冲；保留状态及关联；产品增加 ACCESS-01 的分层/子集访问和 MEAS-01 的基础取值，不预定任意坐标搜索；读取不更新，指定快照写入另按 SNAP-01 |
| <a id="r-05"></a>R-05 | 每个波形槽位一个有效性位，写入时由调用者显式提交完整位图（存储初值为无效）；标记有效且通过结构校验的样本视为合法并无损保存，包括真实全 0。无效槽位零填充，不要求提供或保留其输入样本；不再独立区分 payload 存在性与业务有效性。SDK 管结构合法性，不作业务合法性或成像判断 |
| <a id="r-06"></a>R-06 | 调用者维持缓冲，同步单 Frame／Frame 批次写入允许阻塞、不提供取消；普通写入不要求立即落盘，显式 Flush 成功后，已写数据在之后任意时刻的进程崩溃后可恢复（断电与操作系统崩溃不作保证）；Core 不负责设备背压、缺失补全或端到端采集不丢数据保证 |
| <a id="r-07"></a>R-07 | 实时显示走采集内存；原始采集事实封存后不改写，但允许重开后新增/替换指定 C 扫快照 |
| <a id="r-08"></a>R-08 | 未正常关闭文件尽力只读恢复，不改源文件；不预设最大损失时间界限，但不免除 Flush 成功后条件 |
| <a id="r-09"></a>R-09 | 单文件允许超过 100 GB、远超 RAM；每个 Scan 的 Frame 数量 N 在 u64 范围，无分卷需求，不建立隐含的全文件 Frame 轴 |
| <a id="r-10"></a>R-10 | 无损压缩用于降低采集磁盘流量和长期容量，允许第三方 filter；GPU 解压是期望的可选能力 |
| <a id="r-11"></a>R-11 | Scan、事件、流组的采集设置分别固定，每份定义保存一次（逐流差异以组内流表保存）；不要求逐帧参数快照或 config_index。观测位置、波形和状态可变化；派生结果与辅助块不改写原始历史 |
| <a id="r-12"></a>R-12 | 多 Scan 原始结果并存，不自动拼接、融合或替代。扫描关联目标区域、复检/局部重扫能指向原扫描具体区域已定；区域内容及关系模型待 D-11。对象归属未追加为产品必需关系，旧工件容器不等于完整覆盖证明 |
| <a id="r-13"></a>R-13 | SDK 维护模式专属 schema、自包含解释和必要关系，具体内容按 REL-01/D-09/D-11 细化；不依赖未来 Extensions 才承认这项产品责任 |
| <a id="r-14"></a>R-14 | 进程内 HDF5 调用全局串行化，同一对象不并发调用；多个 Reader 借用独立，已封存文件可多进程只读，一个文件一个 Writer；平台、语言支持目标及偏好见 Core 范围，精确支持矩阵待 D-12 |
| <a id="r-15"></a>R-15 | 每次数据读写调用失败报告原因/错误码：push 目标不变；poll 不发布部分新结果且不延长旧借用期；写失败无新增提交、已提交数据不被修改，Writer 进入失败态。不是崩溃事务，机制待验证 |
| <a id="r-16"></a>R-16 | 全波、仅特征与混合保留均合法；必要解释、保留状态、缺口及有效性分别表达，见 RET-01/POS-01 |
| <a id="r-17"></a>R-17 | C 扫快照的存取、新增/指定替换、重开后保存及失败保护，见 SNAP-01；不纳入标注/缺陷成果 |
| <a id="r-18"></a>R-18 | 顶层代表与底层 0～N 原始来源访问、布局优化与规范子集访问，见 ACCESS-01；具体规则待 D-17 |
| <a id="r-19"></a>R-19 | 文件输入的明确窗口内基础幅值与位置/时间取值，区域逐点数值与状态，见 MEAS-01；不做转换、复杂分析或额外导出 |

## 2. 职责划分

```text
设备与采集层
  ├─ 按固定采集方案归组完整 Frame、各流波形及原始关联
  ├─ 采集内存 → 实时显示
  └─ 同步提交结构闭合的 Frame/批次及波形有效性位图
          ↓
       SDK 单写者 → 单一 HDF5 工件文件
                         ├─ 顺序写入：Scan A 完成 → Scan B 完成 → …
                         ├─ 文件正常封存 → 普通离线读取
                         └─ 异常结束 → 显式尽力只读恢复，逐 Scan 报告
```

上图只表达原始采集路径，不是仅特征或快照写入的强制流程。SDK 负责规范存取、结构关联、必要模式解释及限定的基础取值；不做缺失补全、设备协议解码、时间配准、位置插值、标定、包络、完整闸门分析、聚焦或几何重建。文件自身必要的类型和编码仍须有明确约定，不将这些存储描述等同于设备数据处理。帧级原始位置的采集准确性由采集层负责；共同 Frame 轴不证明物理同步或完成运动校正。

无效波形槽位的零填充是存储表示，不是补采或推算真实信号。SDK 接受调用者的有效性声明，但仍检查有效波形是否提供、dtype/长度、容量、身份和引用；文件损坏及 I/O 错误不能改成无效位来掩盖。此决定简化初版状态模型，取代原“有 payload 但业务无效仍保留样本”的要求；正式逻辑契约见 STA-01。

同步式单写者降低并发与缓冲复杂度，不引入无界异步队列。设备缓存和归组策略属于调用方，不作为 Core 必须设计的协议；其输入规模、速率可作为以后存储负载验收的依据。阻塞调用不证明设备可以无限暂存，也不等于断电后零损失。

## 3. 主要架构决策及理由

| 决策 | 理由与边界 | 数据契约入口 |
|---|---|---|
| HDF5 2.x 库、1.10–1.14 文件格式，一套公共 schema | 不再做后端选型；采集语义与物理布局分离，模式通过必要语义区分而非 shape 猜测；写出格式让 1.x 工具可读 | [ID-01](DATA_SPEC.md#id-01)、[MAP-01](DATA_SPEC.md#map-01) |
| 超声专用产品，内部 Core/扩展划分后续细化 | 模式解释和 C 扫快照是产品责任，不扩展为通用派生成果平台 | [CORE-01](DATA_SPEC.md#core-01)、[META-01](DATA_SPEC.md#meta-01) |
| 既有 Core 的文件工件容器，Scan 为独立采集单元 | 分块及复扫/精扫可一起交付；每个 Scan 仍有固定定义、局部 Frame 轴和独立前缀，不将多次扫描拼成动态配置的大 Scan | [SCAN-01](DATA_SPEC.md#scan-01) |
| 多 Scan 结果并存，映射关系后置 | 先支持工件容器和独立扫描；区域/来源/坐标关系的模型及约束待定，不因应用目标预设字段或映射，也不自动融合 | [SCAN-01](DATA_SPEC.md#scan-01)、[SCAN-02](DATA_SPEC.md#scan-02) |
| 三个主体定义、流组及一个 Frame 组合记录 | Scan、EventDefinition、WaveformStream 职责明确，同构流组承载共享表示与组解释，不新增三套模式专属主体；采集层归组 | [逻辑模型](DATA_SPEC.md#logical-model)、[REC-01](DATA_SPEC.md#rec-01) |
| 组间异构、组内固定 | 保留设备原始表示；组内天然稠密，跨组不为稠密数组隐式转换。同一硬件接收通道在不同事件下可对应不同流 | [WAV-01](DATA_SPEC.md#wav-01)、[WAV-02](DATA_SPEC.md#wav-02) |
| 单一波形有效性位图，无效零填充 | 波形槽位规则不代替 RET-01 的保留和质量状态；以位图区分真实零波形和填充值，有效样本保真，不承诺保存无效输入内容 | [STA-01](DATA_SPEC.md#sta-01)、[WAV-02](DATA_SPEC.md#wav-02) |
| 扫描/事件/流组固定定义保存一次 | 固定程序重复执行不产生参数历史；真实定义变化新建 Scan，不要求整个文件共用定义 | [PAR-01](DATA_SPEC.md#par-01) |
| PA 一帧共用一份位置，其他内容以帧级附加记录关联 | 不逐束重复位置；实际反馈与理论坐标等保持独立来源，不计算变换或覆盖原始位置 | [POS-01/02](DATA_SPEC.md#pos-01)、[PA-01](DATA_SPEC.md#pa-01) |
| FMC 显式矩阵语义与共享来源 | 流视图与 Tx/Rx 矩阵视图等价；同构可稠密，异构保留单元表示，互易对独立 | [FMC-01](DATA_SPEC.md#fmc-01)、[FMC-02](DATA_SPEC.md#fmc-02) |
| 物理布局后置 | 逻辑流不必对应一个 dataset，Frame 不必对应一个 group；旧 SPLIT 只是历史参考 | [MAP-01](DATA_SPEC.md#map-01) |
| 完整 Frame 提交、提交记录、不修订历史 | 提交记录是可见范围的唯一依据，物理块带校验值；不把逻辑闭合包装成 HDF5 事务，HDF5 重写块时可能原地覆写或复用空间 | [WRT-01](DATA_SPEC.md#wrt-01)、[WRT-02](DATA_SPEC.md#wrt-02) |
| 封存后读取，不做在线文件读取 | 实时显示已有采集内存路径，无需跨进程发布协议；SWMR 只可能作为写入保护的内部机制（MAP-02），不开放增长文件读取 | [LIF-01](DATA_SPEC.md#lif-01) |
| 异常只读恢复 | 保留原始证据，避免自动修复或续写扩大损失；状态标志只在副本上清除，建议独立进程执行 | [LIF-02](DATA_SPEC.md#lif-02) |
| 原始 Core 的 Frame/Batch、poll/push、有界内存 | 常规分析与 GPU 上传共享来源；poll SDK 缓冲与 push 调用者缓冲分别管理，单 Frame 不分块，不要求全扫描驻内存 | [READ-01/03](DATA_SPEC.md#read-01)、[BUF-01](DATA_SPEC.md#buf-01)、[CAP-01](DATA_SPEC.md#cap-01) |
| 显式 Flush 与调用级原子失败 | 普通写入与 Flush 分开；进程崩溃保护来自含已提交数据的块不再重写，Flush 只需把数据交给操作系统，不要求 fsync（ADR-0008）；错误不能只统一返回码而留下未说明的部分成功 | [WRT-03](DATA_SPEC.md#wrt-03)、[IO-01](DATA_SPEC.md#io-01) |
| CPU 解码基础路径，GPU 解压可选 | GPU 完整编码链兼容性尚无证据，不应成为基本可读性的前提 | [CMP-01](DATA_SPEC.md#cmp-01)、[CMP-02](DATA_SPEC.md#cmp-02) |

SPLIT/CTS/TCS 可在适用的同构工作负载中作为后续物理实验对照，不是公共 schema 的强制组织。连续批量写入、Frame 随机读、GPU 上传前的 Batch 读取和 A-Scan 随机读是既有候选负载；产品的优化优先级、比例、尺寸与指标待实际场景确认。本阶段不调优，不为布局改变数据含义；主机只读指针不等于 GPU 内存、零拷贝或 GPU 解压。

Bitshuffle + LZ4、Blosc2 + Bitshuffle + LZ4 及低级别 Zstd 仅是可探索的压缩候选，不作为本轮选型优先级或测试前提。压缩率不是本阶段的设计或验收指标，此前的压缩测试只用于选型。布局、压缩参数及缓存全部暂缓；后续选择由真实工作负载与部署证据驱动。

### 3.1 本轮逻辑收敛与尚未验证的边界

0.2 起已替换同构共同触发、动态快照以及排除 PA/FMC 的旧前提。其余边界继续保留；若实际场景与新契约冲突，应显式修订需求、Spec 和测试，而不是在实现里加入例外。

既有 Core 的工件容器及多 Scan 模型保留，不强制成为全部 UMS 成果的映射。原始 Scan 不再追加、不自动融合的限制保留；整个文件封存后不可更新已改为 SNAP-01 的指定快照写入边界。同文件类别限制仅适用于旧 Core profile，混合扫描继续待定。

- **Scan 与轨迹**：分块/复扫/精扫以独立 Scan 承载；每个 Scan 的映射关系（含区域、来源和坐标模型）保持待决策，撤回上一轮提前设定的关系约束。短暂停顿仍需场景证据，Frame 轴不等于空间邻接或实际覆盖。
- **输出与测点**：接收阵元、合成输出、硬件通道和声束身份分开；共享帧位置不表示各输出的物理测点重合。
- **存储消费**：保留帧内流/束/FMC 选择及 Batch 多 Frame 读取；本轮将“全部读取由调用者持有缓冲”修订为 poll/push 双模型，不做单 Frame 内分块。数据随单一有效性位图返回，无效槽位零填充；位图/数据布局及失败保证的机制继续讨论。
- **运行边界**：实时算法走采集内存，文件算法面向封存或显式恢复视图；若实际需求要求增长文件读取，属于范围变更。
- **正确性与性能**：先用有独立期望值的小样例确认语义，再定义资源与延迟目标；SPLIT、压缩候选和 GPU 期望均不构成生产性能保证。

具体问题与设计细节索引集中在 [SCENARIO_AUDIT.md](SCENARIO_AUDIT.md)，不在这里维护第二份待定项清单。

## 4. 首版不包含的范围

- 完整任务/文件集合管理、通用派生成果平台和 Extensions 框架；不排除已确认的模式 schema、必要关系及 C 扫快照。
- 按位置查询或其他非索引匹配；后续匹配能力与位置 schema 一起规划。Batch 读取已纳入，不自动承诺任意离散 Frame 清单语法。
- 原始 Core 的单 Frame 内分块交付、写入取消及读取时更新；指定快照写入不在此排除范围；不把批次指针交付扩为 GPU 上传调度或 GPU 内存管理。
- 对象级线程安全、写入期间的读者、部署打包方案；本阶段不做 chunk/codec/cache 等细节调优。
- 混合扫描及 HMC/PWI/Sparse 等扩展模式的具体范围（D-13/D-14）尚未确定；旧 profile 限制不是产品永久排除，也不是已支持声明。
- 独立通道时间轴、同一流动态变长或采集定义在同一 Scan 内变更。
- Scan 内 Segment/Round、跨 Scan 自动拼接、重扫融合、结果替代优先级或完整重建模型；Scan 间映射/来源关系另列 D-11 待决策，不当作已确定能力。
- 分卷、多写者、在线文件读取、独立背压协议。
- SDK 等待缺通道、乱序组装和已提交记录的晚到补写。
- 原始波形槽位的双位状态及无效输入样本原样保留仍非当前 Core 要求；但 RET-01 的未保留、缺测、无效与有效零值须分别表达，不增加 SDK 业务合法性判断。
- 自动修复/原地续写异常文件；断电、操作系统崩溃与存储设备故障后的恢复保证（ADR-0008）。
- 已封存文件重新打开追加 Scan、多个活动 Scan 交错追加、跨 Scan 固定定义去重。
- 通用 overlay 加载与冲突合并、标注/缺陷成果、激光点云、额外导出与成果打包；指定 C 扫快照不属于这些排除项。

同工件的文件内扫描归组由工件容器承担，跨文件任务可由外部清单处理。区域、来源关系、辅助计划/反馈和记录位置不等于完整扫描拓扑，不能因此承诺自动生成 B/C/D 空间排列。
