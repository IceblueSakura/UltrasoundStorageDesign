# 扫描场景与算法需求审计

状态：**测试用例编写前的设计整合，实际设备/算法证据仍待补充**。本文只保留未确认场景问题，不维护第二套 schema，也不是算法实现或审计通过报告。本次不编写或执行测试，文档职责按 [设计维护原则](DESIGN.md#integration-policy)划分。

需求与选择理由以 [DESIGN.md](DESIGN.md) 为准，语义和不变量以 [DATA_SPEC.md](DATA_SPEC.md) 为准，待定项只在其 [D-01～D-11 登记表](DATA_SPEC.md#open-items)维护。本文 A 编号是讨论主题，不是需求；访问选择见 [ACCESS_USE_CASE_PLAN.md](ACCESS_USE_CASE_PLAN.md)，独立样例及执行状态见 [SPEC_TEST_PLAN.md](SPEC_TEST_PLAN.md)。

## 1. 本轮要回答什么

按“实际动作 → 设备交付 → 记录含义 → 算法输入 → 文件访问”的顺序核查：

1. 实际设备能否交付符合固定方案的完整 Frame，事件/接收输出身份来自哪里？
2. 各设备的样本表示、采样轴、位置参考对象和固定几何如何在离线时独立解释？
3. 实际算法需要多大的数据块、何种采样解释和外部模型，如何分批消费？
4. 哪些运行协议、资源目标或范围冲突仍需要证据，而非由小样例或历史性能猜测？

先确认上述语义，再讨论布局、chunk、压缩和 GPU。历史脚本中的 C/S/dtype、规则网格和单通道负载均不得作为答案。

已经收敛、无需重复作为开放问题的事项：核心类型及 Frame 身份见 [逻辑模型](DATA_SPEC.md#logical-model)；流间异构/流内固定见 [WAV-01](DATA_SPEC.md#wav-01)；固定参数见 [PAR-01](DATA_SPEC.md#par-01)；PA 唯一帧位置见 [PA-01](DATA_SPEC.md#pa-01)；FMC 矩阵语义见 [FMC-01](DATA_SPEC.md#fmc-01)、[FMC-02](DATA_SPEC.md#fmc-02)。实际设备不符合这些规则时，记录范围冲突，不在实现中偷偷加入例外。

一个工件文件允许多个独立 Scan 承载分块/复扫/精扫，不自动融合，见 [SCAN-01](DATA_SPEC.md#scan-01)。多 Scan 容器已确定；每个 Scan 的区域、来源和坐标映射关系连同模型及必要性仍待 [SCAN-02/D-11](DATA_SPEC.md#scan-02) 决策，不仅是字段编码。调查不再询问是否允许多 Scan，但不能预设必填关系、引用图或坐标变换。

## 2. 先对齐四种“顺序”

| 对象 | 当前设计能表达什么 | 本轮要查的缺口 |
|---|---|---|
| Frame 索引 `n` | Scan 内身份和完整前缀范围 | 实际采集层怎样归组；是否需要设备来源 ID 追溯 |
| 设备来源 trigger/event ID | 可选诊断/追溯信息，不等于 Frame 身份 | 跳号、回绕、重复语义；多事件来源怎样说明，不默认补空行 |
| 原始采集位置 | Frame 绑定历史位置；PA 层级已确定 | 参考对象、单位、有效性、精度、来源及运动期间的位置含义 |
| 空间网格/算法顺序 | 目前未定义自动重建映射 | 扫描线、方向、邻接关系、重复位置与缺点如何处理 |

位置相同不等于同一 Frame，帧相邻不等于空间相邻，共同 Frame 不证明事件同时发生。真实采集准确性由采集层负责，SDK 不补时间配准。

## 3. 扫描场景核查

下列例子仅用于检查边界；访谈时应先标明“实际存在 / 不适用 / 尚不清楚”，不为不存在的场景扩展格式。

| 主题 | 当前约束与设计入口 | 需要补充的实际信息 | 若存在冲突，影响哪里 |
|---|---|---|---|
| A-01 一次扫描的边界 | [R-01](DESIGN.md#r-01)：停后继续、局部复扫/精扫、换探头、重装、重新标定或定义变化新建 Scan；同工件可留在未封存文件 | 实际开始/完成动作；暂停与结束如何区分；是否需要显式区域/来源关系及其实际含义；何时最终封存工件文件 | D-05/D-10/D-11；Scan 完成与文件封存分开，映射关系待决策，已封存文件不重开追加 |
| A-02 轨迹与触发方式 | [REC-01](DATA_SPEC.md#rec-01)、[POS-02](DATA_SPEC.md#pos-02)：记录轴不是空间网格 | 是否存在往返/蛇形、自由轨迹、回退、重复经过、非等距触发；触发与运动的关系；扫描线/方向信息来自哪里 | D-01/D-02/D-03；记录到空间选择的映射，不能用旧脚本的行列公式补齐 |
| A-03 输出与物理测点 | [REC-01](DATA_SPEC.md#rec-01)、[WAV-01](DATA_SPEC.md#wav-01)：事件/流身份明确、流内固定、跨流异构合法 | 实际设备怎样给出事件、阵元接收或合成输出身份；归组边界；几何偏移、各流采样解释来源 | D-01/D-02/D-07；流不等于硬件通道，接收层次不由 shape 猜测 |
| A-04 位置及异常 | [POS-01](DATA_SPEC.md#pos-01)、[POS-02](DATA_SPEC.md#pos-02)：明确的采集位置关联必需 | 位置指探头、工件还是运动机构；坐标系、轴向、单位、来源、标定关系；位置缺失/无效时设备与算法怎么做 | D-01；无效位置与波形缺失/业务无效不是同一语义，不能用零坐标代替 |
| A-05 固定采集方案来源 | [PAR-01](DATA_SPEC.md#par-01)：扫描/事件/流定义固定、跨帧复用 | 设备能否给出完整固定程序和必要设置；实际变化怎样在采集层识别并切换 Scan；固定领域定义怎样解释 | D-02/D-09；预定多法则重复不是变化；真实变化不能藏入快照 |
| A-06 过载和中断 | [WRT-01](DATA_SPEC.md#wrt-01)、[LIF-02](DATA_SPEC.md#lif-02)：阻塞写入，异常尽力只读恢复 | 持续/突发输入速率；设备缓存、可暂停性；阻塞后的调用方行为；取消、磁盘满和异常结束的用户预期 | D-02/D-05/D-10；区分输入交付、SDK 接受、持久化和可恢复，不承诺断电零损失 |

多通道单晶、PA、FMC、跨流异构及工件内多 Scan 已纳入逻辑范围，不再作为首版范围冲突。PA/FMC 同文件组合、独立时间轴、同流动态变长或同 Scan 内变更定义若有实际需求，仍须返回 DESIGN 重新决策，不能只改 shape。

## 4. 算法输入与读取方式核查

算法名称不等于数据访问方式。例如“A/B/C/D 显示”不足以决定存储布局，必须说明具体记录、通道、样本选择以及输出含义。

| 主题 | 审计问题 | 当前边界与关联 |
|---|---|---|
| A-07 波形数值与采样轴 | 算法接收原始整数码还是物理量？需要哪些 ADC 表示、采样间隔、起点/延迟和单位？样本索引转传播距离是否还依赖声速或路径模型？ | [WAV-01](DATA_SPEC.md#wav-01)、[WAV-02](DATA_SPEC.md#wav-02)，D-02/D-07/D-09；不预设设备字段，也不由 SDK 隐式换算 |
| A-08 单条/批量/门内计算 | 实际选哪些 Frame/流/声束/Tx/Rx？门按样本、时间还是距离给出，是否逐流或逐对变化？块大小和重复消费需求？ | [READ-02](DATA_SPEC.md#read-02)、[FMC-02](DATA_SPEC.md#fmc-02)，D-03/D-10；选择语义已定，物理门转换与频率待确认 |
| A-09 空间显示与重建 | 是否需要区域模型、共同参考系或 Scan 间来源关系？实际算法需要何种映射，其依据与责任方是什么？跨 Scan/跨文件消费怎样处理重复位置及分辨率差异？ | [SCAN-02](DATA_SPEC.md#scan-02)、[POS-02](DATA_SPEC.md#pos-02)，D-01/D-03/D-09/D-11；先收集事实再决定关系模型，不预设变换或缺失处理，不承诺自动拼接或复扫替代 |
| A-10 跨流/跨帧与 TFM 输入 | 相位/时间轴有哪些实际前提？是否需滑窗、重叠或随机回访？TFM 需要何种完整块、子矩阵及逐对窗口，传播模型从哪里取得？ | [FMC-02](DATA_SPEC.md#fmc-02)、[CAP-01](DATA_SPEC.md#cap-01)，D-02/D-03/D-10；稠密形状不证明共同时间轴，不要求逐像素 I/O |
| A-11 状态与可复现性 | 算法遇到业务无效、缺 payload、无效位置分别怎样处理？固定定义及外部模型是否足以复现输入？派生结果怎样追溯？ | [STA-01](DATA_SPEC.md#sta-01)、[PAR-01](DATA_SPEC.md#par-01)，D-01/D-08/D-09；SDK 不替算法过滤，也不把读取错误转成无效 |
| A-12 执行与资源 | 算法实时执行还是封存后执行？能否分批、是否要求连续数组、CPU/GPU 数据类型与布局是什么？内存和响应目标是多少？ | [R-07](DESIGN.md#r-07)、[CAP-01](DATA_SPEC.md#cap-01)、[CMP-02](DATA_SPEC.md#cmp-02)，D-03/D-06/D-10；实时路径走采集内存，GPU 计算与 GPU 解压分开审计 |

### 每个真实工作负载应留下的最小记录

不要先估计“单通道占主导”。对实际存在的算法/操作填写：

| 项目 | 需要记录的内容 |
|---|---|
| 输入来源与阶段 | 采集内存、正常封存文件或显式恢复视图；是否跨文件 |
| 选择 | 连续/离散 Frame、流/束/Tx/Rx/收发对、整波形/样本窗口；选择来源 |
| 顺序与关联 | 采集还是空间顺序；重复索引、位置、状态、固定定义关联 |
| 解释依赖 | 各流数值/采样轴、坐标系、事件/输出及矩阵映射、固定定义、标定和传播模型来源 |
| 输出与执行 | 张量轴顺序、dtype、连续性、分批/滑窗、CPU/GPU、缓冲所有权要求 |
| 负载与验收 | 请求大小、频率、并发、可接受延迟及内存预算；区分测量值与期望值 |
| 证据与预期 | 调用示例或算法输入说明、可共享的小样例及独立期望值；未知项显式留空 |

### 信息应该归在哪里

审计中发现必需信息时，先按现有职责分类，再讨论具体字段：

- **固定定义与解释**：扫描/事件/流设置、各流采样轴、输出及矩阵映射、必要几何和位置描述；不能依赖设备当前默认值，不能逐帧更换。
- **Frame 观测关联**：每帧的原始波形、状态、位置及正确固定引用；不是逐帧配置历史。
- **可选辅助块**：计划、独立反馈等；若缺少它就无法完成必要解释，不能继续把它称为可忽略。
- **工件容器与待定 Scan 映射**：文件内 Scan 归组和独立身份已确定；用途、区域、来源及坐标关系的必要性、模型、作用域和约束等待 D-11，不先归为必需固定定义。
- **外部/派生结果**：跨文件任务归组、处理输出等；若算法依赖外部标定或模型，须明确引用及可追溯边界，不能直接宣称文件自足或原始历史已被更新。

这只是审查分类方法，不预先决定所有标定、拓扑或处理参数必须存入哪条 HDF5 路径。

## 6. 审计记录与收敛方法

每个实际场景或算法可使用以下短模板，不要求一次填完全部待定项：

```text
场景/算法名称：
证据来源与适用设备/版本：
实际动作、输入与预期输出：
对应审计主题 A-xx：
涉及需求 R-xx / Spec 规则 / 待定项 D-xx：
结论：现有契约覆盖 / 需要补充 / 与现有约束冲突 / 本轮不适用 / 证据不足
拟调整内容及理由（未决定时明确标注）：
最小验证样例与独立期望值：
```

结论按以下规则落回权威文档：

1. 已覆盖：引用具体规则，不为了记录讨论再复制字段表。
2. 待补充：关联现有 D 项；新增待定领域仅在证据支持时加入 Spec 登记表。
3. 有冲突：先在 DESIGN 修订需求/范围，再同步 Spec 和测试计划，不能让实现默默改变契约。
4. 可验证：在 [SPEC_TEST_PLAN.md](SPEC_TEST_PLAN.md#scenario-validation) 中将场景映射为小型正反例；没有执行证据时不标为 PASS。

本轮只归位已确认契约并保留未知问题，不冻结坐标字段、算法实现、生产性能指标或物理参数，也不要求立即回答全部问题。历史性能证据的限制另见 [BENCHMARK_REPORT.md](BENCHMARK_REPORT.md)，不用于关闭上述剩余问题。
