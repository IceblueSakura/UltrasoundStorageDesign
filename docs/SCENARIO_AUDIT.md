# 扫描场景与算法需求审计

状态：**审计准备，尚未采集本轮场景证据或作出新产品决定**。本文整理现有设计如何接受实际场景检验，不是新增 schema、算法实现或审计通过报告。

需求与选择理由以 [DESIGN.md](DESIGN.md) 为准，字段语义和不变量以 [DATA_SPEC.md](DATA_SPEC.md) 为准，待定项仍只在其 [D-01～D-10 登记表](DATA_SPEC.md#open-items)维护。本文的 A 编号是讨论主题，不是新的需求编号；候选场景也不表示产品必须支持。

## 1. 本轮要回答什么

按“实际动作 → 设备交付 → 记录含义 → 算法输入 → 文件访问”的顺序核查：

1. 当前“同构多通道、共享触发与共享位置”的记录模型能否覆盖实际采集？
2. 保存的信息是否足以在离线、没有当前设备状态的条件下解释波形和位置？
3. 算法所需的数据选择、顺序、邻域和参数是否有明确来源？
4. 哪些是正确性必需信息，哪些只是性能调优，哪些超出现有首版范围？

先确认上述语义，再讨论布局、chunk、压缩和 GPU。历史脚本中的 C/S/dtype、规则网格和单通道负载均不得作为答案。

## 2. 先对齐四种“顺序”

| 对象 | 当前设计能表达什么 | 本轮要查的缺口 |
|---|---|---|
| 文件记录索引 `t` | SDK 追加后的文件内身份和前缀范围 | 是否需要通过来源 ID 追溯设备触发；异常交付如何报告 |
| 设备来源 trigger ID | 可选诊断/追溯信息，不等于 `t` | 跳号、回绕、重复的真实语义，不能默认补空行 |
| 采集位置 | 同一记录全部通道共享的历史位置关联 | 位置的参考对象、单位、有效性、精度和采集来源 |
| 空间网格/算法顺序 | 目前未定义自动重建映射 | 扫描线、方向、邻接关系、重复位置与缺点如何处理 |

位置相同不等于同一条记录，记录相邻不自动等于空间相邻。真实设备对物理位置的同步准确性由采集层负责，SDK 不补时间配准。

## 3. 扫描场景核查

下列例子仅用于检查边界；访谈时应先标明“实际存在 / 不适用 / 尚不清楚”，不为不存在的场景扩展格式。

| 主题 | 当前约束与设计入口 | 需要补充的实际信息 | 若存在冲突，影响哪里 |
|---|---|---|---|
| A-01 一次扫描的边界 | [R-01](DESIGN.md#r-01)：停后继续、局部重扫、换探头、重装、重新标定或布局变化新建文件 | 实际开始/结束动作；短暂停顿、设备暂停和结束后重启如何区分；多文件是否须共同展示或计算 | Session 边界；如需任务级关联，先核查外部清单是否足够，不直接加入 Segment |
| A-02 轨迹与触发方式 | [REC-01](DATA_SPEC.md#rec-01)、[POS-02](DATA_SPEC.md#pos-02)：记录轴不是空间网格 | 是否存在往返/蛇形、自由轨迹、回退、重复经过、非等距触发；触发与运动的关系；扫描线/方向信息来自哪里 | D-01/D-02/D-03；记录到空间选择的映射，不能用旧脚本的行列公式补齐 |
| A-03 通道与物理测点 | [R-02](DESIGN.md#r-02)、[WAV-01](DATA_SPEC.md#wav-01)：同构通道、共享位置、固定身份 | 通道代表探头、收发路径还是其他对象；同一触发是否真的全部到齐；是否存在通道空间偏移或各自的采样轴差异 | D-01/D-02/D-07；区分“共享参考位置”和“所有通道物理测点相同”，必要时复审 profile 适用性 |
| A-04 位置及异常 | [POS-01](DATA_SPEC.md#pos-01)、[POS-02](DATA_SPEC.md#pos-02)：明确的采集位置关联必需 | 位置指探头、工件还是运动机构；坐标系、轴向、单位、来源、标定关系；位置缺失/无效时设备与算法怎么做 | D-01；无效位置与状态 0/1 不是同一语义，不能用零坐标代替 |
| A-05 采集中参数变化 | [WAV-01](DATA_SPEC.md#wav-01)、[PAR-01](DATA_SPEC.md#par-01)：固定解释与动态快照分离 | 增益等参数是否变化、何时生效、涉及哪些通道；设备能否给出精确的记录边界 | D-02/D-09；实际变化若涉及布局或采样轴，应按当前契约新建文件，而非藏入快照 |
| A-06 过载和中断 | [WRT-01](DATA_SPEC.md#wrt-01)、[LIF-02](DATA_SPEC.md#lif-02)：阻塞写入，异常尽力只读恢复 | 持续/突发输入速率；设备缓存、可暂停性；阻塞后的调用方行为；取消、磁盘满和异常结束的用户预期 | D-02/D-05/D-10；区分输入交付、SDK 接受、持久化和可恢复，不承诺断电零损失 |

PA/FMC、异构通道或独立通道流若确有需求，记录为首版范围冲突，返回 DESIGN 重新决策；不把更改 shape 当作已经解决事件/张量语义。

## 4. 算法输入与读取方式核查

算法名称不等于数据访问方式。例如“A/B/C/D 显示”不足以决定存储布局，必须说明具体记录、通道、样本选择以及输出含义。

| 主题 | 审计问题 | 当前边界与关联 |
|---|---|---|
| A-07 波形数值与采样轴 | 算法接收原始整数码还是物理量？需要哪些 ADC 表示、采样间隔、起点/延迟和单位？样本索引转传播距离是否还依赖声速或路径模型？ | [WAV-01](DATA_SPEC.md#wav-01)、[WAV-02](DATA_SPEC.md#wav-02)，D-02/D-07/D-09；不预设设备字段，也不由 SDK 隐式换算 |
| A-08 单条/批量/门内计算 | 每次选哪些记录和通道？门按样本索引、时间还是距离给出？固定门还是逐记录变化？是否需要门外样本？ | [READ-01](DATA_SPEC.md#read-01)，D-03/D-10；物理门到样本区间的转换责任待确认，不能从历史 gate 切片推出算法需求 |
| A-09 空间显示与重建 | 输入是否要求规则网格、空间邻域、跨扫描线或跨文件？如何处理蛇形方向、缺点、重复位置、非等距点？谁提供坐标变换和标定？ | [POS-02](DATA_SPEC.md#pos-02)，D-01/D-03/D-09；SDK 目前不做插值或拓扑重建，若算法依赖这些信息需核查其保存或外部来源 |
| A-10 跨通道/跨记录运算 | 是否必须同时取全通道？通道身份/顺序、相位或采样轴关系有哪些前提？滑窗是否需要重叠、前后邻居或随机回访？ | [REC-01](DATA_SPEC.md#rec-01)、[WAV-01](DATA_SPEC.md#wav-01)、[CAP-01](DATA_SPEC.md#cap-01)，D-02/D-03/D-10；共享触发本身不证明任何算法所需的相位精度 |
| A-11 状态与可复现性 | 算法遇到业务无效波形、无 payload、无效位置、参数切换分别如何处理？能否仅凭文件重现输入解释？需要记录哪些处理参数/版本/来源记录？ | [STA-01](DATA_SPEC.md#sta-01)、[PAR-01](DATA_SPEC.md#par-01)、[R-11](DESIGN.md#r-11)，D-01/D-08/D-09；SDK 保留状态，算法过滤策略另定，派生结果不覆盖原始历史 |
| A-12 执行与资源 | 算法实时执行还是封存后执行？能否分批、是否要求连续数组、CPU/GPU 数据类型与布局是什么？内存和响应目标是多少？ | [R-07](DESIGN.md#r-07)、[CAP-01](DATA_SPEC.md#cap-01)、[CMP-02](DATA_SPEC.md#cmp-02)，D-03/D-06/D-10；实时路径走采集内存，GPU 计算与 GPU 解压分开审计 |

### 每个真实工作负载应留下的最小记录

不要先估计“单通道占主导”。对实际存在的算法/操作填写：

| 项目 | 需要记录的内容 |
|---|---|
| 输入来源与阶段 | 采集内存、正常封存文件或显式恢复视图；是否跨文件 |
| 选择 | 连续/离散记录、通道集合、整波形/样本区间；选择由什么产生 |
| 顺序与关联 | 采集顺序还是空间顺序；重复索引、位置、状态、配置是否随结果绑定 |
| 解释依赖 | 数值/采样轴、坐标系、通道映射、参数快照、标定等，分别从哪里取得 |
| 输出与执行 | 张量轴顺序、dtype、连续性、分批/滑窗、CPU/GPU、缓冲所有权要求 |
| 负载与验收 | 请求大小、频率、并发、可接受延迟及内存预算；区分测量值与期望值 |
| 证据与预期 | 调用示例或算法输入说明、可共享的小样例及独立期望值；未知项显式留空 |

## 5. 设计细节的阅读路线

结合场景逐项追踪，不从 benchmark 的实现反推规范：

| 环节 | 需检查的契约 | 仍不能从当前文档推出的细节 |
|---|---|---|
| 初始化 | [ID-01](DATA_SPEC.md#id-01)、[WAV-01](DATA_SPEC.md#wav-01)、[MAP-01](DATA_SPEC.md#map-01)：身份、固定解释和参考对象组织 | 正式标识、字段编码、支持的设备范围；SPLIT 尚非生产性能定案 |
| 提交 | [REC-01](DATA_SPEC.md#rec-01)、[WAV-02](DATA_SPEC.md#wav-02)、[WRT-01](DATA_SPEC.md#wrt-01)：完整记录、严格校验、阻塞、校验失败不修改 | 输入 API、所有权、取消、缺 payload 表示和设备缓冲 |
| 参数关联 | [PAR-01](DATA_SPEC.md#par-01)、[PAR-02](DATA_SPEC.md#par-02)：完整不可变快照及候选字节区 | 参数领域 schema、粒度、空快照、索引/offsets 编码 |
| 追加确认 | [REC-02](DATA_SPEC.md#rec-02)、[WRT-02](DATA_SPEC.md#wrt-02)：物理 extent 与完整前缀分离 | 返回/flush/持久化协议；跨 dataset 非事务，部分压缩 chunk 追加可能重写旧字节 |
| 封存/恢复 | [LIF-01](DATA_SPEC.md#lif-01)、[LIF-02](DATA_SPEC.md#lif-02)：封存拒写，异常只读验证可信范围 | 状态编码、可靠确认点、恢复损失范围；不得按最短 extent 猜数量 |
| 离线读取 | [ID-02](DATA_SPEC.md#id-02)、[READ-01](DATA_SPEC.md#read-01)、[READ-02](DATA_SPEC.md#read-02)：能力识别、独立/绑定读、候选选择规则 | 正式 API 与错误类型；半开区间、重复索引等仍为参考行为 |
| 算法消费 | [POS-01](DATA_SPEC.md#pos-01)、[CAP-01](DATA_SPEC.md#cap-01)、[CMP-01](DATA_SPEC.md#cmp-01)：历史关联、有界访问、无损解码 | 空间拓扑与处理模型、性能门槛；存储符合性不等于算法正确性 |

### 信息应该归在哪里

审计中发现必需信息时，先按现有职责分类，再讨论具体字段：

- **固定解释**：实例的样本/采样轴、通道映射和位置描述，不能依赖“设备当前默认值”。
- **记录关联**：每次触发的波形、状态、共享位置和配置引用。
- **参数快照**：影响相应记录的非布局设置，不能覆盖历史或改变固定布局。
- **可选辅助块**：计划、独立反馈等；若缺少它就无法完成必要解释，不能继续把它称为可忽略。
- **外部/派生结果**：任务归组、处理输出等；若算法依赖外部标定或模型，须明确引用及可追溯边界，不能直接宣称文件自足或原始历史已被更新。

这只是审查分类方法，不预先决定所有标定、拓扑或处理参数必须存入哪条 HDF5 路径。

## 6. 审计记录与收敛方法

每个实际场景或算法可使用以下短模板，不要求一次填完全部待定项：

```text
场景/算法名称：
证据来源与适用设备/版本：
实际动作、输入与预期输出：
对应审计主题 A-xx：
涉及需求 R-xx / Spec 规则 / 待定项 D-xx：
结论：现有契约覆盖 / 需要补充 / 与现有约束冲突 / 本轮不适用 / 证据不足
拟调整内容及理由（未决定时明确标注）：
最小验证样例与独立期望值：
```

结论按以下规则落回权威文档：

1. 已覆盖：引用具体规则，不为了记录讨论再复制字段表。
2. 待补充：关联现有 D 项；新增待定领域仅在证据支持时加入 Spec 登记表。
3. 有冲突：先在 DESIGN 修订需求/范围，再同步 Spec 和测试计划，不能让实现默默改变契约。
4. 可验证：在 [SPEC_TEST_PLAN.md](SPEC_TEST_PLAN.md#scenario-validation) 中将场景映射为小型正反例；没有执行证据时不标为 PASS。

本轮整理不冻结位置字段、算法集合、生产性能指标或物理参数，也不要求立即回答全部问题。历史性能证据的限制另见 [BENCHMARK_REPORT.md](BENCHMARK_REPORT.md)，不用于关闭上述语义问题。
