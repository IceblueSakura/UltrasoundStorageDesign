# ADR-0002：Flush 承诺、写失败态、提交记录与校验和

- 状态：已采纳（2026-10-24，Spec 0.3-draft）；决定 1、2 中关于断电、操作系统崩溃与操作系统层同步的部分已被 [ADR-0008](0008-process-crash-scope.md) 替代；`MAP-02` + 按 Scan SWMR、禁原位重试与空对象边界已由 [ADR-0018](0018-storage-engine-swmr-and-strict-lifecycle.md) 正式选定（多级块索引大文件 SIGKILL 待 M2 复核）
- 规则落点：[WRT-01](../DATA_SPEC.md#wrt-01)、[WRT-02](../DATA_SPEC.md#wrt-02)、[WRT-03](../DATA_SPEC.md#wrt-03)、[IO-01](../DATA_SPEC.md#io-01)、[LIF-01](../DATA_SPEC.md#lif-01)、[LIF-02](../DATA_SPEC.md#lif-02)、[VAL-01](../DATA_SPEC.md#val-01)、[参考写入保护机制](../DATA_SPEC.md#map-02)
- 仍未决定：带失败标记封存的编码、重试规则与绑定层失败（D-05/D-07/D-10/D-12）
- 补充：[ADR-0009](0009-review-contract-clarifications.md) 规定失败态时活动的 Scan 在带失败标记封存后保持未完成

## 背景

0.2 只规定了目标：显式 Flush 强制落盘，批次写失败不改变旧数据，异常文件只读恢复。对 HDF5 2.2.0 的源码核对和进程崩溃实验（脚本在 `experiments/m1/probes/`）表明，默认机制兑现不了这些目标：

| 现象 | 证据 |
|---|---|
| 压缩 chunk 重写时，大小不变就原地覆写，大小变化就释放旧块再分配；无压缩 chunk 一律原地覆写 | `H5Dchunk.c` 的 `H5D__chunk_file_alloc` 及缓存写出路径 |
| 释放块先尝试收缩文件，之后才看空间策略，`H5F_FSPACE_STRATEGY_NONE` 救不了文件末尾的块 | `H5MF.c` 的 `H5MF_xfree` |
| HDF5 从不 fsync；sec2 驱动的 flush 回调为 NULL，Windows 驱动就是 sec2 | `H5FDsec2.c:151`、`H5FDwindows.h:28` |
| v3 superblock 文件在写者崩溃后，普通只读打开失败；`h5clear` 清除状态标志需要改写文件（2026-10-25 补充：h5clear 所用的 fapl 属性也能只在内存中清除，见决定 7） | `H5Fint.c:2237-2241`、`H5Fint.c:2165-2172` |
| 写入 → H5Fflush+fsync → 继续追加 → 进程崩溃：已 Flush 的帧读取报错，或在空间复用时**静默错值** | `probes/flush_crash.py` |
| 同条件下"整 chunk 只写一次 + 尾部 A/B 日志 + 双槽提交记录"恢复出全部已 Flush 帧；SWMR 模式不回收空间，探针中也未丢数据（观察到，非保证） | `probes/writeonce_journal.py`、`probes/flush_crash.py` |

## 决定

1. **Flush 成功后条件。** 对进程崩溃：Flush 返回成功后，在此之前所有成功写入的 Frame 及解释它们所需的元数据，在之后任意时刻的进程崩溃（包括后续追加、Flush、完成 Scan 与封存期间）后都能由恢复模式完整恢复并通过校验。对断电和操作系统崩溃：只在声明的环境（操作系统、文件系统、本地块设备）上承诺同一后条件，并用断电模拟工具（如 LazyFS）单独取证；未取证的环境不作声明。（断电与操作系统崩溃部分已由 ADR-0008 撤回。）
2. **Flush 的实现要求。** 刷新 SDK 与库缓存之后，还必须完成操作系统层的同步（Linux `fsync`、Windows `FlushFileBuffers`）；新建文件还要同步所在目录。单独调用 `H5Fflush` 不算 Flush。（已由 ADR-0008 替代：Flush 只需把数据交给操作系统，不要求操作系统层同步；只调用 `H5Fflush` 仍不足以满足决定 1。）
3. **提交记录唯一权威。** 每个 Scan 由 SDK 维护提交记录（N、各帧轴对象的行数、校验值），它是该 Scan 可见范围的唯一依据；HDF5 dataset 的 extent 只是上界。
4. **完整性校验和是格式的必需部分。** 每个物理块保存存储字节与解码后字节的校验值，作为深度检查、恢复核对和"旧数据未变"的独立观察依据。具体算法与编码属 D-07。
5. **写失败态。** 写调用、Flush、完成 Scan 或封存中出现任何 I/O 错误，Writer 进入失败态，拒绝继续追加。之后只允许两种操作：放弃并关闭；或在全部已提交数据通过校验后"带失败标记封存"。封存失败则走恢复路径。IO-01 的"此前成功写入的数据不变"细化为：失败调用不得覆写或修改已提交的数据与关联，并且可以通过校验和观察到这一点。
6. **完成 Scan 隐含 Flush**，并写入该 Scan 的完成与校验记录。
7. **恢复不改源文件。** 需要清除状态标志时在副本上进行，或者使用 SWMR 只读路径；建议在独立进程中执行（HDF5 2.0 修复了 19 个、2.1 修复了 3 个与畸形文件相关的 CVE）。（2026-10-25 补充：也可以只在内存中清除状态标志、原地只读打开，结果与副本一致，见 [M1 报告](../../experiments/m1/REPORT.md)第 3 节。）

## 参考机制（不冻结）

- 主数据集的 chunk 只写一次：SDK 按流组组装整 chunk、自行编码（可在 HDF5 锁外并行），用 `H5Dwrite_chunk` 写入；Scan 完成时，最后一个半满 chunk 也只写这一次。
- Flush 时，各帧轴对象的半满尾部写入 A/B 双槽日志，不碰主数据集。
- 可选：每个 Scan 先在非 SWMR 状态下创建对象，再进入 SWMR 追加，以获得元数据写入顺序与不回收空间的性质。

这些机制只是满足上述决定的一种候选，正式布局在 M2 冻结前取证选定（D-05/D-07）。

## 后果

- D-05 从"选择保证"收窄为"取证与编码"：断电声明（已由 ADR-0008 移出范围）、HDF5 元数据刷新期间崩溃的覆盖、带失败标记封存的编码；交替槽位写入提交记录属参考机制（MAP-02）。
- T-14/T-15 增加故障注入点、写失败注入与恢复校验；`kill -9` 不丢页缓存，因此不能代替断电测试（断电测试已由 ADR-0008 移出范围）。
