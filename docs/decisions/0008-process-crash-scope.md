# ADR-0008：持久化只覆盖进程崩溃，不考虑断电与操作系统崩溃

- 状态：已采纳（2026-10-25，用户决定）；高频 Flush 不要求 `fsync` 维持有效，[ADR-0021](0021-hdf5-simplification-wal-push-only-and-ndt-fixes.md) 补充规定低频 `complete_scan`/`seal`/旁路提交强制 `fsync`/`FlushFileBuffers`。
- 规则落点：[WRT-03](../DATA_SPEC.md#wrt-03)、[IO-01](../DATA_SPEC.md#io-01)、[MAP-02](../DATA_SPEC.md#map-02)、D-05

## 背景

ADR-0002 在声明的环境中承诺断电后同样可恢复，为此要求 Flush 执行 `fsync`，并用断电模拟工具单独取证。用户明确：不考虑断电与系统崩溃时的恢复，本阶段只需确保公开 API 的稳定性。用户随后确认，“系统崩溃”指操作系统崩溃；上位机进程自身崩溃仍在 Flush 后条件内。

## 决定

1. 断电、操作系统崩溃与存储设备故障后的数据状态不在 SDK 的保证范围内：不作承诺，不为其取证。此类事件后，文件可能丢失最近的写入，甚至无法打开；恢复模式只能尽力而为。
2. Flush 的成功后条件只针对进程崩溃，表述与 ADR-0002 相同：Flush 返回成功后，之前所有成功写入的 Frame 在之后任意时刻的进程崩溃后，都能由恢复模式完整恢复并通过校验。
3. Flush 不要求操作系统层同步，只需把 SDK 与 HDF5 缓存中的数据交给操作系统。是否额外同步属实现选项，不构成对外承诺。前提是 Linux 本地文件系统：进程退出后，内核仍会写回其页缓存，其他进程也能立即读到。网络文件系统不在本阶段范围内。
4. 进程崩溃保护来自“含已提交数据的块不再重写”（MAP-02），而不是来自 `fsync`。ADR-0002 中的其余决定（写失败态、提交记录、校验值、完成 Scan 隐含 Flush、恢复不改源文件）不变。

## 理由与证据

- 进程被杀后页缓存不丢，`fsync` 只对断电和操作系统崩溃有意义。
- M1 第二轮去掉 `fsync` 后，112 次随机 SIGKILL 与 22 个故障点仍全部满足 Flush 后条件；而保留 `fsync` 的普通 HDF5 追加，58 次 SIGKILL 中有 28 次丢失已 Flush 的帧。见 [实验报告](../../experiments/m1/REPORT.md)。
- 每 8 帧 Flush 一次时，单次 Flush 的中位耗时从 2.5–3.1 ms（含 `fsync`，btrfs/NVMe）降到 0.3–0.5 ms，写入吞吐从约 150 MB/s 升到约 185 MB/s。

## 后果

- WRT-03 删去断电条款与 `fsync` 要求；D-05 删去断电环境声明与模拟取证；T-15 只做进程崩溃测试，不再需要 LazyFS 一类工具。
- MAP-02 中的“同步”改为把库缓存写给操作系统（`H5Fflush`）。
- 若将来需要断电保证，可以给 Flush 增加可选的设备同步。Flush 带预留的标志参数（[ADR-0010](0010-public-api-stability.md)），这一扩展不需要改动 API。
