## 结论摘要

| 问题 | 结果 | 证据强度 |
|---|---|---|
| 参考机制能否兑现 WRT-03 的 Flush 后条件（进程崩溃） | 能。Flush 不含 `fsync` 时，随机 SIGKILL 共 112 次、故障点 22 个（非 SWMR 与 SWMR 各一半），恢复出的已验证前缀从未短于已 Flush 范围，恢复帧全部与源数据逐位一致；第一轮（含 `fsync`，117 次 SIGKILL）结果相同 | 观察到；只覆盖进程崩溃（ADR-0008 的范围） |
| 不用该机制会怎样 | 普通 HDF5 追加 + `H5Fflush`+`fsync` 在 58 次 SIGKILL 中有 28 次让已 Flush 帧读取报错（第一轮 19/58）；SWMR 模式的普通追加 56 次未出错 | 观察到；印证 ADR-0002 的风险 |
| Flush 是否需要 `fsync` | 进程崩溃范围内不需要（见第一行）。每 8 帧 Flush 一次时，单次 Flush 的中位耗时由 2.5–3.1 ms 降到 0.3–0.5 ms，写入吞吐由约 150 MB/s 升到约 185 MB/s | 测量；btrfs/NVMe，单线程 |
| 非 SWMR 的崩溃文件能否不复制就恢复 | 能。用 `h5clear` 所用的 fapl 属性只在内存中清除状态标志，原地只读打开；65 次崩溃（53 次随机、12 个故障点）的恢复结果与“副本 + `h5clear`”逐项一致；原型每次恢复前后，源文件的 SHA-256 都不变 | 观察到；依赖 HDF5 私有属性 |
| 写 I/O 失败（EFBIG） | 调用失败、Writer 进入失败态、后续写/Flush/封存被拒；空间恢复后带失败标记封存成功，普通 Reader 读到全部 72 个已提交帧（含 32 个未 Flush 帧）和失败标记；空间不恢复时封存失败，恢复得到全部 40 个已 Flush 帧 | 观察到；只测了 EFBIG 一种错误 |
| 读失败的原子性 | 损坏一个存储块后，push 目标（样本、位图、记录）逐字节不变，poll 不发布结果，旧借用已结束；深度校验把验证前缀停在损坏块之前 | 观察到 |
| 校验和是否必要 | 无压缩时，HDF5 普通读取对损坏块**静默返回错误数值**；deflate 时 HDF5 报错。单阶段读（不先校验）在两种 codec 下都已改写目标后才失败或返回错值 | 观察到；支持 ADR-0002 第 4 条 |
| 两阶段 push 读的代价 | 见第 6 节；压缩数据上比单阶段慢约 6%，无压缩数据上 CRC 成本占主导 | 测量；Python 原型、热缓存 |
| 固定内存池能否遍历整个 Scan | 能。3 个 64 帧的 push 槽位（共 46 MB）遍历 2995 帧（解码后 749 MB），进程常驻内存约 100–104 MB，不随已读帧数增长；Batch 未按存储块对齐时，顺序吞吐低约 19%，随机读多解码一个块 | 测量；数据量小于内存，不是超 RAM 证据 |
| 写出格式能否被 1.x 读取 | HDF5 1.14.6 经自身 filter 解码读取 2.2.0 写出的四个文件（含直接块写入的压缩块、SWMR 写出的文件），与导出数据逐值一致，全部校验值吻合 | 观察到；独立核对与原型同一作者 |
| 并发范围 | 4 个线程各持 Reader 读同一文件、同时另一线程写另一文件，无错且数据正确；3 个进程同时只读同一已封存文件结果一致；Writer 打开期间另一进程打开同一文件被 HDF5 文件锁拒绝 | 观察到；文件锁可被环境变量关闭，SDK 仍需自行检测 |

## 1. 往返与独立核对

`test_roundtrip`：导出数据以 1–32 帧不等的批次写入（共 281 次调用，每 8 次 Flush），完成 Scan 并封存，重开后：

- `check_independent.py`（不导入原型，按 README 的布局说明解析）在 HDF5 2.2.0 与 1.14.6 下分别核对 `shuffle-deflate1`、`shuffle-deflate1`+SWMR、`deflate1`、`none` 四个文件：374,375,000 个样本值、374,369 个有效槽位与 6 个无效槽位、全部帧记录一致；无效槽位全为 0；每块的存储字节与解码后字节 CRC 及校验表链全部吻合。
- 原型 Reader 以 B=100 的 poll 逐批读取，与导出数据一致；元信息内容逐字节返回；深度校验覆盖完整前缀。

| codec | 文件大小 | 写入总耗时 | 其中读取源数据 |
|---|---:|---:|---:|
| none | 760 MB | 2.3 s | 1.7 s |
| deflate1 | 274 MB | 6.3 s | 1.7 s |
| shuffle-deflate1 | 217 MB | 6.0 s | 1.8 s |
| shuffle-deflate1 + SWMR | 217 MB | 6.0 s | 1.7 s |

单线程 Python 编码约 200 MB/s；SWMR 模式未见额外写入开销。第一轮的耗时（4.0/8.2/7.7/7.6 s）包含 `fsync`，读取源数据时缓存也更冷，不能直接比较。

## 2. 语义与写入校验

- `test_semantics`（21 项）：poll Batch、push Batch、单帧读取与选择层 A 扫结果一致；流清单 `[2,0,2]`、样本清单 `[3,1,3]` 保序保重复；越界窗口、越界流、超出 N 的 Batch、空 Batch、未知流组均被拒绝而非截断。借用：目录/元信息/生命周期/块几何查询不结束借用，push 读与被拒绝的读都结束借用，另一 Reader 的读取不影响，关闭 Reader 结束借用，push 目标在 Reader 关闭后仍可用，poll 数组只读。块几何查询 `layout()` 返回每块帧数与每帧样本、位图、帧记录的字节数。
- `test_validation`（23 项）：位图缺失、长度不符、非 bool、帧数不一致、dtype 转换、S+1、`valid=1` 缺波形、帧记录缺失或布局不符、未知流组，均整调用拒绝且 N 不变；`valid=0` 带非零输入被零填充，严格模式下被拒绝；活动 Scan 未完成时新建 Scan、封存被拒，完成后写入被拒；PA 文件拒绝 Tx×Rx 组与单晶通道组（DOC-01）。

## 3. 进程崩溃（WRT-03、LIF-02）

`test_crash`：源为前 800 帧；原型写两个 Scan（各 400 帧，批次 1–12 帧随机，每 2–6 次调用 Flush 一次），每次 Flush 返回后把范围写入并同步一个旁路文件。父进程在随机时刻 SIGKILL，然后用恢复模式打开并核对。第二轮 Flush 不含 `fsync`；恢复依次尝试普通只读、SWMR 只读、内存中清除状态标志、副本 + `h5clear`。凡用第三种方式打开的文件，再用副本方式恢复一次并比较两份报告；每次恢复前后都核对源文件的 SHA-256。

| 写入方式 | 运行次数 | 被杀 | 违反 Flush 后条件 | 恢复的打开方式 |
|---|---:|---:|---:|---|
| 原型 | 60 | 53 | 0 | 53 次内存中清除标志，均与副本一致 |
| 原型 + SWMR | 60 | 59 | 0 | 58 次 SWMR 只读，1 次已正常关闭 |
| 普通追加（Flush 含 `fsync`） | 60 | 58 | 28（已 Flush 帧读取报错） | 副本 + `h5clear` |
| 普通追加 + SWMR | 60 | 56 | 0 | SWMR 只读 |

故障点（两种模式各 11 个）：创建第二个 Scan 之后、写块之后、日志写后同步前、提交记录写后同步前、最后半满块写后、完成记录之后、封存记录前后。全部满足：已 Flush 范围都在已验证前缀内；声明范围总是等于验证范围；完成前被杀的 Scan 恢复为 active，完成后的为 complete。非 SWMR 的 11 个故障点，以及 SWMR 模式中创建第二个 Scan 时的窗口（此时文件尚未进入 SWMR），都以内存中清除标志的方式恢复，与副本结果一致。

需要注意的现象：

- **恢复不需要复制整个文件**（修正第一轮的结论）。v3 superblock 的写访问标志使普通只读打开失败，第一轮因此在副本上执行 `h5clear`，对 100 GB 级文件就意味着先复制 100 GB。HDF5 的 `H5F_open` 在只读一致性检查之前读取 fapl 属性 `clear_status_flags`（`h5clear` 与 HDF5 自身测试所用），只在内存中清除状态标志（`H5Fint.c:2165-2172`）；只读打开不会写回文件。原型通过 ctypes 设置该属性后原地打开，结果如上。代价：该属性是 HDF5 的私有属性，每次升级 HDF5 都须复核；完全基于公开 API 的替代做法是一个只读 VFD，在读取 superblock 时修补状态标志及其校验和。
- 封存记录已写入、但 `H5Fclose` 尚未完成时被杀，文件带“已封存”标记却不能普通打开。`H5Fclose` 会改写 superblock 的状态标志，因此封存成功的定义必须包含 HDF5 关闭。
- 普通追加加 SWMR 在两轮中都未丢已 Flush 帧，与评审阶段的探针一致（SWMR 不回收空间）。但这只是未观察到失败，不能当作保证：它仍会原地重写尾块。

## 4. 写 I/O 失败（WRT-01、IO-01、LIF-01）

`test_io_failure`：40 帧并 Flush，再写 8 帧，然后用 `RLIMIT_FSIZE` 把文件上限设为当前大小加 1.5 MB，继续写到失败。失败发生在 `H5Dwrite_chunk` 写原始块时（errno 27），此时已提交 72 帧。

- 失败后，写入、Flush、普通封存均以状态错误拒绝，没有被当作输入错误。
- 暂时性：恢复上限后，`seal_with_failure` 先把尾部日志与提交记录交给操作系统，再深度校验已提交数据，最后写失败标记。普通 Reader 看到 `sealed_with_failure`、失败原因和 72 个已提交帧；数据与独立核对均通过。失败调用写出的不完整块位于提交范围之外，没有影响读取。
- 持续性：`seal_with_failure` 在刷新阶段同样遇到 EFBIG 而失败；恢复得到 40 个已 Flush 帧，未 Flush 的 32 帧丢失。这符合 WRT-03：只有 Flush 作出承诺。

`test_read_failure`：200 帧的已封存文件，复制后翻转第 3 块（帧 48–63）中间的 64 个字节。

| | `none` | `shuffle-deflate1` |
|---|---|---|
| 两阶段 push 读帧 40–71 | 失败；目标逐字节不变 | 失败；目标逐字节不变 |
| poll 读同一范围 | 失败，无视图 | 失败，无视图 |

## 6. 两阶段 push 读的代价（测量，无门槛）

`bench_push_read`：完整导出文件，随机起点，单线程，热页缓存，取中位数。

| codec | B | 两阶段 push | 单阶段 push（无校验） | HDF5 `read_direct` | 暂存的存储字节 |
|---|---:|---:|---:|---:|---:|
| shuffle-deflate1 | 1 | 11.0 ms | 10.4 ms | 6.2 ms | 1.1 MB |
| shuffle-deflate1 | 16 | 23.1 ms | 21.7 ms | 12.3 ms | 2.2 MB |
| shuffle-deflate1 | 64 | 55.9 ms | 52.6 ms | 30.8 ms | 5.6 MB |
| none | 1 | 1.10 ms | 0.15 ms | 0.09 ms | 4.0 MB |
| none | 16 | 2.28 ms | 0.34 ms | 0.21 ms | 8.0 MB |
| none | 64 | 6.59 ms | 1.61 ms | 0.65 ms | 20 MB |

解读：

- 两阶段读的额外开销主要是 CRC 计算，不是暂存复制。压缩数据上开销约 6%；无压缩数据上，CRC 要扫描整块存储字节（B=1 时为 4 MB），因此占主导。
- 单帧与 A 扫随机读须解码并校验整块。每块 16 帧时，一次 A 扫要读约 1.1 MB 压缩字节、解码 4 MB。这是 D-04 中块帧数的直接权衡。
- 原型比 HDF5 原生读取慢约 1.8 倍，原因是 Python 的 zlib 与 numpy 反 shuffle。这不是机制本身的代价。

## 7. Flush 开销（ADR-0008，测量，无门槛）

`bench_flush`：480 帧，每次调用写 8 帧后立即 Flush；两种方式交替各运行两次。

| Flush 方式 | 中位耗时 | p95 | 最大 | 写入吞吐 |
|---|---:|---:|---:|---:|
| `H5Fflush` | 0.34 / 0.45 ms | 0.50 / 0.60 ms | 0.57 / 0.80 ms | 186 / 183 MB/s |
| `H5Fflush` + `fsync` | 2.52 / 3.06 ms | 3.64 / 3.71 ms | 3.84 / 8.60 ms | 151 / 150 MB/s |

Flush 越频繁，差距越大。在进程崩溃范围内，`fsync` 不带来额外保证（第 3 节）。数字只代表本机的 btrfs/NVMe。

## 8. 固定内存池遍历（角度 15，测量）

`bench_pool_stream`：按 `layout()` 返回的块几何分配 3 个各 64 帧（4 块）的 push 槽位，循环复用，遍历整个 Scan；消费者对每帧样本求和。

- 常驻内存：打开文件前 47 MB；遍历到 25%、50%、100% 时分别为 103、103、102 MB，峰值 103 MB；槽位共 46 MB。起点错开半块时为 104、100、102 MB。
- 顺序遍历：按块对齐 327 MB/s；起点错开半块 265 MB/s（边界块被相邻两个 Batch 各解码一次）。两种方式交付的每帧数据一致。
- 随机读（40 次取中位数）：

| Batch | 按块对齐 | 错开半块 |
|---|---:|---:|
| 16 帧 | 11.6 ms（解码 1 块） | 22.4 ms（2 块） |
| 64 帧 | 46.9 ms（4 块） | 55.8 ms（5 块） |

解读：内存由槽位数与 Batch 大小决定，与 Scan 长度无关；错位的代价就是多解码的边界块，只要提供块几何查询并让 Batch 对齐即可消除。数据量（749 MB）小于内存，不能替代 T-18 的超 RAM 验证。

## 对设计的含义

以下是建议，不是已作出的决定：

1. **D-05**：恢复已不需要复制文件（第 3 节），采用 SWMR 的理由只剩元数据写入顺序这一条。本轮每个 Scan 只有 25 个块，块索引很小；建议在块数多、索引多级的文件上比较两种模式的崩溃结果后再定。SWMR 属实现内部选择，不影响公开 API。
2. **D-05/D-07**：封存成功的定义应包含 `H5Fclose`。读到“已封存”标记但文件无法普通打开时，应转入恢复，而不是报告为损坏。
3. **D-07**：校验值必须存在（无压缩数据损坏时 HDF5 会静默返回错值）。算法应选择有硬件加速的类型（如 CRC32C），以降低两阶段读的成本；校验粒度宜与块一致。
4. **IO-01 的 push 语义**：两阶段读在压缩数据上的代价不大，暂存只占存储字节。本轮证据不支持放宽“失败时目标不变”。
5. **D-04**：块帧数同时决定 A 扫随机读的放大量、写入端的整块组装内存与 Batch 对齐粒度，应在真实负载与目标 A 扫比例下取舍。
6. **D-10**：提供块几何与容量查询，上位机据此分配内存池槽位并对齐 Batch（[角度 15](../../docs/DECISION_DIRECTIONS.md#angle-15)，内存池设计已暂缓）。
7. **ADR-0008**：Flush 只调用 `H5Fflush` 即可满足进程崩溃范围内的后条件，Flush 频繁时每次约省 2.5 ms。

## 未覆盖

- 断电与操作系统崩溃不在范围（ADR-0008），未测试。
- 块索引规模：每个 Scan 只有 25 个块，HDF5 块索引很小；块数多、索引多级时元数据刷新期间的崩溃没有覆盖（D-05）。
- 只测了 EFBIG 一种写错误。EIO、延迟写回错误，以及 HDF5 元数据刷新阶段的失败，都没有单独注入。
- H/P/F/W 合成夹具、FMC、异构多流组、多 Scan 的 UC 断言都没有执行。真实负载只有单一 PA 流组。
- Windows（本阶段不在范围）、语言绑定（pybind11/.NET）、GC 与资源生命周期均未测试；超 RAM 与持续负载也未测试。
- 独立核对与原型出自同一作者、同一语言。1.14 读取证明的是格式可读，不是第三方实现互通。
